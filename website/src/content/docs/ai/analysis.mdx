分析ステップでは、記録された決定点から繰り返し現れる「状況 → 行動」の組み合わせを見つけ、
規則の条件として表現します。パイプラインの中で、パターンを見つける判断が必要になる段階です。

この役割には LLM を使えますが、実装は **`Analyzer` インターフェース**として差し替えられます。

```go
type Analyzer interface {
	Propose(v *Vocabulary, records []Record) (
		candidates []Candidate, uncovered []Record, err error)
}
```

返り値の `uncovered` には、**どの規則でも説明できなかった決定点**が入ります。これを調べることで、
追加すべき述語や規則の候補を見つけられます。

`SequentialCovering` は、決定的に動くベースライン実装です。各ラウンドで、残っているレコードを
最も多く正しく被覆する特徴量と行動の組を選びます。反例がない組を優先し、規則として追加したら、
実行時にその規則が処理するレコードを対象から外します。同点の場合は語彙の順序で決めるため、
結果を再現できます。この実装により、LLM を使わずにパイプライン全体をテストできます。
どの Analyzer も**同じ形式の成果物**を返すため、分析役を入れ替えてもレビュー、マージ、コード生成は
変わりません。

## LLM に任せる場合

LLM を使うために必要なのは、
[`skills/behavior-analyze/`](https://github.com/shibukawa/ebigentserver/tree/main/skills/behavior-analyze)
のフォルダです。詳しく分析する場合は `duckdb` の CLI も使えます。スクリプトは Python の標準
ライブラリだけで動くため、追加パッケージは不要です。

LLM を framework から API 経由で呼ぶことはありません。**開発者自身の agentic 環境**で skill として
実行し、ファイルを介してパイプラインと入出力を交換します。

<Steps>

1. **エクスポート** — パイプラインが `analysis-request.json` を書き出します。

2. **分析** — LLM が読み、`proposals.json` を書きます。

3. **検証** — Python 側と Go 側で二重に検証します。

4. **マージ** — 差分としてライブラリへ取り込みます。

5. **承認** — エディタで人が採用するかどうかを決めます。

</Steps>

### 分析役に渡るもの

```json
{
  "game": "tictactoe",
  "features": [
    {"name": "cell_4_empty", "doc": "中央が空いている",
     "go_expr": "obs.Board[4] == ttt.Empty"}
  ],
  "actions": [
    {"name": "play_4", "doc": "中央に打つ", "go_expr": "ttt.Move{Cell: 4}"}
  ],
  "records": [
    {"episode": "ep-001", "tick": 3, "slot": 1,
     "action": "play_4", "bits": "010110001"}
  ],
  "library": { "chips": [] },
  "corpus_root": "episodes/"
}
```

`bits` は、特徴量の順序に合わせて `0` / `1` を並べた文字列です。コーパスが大きくても読みやすく、
diff を取りやすい形式です。

重要な制約として、**条件には `features` にある名前しか使えません**。一覧にない情報は実行時の
agent から見えないため、検証時に拒否します。

### 既存ライブラリを渡す意味

分析役には、既存の `library` も渡します。承認済みの規則を再提案しないだけでなく、却下済みチップの
`reject_reason` を確認できます。これにより、**却下理由を解消しないまま同じ候補を繰り返すこと**を
防ぎます。

### 分析役が返すもの

```json
{
  "game": "tictactoe",
  "candidates": [
    {"condition": "cell_4_empty", "action": "play_4",
     "rationale": "中央が空いているときは一貫して中央が選ばれている",
     "evidence": [{"episode": "ep-001", "tick": 3}]}
  ],
  "predicates": [
    {"name": "fork_available",
     "doc": "2方向のリーチを同時に作れる手があるか",
     "go_draft": "func ForkAvailable(obs ttt.Sight) bool { ... }",
     "rationale": "現在の語彙では、中央を取る手と分岐を作る手を区別できない"}
  ],
  "notes": "レビュー向けの要約"
}
```

候補は順序付きの**決定リスト**として扱います。前の規則を優先するため、後ろの条件に前の条件の
否定を加える必要はありません。被覆数も分析役では計算せず、検証側がレコードから再計算します。

`predicates` には、語彙へ追加する述語を提案します。現在の語彙では二つの決定を区別できない場合に
使います。`go_draft` は開発者が実装を始めるための案であり、そのまま実行可能なコードとしては
扱いません。

## 提案は権威ではない

<Aside type="caution" title="信頼境界はここにある">
`ValidateProposals` が信頼境界です。条件と行動が語彙に含まれるかを照合し、分析役が示した数値は
**特徴量化したレコードからすべて再計算します**。引用された証拠が実在するかも確認します。
</Aside>

検証は、Python と Go の二か所で実行します。

```bash
python3 skills/behavior-analyze/scripts/validate_proposals.py --request analysis-request.json --proposals proposals.json --out validated-proposals.json
```

分析役は、このコマンドを使って提案を事前に修正できます。終了コード 0 は問題なし、1 は拒否または
訂正した主張があることを示します。

その後、`ebigent merge` も上流の結果を信用せず、**独立してもう一度検証します**。validated ファイルを
使っても、Go 側の検証を省略することはできません。

## 判断の指針

skill が分析役へ渡す指針は、人が手作業で分析するときにも使えます。

- 被覆数が大きくても反例が多い規則は、条件が不十分です。反例を分離できる述語を検討します。
- 重なり合う規則を増やすより、少数の明確な規則へ順序を付けます。生成するのは、人が読む
  決定リストだからです。
- **コーパスを仕様として扱います**。コーパスに現れない状況は推測せず、「現れなかった」と
  記録します。

## 掘るための道具

```bash
python3 skills/behavior-analyze/scripts/corpus_stats.py --request analysis-request.json --cooccurrence
```

実行すると、特徴量 × 行動の純度表が出ます。一つの行動に集中する特徴量は、チップの候補です。
純度が低い特徴量は、**より具体的な述語が必要**であることを示します。この場合は反例の多いチップを
作るのではなく、`predicates` へ新しい述語を提案します。

```bash
python3 skills/behavior-analyze/scripts/corpus_stats.py --corpus episodes/ --sql "SELECT ..."
```

`decisions` / `events` / `outcomes` の view が作られた状態で SQL を実行できます。ヘッダ行は
除外済みです。outcomes から勝ちと相関する規則を調べ、events の拒否から操作に迷った箇所を探せます。
