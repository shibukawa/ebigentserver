生成された AI の一番の問題は、強さではなく**直せなさ**にある。なぜこの手を選ぶのかを説明できず、
一箇所だけ変えることもできない。

## 承認ゲート

チップは承認されるまでライブラリの中で不活性のまま残る。

```go
func (l *Library) Approved() []Chip {
	// Approved かつ Rejected でないチップだけが有効なルールセット
}
```

`ebigent edit`（当面は `cmd/behavior-editor`）が承認の場になる。

```bash
go run ./cmd/behavior-editor -library chips.json
```

置いてあるのは、承認と却下（理由付き）、**証拠ペイン**——エピソードと tick から復元した実際の
局面——、述語の使用状況、レベルタグの行列、再生成の差分、そしてベンチ表。

証拠ペインが実局面を出せるのは、[決定性](/integration/boundaries/)が土台にあるからだ。
「ep-007 の tick 3」と言われたら、その盤面を本当に復元できる。

<Aside type="caution" title="迂回路はない">
承認は必須のゲートで、迂回する API はない。現在はスクリプトが門番を代行しているが、
代行しているのはあくまで**門番の役**であって、門そのものは消えていない。
</Aside>

## 生成される Go

承認済みチップは、決定リストの `switch` になる。

```go
// Package gen is generated by ebigentserver/behavior from the approved
// chip library. It is source on purpose — read it, diff it, review it —
// but edits belong upstream in the chips or predicates.
package gen

func Decide(obs ttt.Observation) (ttt.Move, bool) {
	switch {
	case obs.Board[0] == ttt.Empty:
		// chip cell_0_empty → play_0 (coverage 200, counterexamples 0)
		return ttt.Move{Cell: 0}, true
	case obs.Board[4] == ttt.Empty:
		// chip cell_4_empty → play_4 (coverage 52, counterexamples 0)
		return ttt.Move{Cell: 4}, true
	}
	var zero ttt.Move
	return zero, false
}
```

各 `case` に、由来のチップと被覆数と反例数がコメントで付く。生成物を読んでいる人が、
そのルールがどれだけの証拠に支えられているかをその場で見られる。

そして生成された agent は、`Agent` インターフェースを実装した**ただのボット**になる。
手書きのボットと区別が付かないし、session からも区別されない。

<Aside type="tip" title="古びた述語はビルドで死ぬ">
述語を変えると `GoExpr` が変わり、それを使っている生成コードはコンパイルできなくなる。
「知らないうちに意味が変わっていた」という事故が、型検査で潰れる。
</Aside>

## 記録済み局面からテストが出る

生成されるのはコードだけではない。記録された局面をフィクスチャにしたテストも出る。

失敗したときは、**エピソードと tick で場所を名指しする**。「この生成ルールは ep-012 の
tick 7 で期待と違う手を返した」と言われれば、その局面をエディタで開ける。

三目並べの例では、9チップの承認から生成フィクスチャテストが24件付いてきた。

## 再生成が壊さないこと

コーパスが増えれば、また分析を回したくなる。そのとき既に承認したものが黙って上書きされる
なら、承認ゲートは意味を失う。

`Merge` は、新しい提案を**差分として**畳み込む。

| 分類 | 意味 |
|---|---|
| `new` | 見たことのない候補。未承認のままライブラリに入る |
| `unchanged` | 既存チップと一致し、数値も同じ |
| `changed_metrics` | 一致するが証拠の数が動いた。**保存済みチップは触らず**、新しい数値だけが差分に乗る |
| `matches_rejected` | 却下したチップと一致。古い却下理由が再提示される |
| `conflicts_with_approved` | 承認済みチップが主張している条件に、別の行動を提案してきた |

**ライブラリを変更するのは `new` だけ**で、残りは全部レポートだ。

`changed_metrics` は地味だが重要な信号を運ぶ。承認したチップの裏付けが弱くなっていたら、
それは**ゲームが変わった**ということだ。バランス調整の影響が、ここに現れる。

`conflicts_with_approved` は自動解決されない。明示的な判断待ちとして人間の前に出る。

```bash
ebigent merge analysis-request.json validated-proposals.json --library chips.json --diff diff.json
```

```
merged into chips.json: 3 new, 9 unchanged, 1 metric changes, 2 rejected-again, 0 conflicts; 0 validation issues
```

同じコーパスをもう一度合成すると、全部が `unchanged` になり、ライブラリのファイルは
**バイト単位で不変**になる。冪等であることがテストで確かめられている。

## 検証

最後に、生成した agent を playtest に通して、元になった打ち手とバランス指標を比べる。
劣化したら前のバージョンを残す。

三目並べでは、first-empty ボットの200対局（686決定）を蒸留して9チップを承認し、生成された
agent が50試合を完走した。**同一シード・同一相手で、元のボットと勝敗も所要 tick も完全に
一致した**——方策として等価だということだ。

オセロでは、`best_move_is_k`（argmax の判断）そのものを述語として蒸留し、61チップ
（到達可能な最大）を得ている。生成されたコードは GreedyBot とビット一致する。

## 無人で回し続ける

```go
sum, err := matchloop.Run(1000, baseSeed,
	func(match int, seed uint64) (matchloop.Result, error) {
		// ペアリング方針（総当たり、ランダム、自己対戦、リーグ）は
		// この関数が match 番号を読んで決める
		return playOneMatch(match, seed)
	})
fmt.Println(sum.WinRate(ttt.SlotX))
```

対局ごとに `baseSeed` から**別々のシード**が導かれる。固定シードだと全試合が同じものの複製に
なり、コーパスとして無価値になるからだ。ループが持つのはシード配りと集計だけで、
誰と誰を当てるかは呼び出し側にある。

ここから出てくるコーパスが、次の分析の入力になる。

パイプラインが一周して戻ってきた。記録が増え、語彙が鋭くなり、チップが増え、生成された
agent が強くなる——ただし、増える一歩ごとに人間が一度は目を通している。
