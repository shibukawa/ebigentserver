生成した AI で問題になるのは、強さだけではありません。判断の理由を説明できず、一部の規則だけを
**修正できないこと**も問題です。

そこで、重みやツリーの中間表現ではなく、**Go のソースコード**を出力します。人が読み、diff を取り、
レビューできます。

## 承認ゲート

チップは、承認されるまでライブラリ内で無効なままです。

```go
func (l *Library) Approved() []Chip {
	// Approved かつ Rejected でないチップだけが有効なルールセット
}
```

`ebigent edit`（当面は `cmd/behavior-editor`）で、チップを承認または却下します。

```bash
go run ./cmd/behavior-editor -library chips.json
```

エディタには、承認と理由付きの却下、エピソードと tick から局面を復元する**証拠ペイン**、
述語の使用状況、レベルタグの行列、再生成の差分、ベンチマーク表があります。

[決定性](/integration/boundaries/)が保たれているため、証拠ペインは記録から実際の局面を復元できます。
たとえば ep-007 の tick 3 を指定すると、その時点の盤面を表示できます。

<Aside type="caution" title="迂回路はない">
承認は必須であり、省略する API はありません。現在はスクリプトが既定の承認を代行する場合も
ありますが、**承認済みでなければ生成に使えない**という条件は変わりません。
</Aside>

## 生成される Go

承認済みチップは、決定リストを表す `switch` に変換します。

```go
// Package gen is generated by ebigentserver/behavior from the approved
// chip library. It is source on purpose — read it, diff it, review it —
// but edits belong upstream in the chips or predicates.
package gen

func Decide(obs ttt.Sight) (ttt.Move, bool) {
	switch {
	case obs.Board[0] == ttt.Empty:
		// chip cell_0_empty → play_0 (coverage 200, counterexamples 0)
		return ttt.Move{Cell: 0}, true
	case obs.Board[4] == ttt.Empty:
		// chip cell_4_empty → play_4 (coverage 52, counterexamples 0)
		return ttt.Move{Cell: 4}, true
	}
	var zero ttt.Move
	return zero, false
}
```

各 `case` のコメントには、元のチップ、被覆数、反例数が入ります。生成コードを読むだけで、
その規則を支持する証拠の量を確認できます。

生成した agent は、`Agent` インターフェースを実装する通常のボットです。手書きのボットと同じように
席へ置け、session からも区別されません。

<Aside type="tip" title="古びた述語はビルドで死ぬ">
述語の `GoExpr` を変えると、古い生成コードがコンパイルできなくなる場合があります。これにより、
述語の意味だけが変わり、生成コードが古いまま残る事故を型検査で検出できます。
</Aside>

## 記録済み局面からテストが出る

コードだけでなく、記録された局面をフィクスチャにしたテストも生成します。

テストが失敗すると、**エピソードと tick で局面を示します**。たとえば ep-012 の tick 7 で
期待と異なる手を返した場合は、その局面をエディタで開けます。

三目並べでは、9個の承認済みチップから24件のフィクスチャテストが生成されます。

## 再生成が壊さないこと

コーパスが増えたら、分析をやり直します。その際、承認済みチップを新しい提案で自動的に上書きすると、
以前のレビュー結果が失われます。

`Merge` は、新しい提案を**差分として**ライブラリへ取り込みます。

| 分類 | 意味 |
|---|---|
| `new` | 見たことのない候補。未承認のままライブラリに入る |
| `unchanged` | 既存チップと一致し、数値も同じ |
| `changed_metrics` | 一致するが証拠の数が動いた。**保存済みチップは触らず**、新しい数値だけが差分に乗る |
| `matches_rejected` | 却下したチップと一致。古い却下理由が再提示される |
| `conflicts_with_approved` | 承認済みチップが主張している条件に、別の行動を提案してきた |

**ライブラリへ新しく追加するのは `new` だけ**です。ほかの分類はレポートとして人へ提示します。

`changed_metrics` は、既存チップを支持する証拠の変化を示します。承認済みチップの被覆が下がった場合、
**ゲームのバランス変更が方策へ影響した**可能性があります。

`conflicts_with_approved` は自動解決せず、人の判断が必要な衝突として表示します。

```bash
ebigent merge analysis-request.json validated-proposals.json --library chips.json --diff diff.json
```

```
merged into chips.json: 3 new, 9 unchanged, 1 metric changes, 2 rejected-again, 0 conflicts; 0 validation issues
```

同じコーパスをもう一度マージすると、すべて `unchanged` となり、ライブラリのファイルは
**バイト単位で変化しません**。この冪等性はテストで確認しています。

## 検証

最後に、生成した agent を playtest へ通し、元の打ち手とバランス指標を比較します。結果が悪化した
場合は、以前のバージョンを残します。

三目並べでは、first-empty ボットの200対局（686決定）から9チップを承認し、生成した agent で
50試合を実行しました。**同じシードと相手に対して、元のボットと勝敗も所要 tick も完全に一致**し、
この範囲で方策が等価であることを確認しました。

オセロでは、`best_move_is_k` という argmax の判断を述語として蒸留し、到達可能な最大数である
61チップを得ました。生成コードは GreedyBot とビット単位で一致します。

```go
sum, err := matchloop.Run(1000, baseSeed,
	func(match int, seed uint64) (matchloop.Result, error) {
		// ペアリング方針（総当たり、ランダム、自己対戦、リーグ）は
		// この関数が match 番号を読んで決める
		return playOneMatch(match, seed)
	})
fmt.Println(sum.WinRate(ttt.SlotX))
```

対局ごとに `baseSeed` から**異なるシード**を導きます。すべての試合で同じシードを使うと、
同じ対局を複製するだけでコーパスの多様性が増えないためです。ループはシードの割り当てと集計だけを
