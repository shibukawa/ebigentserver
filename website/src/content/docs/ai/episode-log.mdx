対局を分析するなら、世界状態をすべて保存したくなるかもしれません。しかし、世界全体は agent が
判断時に見た情報とは異なるため、学習用データには適しません。

実行時の agent が読めるのは視界だけです。世界状態を根拠に規則を作ると、実行時には評価できない
条件ができます。そのため、**実際に agent へ配った視界そのもの**を記録します。この地点で記録すれば、
追加の投影処理が不要で、情報のスコープも実行時と一致します。

## 4つのストリーム

<FileTree>
- episodes/
  - ep-001/
    - decisions.jsonl  分析の主テーブル
    - events.jsonl     ライフサイクル遷移・拒否・チェックポイント
    - outcomes.jsonl   エピソードごとに1席1行
    - world.jsonl      任意。デバッグ用の ground truth
</FileTree>

各行に一つの JSON オブジェクトを UTF-8 で追記します。**行単位でクラッシュに耐えられる**ため、
途中で停止しても、書き込み済みの行までは読み取れます。

ストリームを分けることで、ファイルごとの列構成を一定に保ちます。複数のレコード型を一つの
ファイルへ混ぜるより、列指向のリーダーから扱いやすくなります。

すべてのストリームは、共通形式のヘッダから始まります。

```json
{"stream":"decisions","schema_version":1,"protocol_version":"ttt/1",
 "episode_id":"ep-001","mode":"replay_complete","seed":42,"evaluation_version":1}
```

評価関数を変更すると異なるコーパス間の比較が無効になるため、`evaluation_version` を記録します。

## decisions の1行

```go
type Decision struct {
	Tick          uint64
	Slot          uint16
	AgentKind     string          // "human" / "bot" / "replay" — 行を分離できる
	Sight   json.RawMessage // 配られた視界そのもの。世界状態ではない
	Action        json.RawMessage // 取った行動、または null
	Evaluation    Evaluation      // この判断点での評価シグナル
	LatencyMicros int64           // 判断にかかった実時間。測定メタデータ
}
```

`Evaluation` 内の `RewardDelta` を、判断ごとの信用ラベルとして使います。最終結果だけでは
一つのエピソードに一つのラベルしか付かず、良い判断と、結果的に運が良かった判断を区別できません。

`LatencyMicros` は反応速度の分析に使います。**シミュレーションの入力には使いません**。

<Aside type="note" title="判断していない tick も記録される">
その席が判断しない tick の視界も `Observed` として残します。この行では `action` が null です。
何が見えているときに何もしなかったのかも、分析に使える情報です。
</Aside>

## 2つの記録モード

| モード | 内容 |
|---|---|
| `replay_complete` | 配られた視界、受理された行動、ライフサイクル遷移、シード、定期チェックポイント。**必須レコードを省けない** |
| `analysis_sampled` | world ストリームとチェックポイントを落とし、長いセッションを間引ける。集計専用 |

サンプリングしたログを、再生可能なログとして扱うことはできません。`NewWriter` は
`analysis_sampled` が指定されると、world の writer が渡されても**使用しません**。replay reader も、
サンプリング済みのログを拒否します。

## 記録は失敗しても対局を止めない

```go
w := episode.NewWriter[State, Move, Sight](streams, episode.ReplayComplete, meta)
cfg.Recorder = w
// ...
if err := w.Err(); err != nil {
	log.Printf("記録が劣化した: %v", err)
}
```

最初の書き込みエラーを保持しますが、対局は続行します。記録はセッションの**出力であり、
進行に必要な依存先ではありません**。ディスク容量の不足によってゲームサーバを停止させないためです。

## 記録フック

`Recorder` は session が呼ぶフックの集合です。`episode.Writer` は、標準で提供する実装の一つです。

| フック | いつ |
|---|---|
| `EpisodeStarted` | エピソード開始 |
| `Observed` | 判断しない席に視界を配ったとき |
| `Decided` | 行動が受理されたとき。視界・評価・レイテンシと一緒に |
| `Rejected` | validator が行動を拒否したとき |
| `Lifecycle` | 状態遷移 |
| `WorldCommitted` | tick 確定後の世界（任意の ground truth ストリーム） |
| `Checkpointed` | チェックポイント |
| `Ended` | 全席の結果と一緒に閉じる |

`Rejected` も重要な分析対象です。**拒否が連続して発生する場合は、チートまたはクライアントの
バグである可能性があります**。単発でも、プレイヤーが操作に迷った箇所を見つける手掛かりになります。

## 記録してみる

```bash
go run ./samples/reversi/cmd/reversi -record=episodes/
```

```bash
go run ./samples/pong/cmd/pong -record=episodes/
```

## コーパスを集計する

```bash
ebigent analyze --corpus episodes/
```

実行すると、種別ごとの勝率、所要時間の分布、行動の頻度、拒否理由のランキングを表示します。
純粋な Go と標準ライブラリだけを使い、cgo に依存しません。wasm を含むすべてのターゲットで
ビルドできますが、**ゲームやセッションのプロセスにはリンクしません**。

詳しく分析する場合は、同じコーパスを読み込む DuckDB 用 SQL を生成し、CLI で実行します。

```bash
ebigent analyze --corpus episodes/ --sql corpus.sql
```

```bash
duckdb -init corpus.sql
```

分析ツール自体には DuckDB を組み込みません。gzip または zstd で圧縮した JSONL も、事前に展開せず
DuckDB から直接読めます。

<Aside type="tip" title="記録されないもの">
プレゼンスメッセージ（カーソル、絵文字、装飾）は記録しません。シミュレーションにも分析にも
使わない情報を混ぜると、再現できない値が状態へ入ってしまいます。
</Aside>
