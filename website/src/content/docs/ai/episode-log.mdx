分析のために対局を記録するとき、つい世界状態を全部保存したくなる。だが、それは学習用の
データとしてはむしろ**間違っている**。

ランタイムの agent が読めるのは観測だけだ。世界状態を根拠にルールを作れば、実行時に評価できない
条件が出来上がる。だから記録するのは、**実際に配られた観測そのもの**になっている。
これは一番安く捕まえられる地点でもあり、スコープが自動的に正しくなる地点でもある。

## 4つのストリーム

<FileTree>
- episodes/
  - ep-001/
    - decisions.jsonl  分析の主テーブル
    - events.jsonl     ライフサイクル遷移・拒否・チェックポイント
    - outcomes.jsonl   エピソードごとに1席1行
    - world.jsonl      任意。デバッグ用の ground truth
</FileTree>

1行1 JSON オブジェクト、UTF-8、追記のみ。**行の粒度でクラッシュ安全**なので、途中で落ちても
そこまでは読める。

ストリームを分けてあるのは、各ファイルの列構成を安定させるためだ。混ざったレコード型を1本に
流すより、列指向のリーダがはるかに扱いやすい。

全ストリームの先頭行は共通のヘッダになっている。

```json
{"stream":"decisions","schema_version":1,"protocol_version":"ttt/1",
 "episode_id":"ep-001","mode":"replay_complete","seed":42,"evaluation_version":1}
```

`evaluation_version` があるのは、評価関数を変えるとコーパスをまたいだ比較が無効になるからだ。

## decisions の1行

```go
type Decision struct {
	Tick          uint64
	Slot          uint16
	AgentKind     string          // "human" / "bot" / "replay" — 行を分離できる
	Observation   json.RawMessage // 配られた観測そのもの。世界状態ではない
	Action        json.RawMessage // 取った行動、または null
	Evaluation    Evaluation      // この判断点での評価シグナル
	LatencyMicros int64           // 判断にかかった実時間。測定メタデータ
}
```

`Evaluation` の中の `RewardDelta` が、判断ごとの信用ラベルになる。エピソードの最終結果だけを
ラベルにすると、1エピソードに1ラベルしか付かず、良い判断と運の良い判断を分けられない。

`LatencyMicros` は反応の速さの軸として使う。**シミュレーションの入力には決してならない**。

<Aside type="note" title="判断していない tick も記録される">
その席が判断しない tick の観測も `Observed` として残る（`action` が null の行）。何が見えていて
何もしなかったのか、は分析上の情報になる。
</Aside>

## 2つの記録モード

| モード | 内容 |
|---|---|
| `replay_complete` | 配られた観測、受理された行動、ライフサイクル遷移、シード、定期チェックポイント。**必須レコードを省けない** |
| `analysis_sampled` | world ストリームとチェックポイントを落とし、長いセッションを間引ける。集計専用 |

サンプルされたログが再生可能を騙ることはできない。`NewWriter` は `analysis_sampled` を渡された
時点で、呼び出し側が world の writer を渡していても**捨てる**。そして replay reader は
サンプルされたログを拒否する。

## 記録は失敗しても対局を止めない

```go
w := episode.NewWriter[State, Move, Observation](streams, episode.ReplayComplete, meta)
cfg.Recorder = w
// ...
if err := w.Err(); err != nil {
	log.Printf("記録が劣化した: %v", err)
}
```

書き込みエラーは最初の1件だけ保持され、対局は続く。記録は**出力であって依存ではない**。
ディスクが埋まったことでセッションが落ちるのは、ゲームサーバとしては本末転倒だ。

## 記録フック

`Recorder` は session が呼ぶフックの集合で、`episode.Writer` はその既製の実装にすぎない。

| フック | いつ |
|---|---|
| `EpisodeStarted` | エピソード開始 |
| `Observed` | 判断しない席に観測を配ったとき |
| `Decided` | 行動が受理されたとき。観測・評価・レイテンシと一緒に |
| `Rejected` | validator が行動を拒否したとき |
| `Lifecycle` | 状態遷移 |
| `WorldCommitted` | tick 確定後の世界（任意の ground truth ストリーム） |
| `Checkpointed` | チェックポイント |
| `Ended` | 全席の結果と一緒に閉じる |

`Rejected` を残す価値は見落とされがちだが、**拒否がかたまって出るのはチートかクライアントの
バグ**だ。分析側では「混乱したプレイ」を見つける手がかりになる。

## 記録してみる

```bash
go run ./samples/reversi/cmd/reversi -record=episodes/
```

```bash
go run ./samples/pong/cmd/pong -record=episodes/
```

## コーパスを集計する

```bash
ebigent analyze --corpus episodes/
```

種別ごとの勝率、所要時間の分布、行動の頻度、拒否のランキングが出る。純 Go・stdlib のみ・
cgo なしなので、wasm を含む全ターゲットでビルドでき、**ゲームやセッションのプロセスには
決してリンクされない**。

深く掘りたいときは、同じコーパスに対する DuckDB 用 SQL を吐かせて CLI で回す。

```bash
ebigent analyze --corpus episodes/ --sql corpus.sql
```

```bash
duckdb -init corpus.sql
```

DuckDB のバイナリを分析ツールに抱き込まないのは、同じ理由による。gzip や zstd で圧縮した
JSONL は、展開ステップなしにそのまま読める。

<Aside type="tip" title="記録されないもの">
プレゼンスメッセージ（カーソル、絵文字、装飾）は記録されない。シミュレーションにも分析にも
入らないので、混ぜると再現できないものが紛れ込む。
</Aside>
