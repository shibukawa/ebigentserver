視界には敵と自分の位置が入っています。しかし、方策の条件として使いたいのは、座標そのものではなく
`in_weapon_range` でしょう。その名前のフィールドは、視界にはありません。

この差を埋めるのが**派生述語**です。視界の生のフィールドから、規則に使える判断を計算し、名前を
付けた関数です。

## 派生述語

```go
type Feature struct {
	Name   string // 開発者が読む語彙の項目。"cell_4_empty"
	GoExpr string // 生成コードでの Go 式。"obs.Board[4] == ttt.Empty"
	Doc    string // 外部の分析役に渡す散文の説明
	Eval   func(obs json.RawMessage) (bool, error) // 記録済み視界の判定
}
```

この型では、**記録を評価する関数と、生成コードで使う Go 式を対にします**。採掘時には `Eval` で
JSON の視界を評価し、実行時には生成コードが `GoExpr` を本来の視界型へ適用します。同じ判断を
二つの経路で表すことで、採掘した条件を実行時のコードへ変換できます。

たとえば `in_weapon_range`、`outnumbered_locally`、`escape_route_exists`、
`objective_contested`、`ally_needs_support` などです。いずれも、座標ではなく**判断**に名前を付けます。

### 述語を先に作る理由

条件へ座標計算を直接書くと、規則をレビューするたびに同じ計算を読み直すことになります。一つの
述語を多くのノードで共有すれば、計算の妥当性を**一度レビューするだけで済みます**。

ただし、述語の意味を変えると、それを使うすべてのノードを再検証する必要があります。そこで、
`Parameters` のしきい値は、再生成せずに開発者が調整できる値として分けます。

<Aside type="caution" title="視界の外は書けない">
述語が読めるのは、記録された視界だけです。`Eval` には視界の JSON しか渡らないため、世界状態を
参照する述語は**実装できません**。これは運用ルールではなく、API の構造による制約です。
</Aside>

## 行動の語彙

```go
type ActionDef struct {
	Name   string // "play_4"
	GoExpr string // "ttt.Move{Cell: 4}"
	Doc    string
	Match  func(action json.RawMessage) (bool, error)
}
```

行動の定義は述語と対称です。`Match` は記録された行動が定義と一致するかを判定し、`GoExpr` は
生成コードでその行動を構築します。

語彙にない行動を含む決定点は、採掘対象から除外します。

## 決定点への切り出し

```go
records, err := behavior.Segment(vocab, "ep-001", decisionsFile, keep)
```

decisions ストリームを読み、語彙に含まれる行動を持つ行を特徴量へ変換します。行動が null の行と、
語彙外の行動を持つ行はスキップします。

変換結果は、次の `Record` です。

```go
type Record struct {
	Episode string
	Tick    uint64
	Slot    uint16
	Obs     json.RawMessage
	Action  string // マッチした ActionDef の名前
	Bits    []bool // Bits[i] は Features[i] を Obs で評価した結果
}
```

`Bits` は、その局面で成立していた可視の事実を表します。分析役にも、この値を渡します。

## チップ

承認した候補は**チップ**になります。チップは、一つの条件と行動をまとめた規則の最小単位です。

```go
type Chip struct {
	Condition       string     // 派生述語の名前だけで書かれた条件
	Action          string     // 行動、または小さなサブツリー
	Priority        int        // 兄弟間の既定の順序
	Coverage        int        // このルールが再現する視界済み決定の数
	Counterexamples int        // 条件は成立したが別の行動が取られた数
	Evidence        []Evidence // 蒸留時に保持した証拠（episode + tick）
	Rationale       string     // なぜこの条件がこの行動を選ぶのか
	Approved        bool
	Rejected        bool
	RejectReason    string     // 却下の理由。再提案されたときに再提示される
	Tags            []string   // level / style / tactic は全部同じ仕組み
}
```

チップは、単独で名前を付け、レビューし、ベンチマークできる大きさにします。
格闘ゲームなら、相手が引きこもっているときの `pressure_rush`、飛び道具が飛んでくるときの
`patient_approach` などが一つのチップになります。

### 反例は雑音ではない

被覆数が大きくても反例が多ければ、規則の条件が不十分です。反例を雑音として捨てるのではなく、
条件を改善する材料にします。反例となった決定を見て、どの述語があれば分離できるかを考えることで、
新しい判断語の候補が見つかります。

## ライブラリは1つ

チップはゲームごとに**一つの共有ライブラリ**へ保存し、agent ごとには複製しません。

```json
{
  "game": "tictactoe",
  "chips": [
    {"condition": "cell_4_empty", "action": "play_4",
     "coverage": 52, "counterexamples": 0, "approved": true,
     "tags": ["level:intermediate", "style:center-first"],
     "evidence": [{"episode": "ep-007", "tick": 3}]}
  ]
}
```

共有ライブラリなら、**一つのチップを修正するだけで、それを使うすべての loadout に反映できます**。
agent ごとの複製が別々に変化するドリフトを防げます。

## 個性は選択で作る

同じライブラリから、異なる個性を持つ loadout を組み立てます。

```go
loadout := behavior.Loadout{
	Name: "CenterFirst",
	Tactics: []behavior.Tactic{
		{
			Name:      "opening",
			Condition: "board_is_empty", // 語彙の述語で作戦を切り替える
			ChipKeys:  []string{"cell_4_empty→play_4"},
		},
		{
			Name:     "default", // 条件なしのフォールバックは最後にしか置けない
			ChipKeys: []string{"cell_0_empty→play_0" /* ... */},
		},
	},
}
```

作戦セレクタの条件にも視界の述語を使うため、切り替えは決定的です。再生時にも同じ順序をたどります。
**プレイヤーが味方 agent に出した指示**を視界に含めれば、その値を使って作戦を切り替えられます。

`Validate` は、すべてのキーが承認済みチップを指すことと、条件なしの作戦が最後にあることを
確認します。三目並べでは、同じライブラリから center-first という別の個性を作ります。
使うチップと順序だけが異なります。

タグの種類は固定していません。スキルレベルによるゲート、スタイル、作戦セレクタを、
**同じタグの仕組み**で表現できます。

## 語彙が足りないとき、多すぎるとき

述語の設計は、パイプラインの結果を大きく左右します。少なすぎても、多すぎても問題が起きます。

述語が足りない場合、失敗がエラーとして現れないことがあります。「セル k が空いている」だけの
語彙で三目並べを蒸留すると、`Propose` が報告する未説明の決定は0件です。しかし、承認済みチップが
説明できるのは59.2%だけです。条件に当てはまっても別の行動を選んだ記録が反例になり、そのチップを
承認できないためです。結果は、間違った手を指すのではなく、**4割の局面で行動を返さないボット**です。

述語が多すぎる場合は、行動を返す局面が増える一方で、誤った行動も増える可能性があります。同じゲームに
fork の述語を追加すると、行動を返さない局面は57から3へ減りましたが、**間違う局面は12から36へ
増えました**。語彙が増えるほど、採掘器はコーパス内に反例のない規則を多く見つけます。しかし、
**コーパス内に反例がないだけでは、ゲーム全体で正しいとは限りません**。

したがって、語彙は増やすほど良くなるわけではありません。一つの判断語を追加すると、採掘器が
表現できる規則も増えます。その規則がゲーム全体で正しいかどうかは、コーパス外の局面を使った
playtest で確認します。
