この framework では、四つの階層を定義します。外側から **Protocol**、**Match**、**Stage**、
**Message** の順に並び、外側の階層が内側の階層を含みます。

括弧内には、一般的なゲーム開発や Ebitengine で対応する呼び方を示します。

| 階層 | 一般の呼び方 | 単位 | 定めるもの |
|---|---|---|---|
| **Protocol** | Game | プロジェクトに1つ | 通信方式、プレイ人数、リアルタイム性、画面の共有 |
| **Match** | — | 集合してから終わるまで | ロスター、シード、リンク |
| **Stage** | Scene | ルールセット1つ | StageRuleSet、Schema、tick レート |
| **Message** | — | 線を流れる1フレーム | 入力、スナップショット、差分、イベント |

## Protocol — ゲームの規約

何人で遊ぶのか。どうやってつながるのか。1フレームの遅れが致命的なのか、
それとも1手に10秒かけるゲームなのか。全員が同じ画面を見るのか、席ごとに視界が違うのか。

これらは**ゲーム全体で共有する規約**です。プレイヤー、ボット、サーバは、対局が始まる前に
同じ条件へ合意している必要があります。この規約を Protocol と呼びます。

Protocol はプロジェクトに一つで、ビルド成果物を作る前に決めます。

Protocol では、次の項目を定めます。

- **席の数と参加形態** — 1人、2人、多数。`concept:participant-shape`
- **リアルタイム性** — ターン制／paced／twitch。`concept:realtime-intensity`
- **画面の共有** — 全員が同じ内容を見るか、席ごとに視界を持つか。`concept:view-arrangement`
- **必要なトランスポート能力** — 到達すべき経路の性質。`concept:transport-capability`
- **受け付ける入力デバイス** — 書いていないアダプタのデバイスは受けられない

<Aside type="note" title="人数はトランスポートを決めない">
Protocol は参加人数と、必要な接続経路の両方を定めます。ただし、人数だけでは経路を決められません。
利用できる経路は、ホストの種類によって決まります。
</Aside>

### ビルド時に決まる設定 — `ebigent.toml`

dev と prod で変わらず、ビルド時に確定する値は `ebigent.toml` に書きます。`ebigent build` が
コードを生成して成果物へ組み込むため、起動時にはこのファイルを読みません。

主な値は、`ebigent init` の質問に答えると設定されます。

| 設定 | 値 |
|---|---|
| Go モジュールパス | `example.com/mygame` |
| プレイスタイル | 1人／2人（リアルタイム必須）／多人数 |
| 最大人数 | 2〜8。多人数のときだけ聞かれる |
| 画面の共有 | 全員が同じ内容を読む／席ごとに視界を持つ |
| 同期モード | `server_authoritative` / `delay` / `rollback` / `hybrid` |

同期モードの選択肢は、参加人数によって絞られます。1ホップで通信できるのは2人対戦だけなので、
3人以上では `rollback` と `delay` を選べません。

### 席の構成もここで決まる

各席を誰が使うかは Match で決まりますが、**どのような席があるか**は Protocol で定義します。
人数だけでなく、チームや空席の扱いも宣言します。

| 設定 | 値 |
|---|---|
| 席の数 | 上の最大人数 |
| チーム分け | チームがあるか、何チームか、各チーム何席か |
| 各席の担い手 | 人だけ／bot だけ／どちらでもよい |
| 空席の扱い | 空席のまま始める／bot で埋めてから始める |

**空席の扱い**は、多人数の対局で必要になります。8席を宣言して6人だけが集まった場合に、
残り2席を空のまま始めるか、bot で埋めてから始めるかを決めます。この方針はゲームごとに異なりますが、
起動するたびに変える値ではありません。

チーム分けも Protocol で定義します。どの席同士が味方になるかは、参加者ではなくゲームのルールが
決めるためです。

質問への回答から自動的に導ける値もあります。

- **エントリポイントの構成** — 形が決まればクライアントとサーバのどちらが要るかも決まる
- **tick / send レートの初期値** — 2人までと3人以上で送信頻度が変わる
- **必要なトランスポート能力** — リアルタイム性から決まる

### 実行時に読む設定 — `config.[env].toml`

実行時設定は、同じ成果物を dev と prod で異なる条件の下に置くために使い、起動時に読み込みます。

| 設定 | 値 |
|---|---|
| トポロジ | `standalone` / `listen` / `dedicated` / `p2p` |
| dedicated サーバの URL | 接続先。ホスト側では待ち受けアドレス |
| 使用するトランスポート | 開いてよいリスナーの種類 |

<Aside type="note" title="トポロジはビルド時の値が開始値">
`ebigent init` はプレイスタイルからトポロジの初期値を生成しますが、選択を固定するものではありません。
実行時設定を編集すれば、コードを再生成せずにホストの種類を切り替えられます。
</Aside>

## Match — 1回の対戦

Match は、ロスターが確定してから対戦が終わるまで存続します。**誰がどの席に座ったか**と、
**リンクがどこへ接続されているか**を保持します。

Match と Protocol を分けるのは、起動時には参加者が確定していないためです。起動後に人が集まるため、
ロスターはプロセス単位ではなく、対戦単位で作ります。

一つの Match 内でシミュレーションを実行するのが `session` パッケージです。Match が席とリンクを
持つのに対し、session はルールを実行し、席の操作者が人か bot かを区別しません。

### Match が持つもの

| 語 | 意味 |
|---|---|
| **Seat** | 1つの参加位置。Protocol が宣言し、Match が埋める。**誰もいなくても存在する** |
| **Roster** | 席全部の、いまの埋まり方。空席が見えるのがロスターらしさ |
| **Agent** | 席の向こうで決定を下すもの。人もボットも同じ扱い |
| **Link** | 2つのインスタンスの間の接続。トランスポートはその実現手段であって Link ではない |
| **Host** | セッションを持つ側 |
| **Guest** | セッションを持たない側。世界は届くもので、作るものではない |

Host と Guest は、ゲーム側で固定的に宣言しません。トポロジと、実際にどのプロセスがホストを
引き受けたかによって決まります。

### 持つ設定

**Match 専用の設定ファイルはありません**。席の構成、チーム分け、空席の扱いは、Protocol が
ビルド時に定めます。Match は宣言済みの席を埋めますが、席を追加しません。

実行時に決まるのは、**それぞれの席を誰が使うか**です。席の状態は三つあります。

| 席の状態 | 意味 |
|---|---|
| Empty | 宣言済みだが誰も座っていない |
| Human | 人が座っている |
| Bot | エージェントが座っている |

着席すると、その席に操作者の ID が付きます。人が集まるまで確定しないため、設定値ではなく
実行中の状態として保持します。

### local か remote かは結果である

「このマシンにいる人」や「リンクの向こうにいる bot」という区別は、事前に宣言するのではなく、
実行中の配置として報告されます。

宣言では bot であることだけを指定します。bot が実際に動く場所は、トポロジとホストを担当する
プロセスによって決まります。

- **ホストになったプロセスの中** — 誰かのマシンがホストを持つ場合
- **サーバの中** — dedicated server がある場合

どちらで動いても、席から見れば同じ bot です。そのため、席の宣言には実行場所を含めません。

### AI のレベル別はソースコードで登録する

難易度と実装の対応は、関数やクロージャとしてソースコードへ登録します。設定ファイルだけでは
方策を表現できません。

Match は空席を埋めるときに、この登録から Agent を選びます。難易度の**段階数**は Protocol で
定められますが、**各段階の動作**はコードへ実装します。

## Matchmaking — Match の作り方

Matchmaking は独立した階層ではなく、**Match を成立させる手順**です。動作は三つあります。

| 語 | 誰が | 何を |
|---|---|---|
| **Host** | ホスト | **条件を宣言して Room を開く**。以後、人ごとの判断はしない |
| **Match** | 参加する側 | Room に到達して中を見る。席はまだ持たない |
| **Sit** | 参加する側 | 席を取る |

**Room** は、条件付きで公開され、参加者を募集中の Match です。ブラウズリストには Room が並びます。
新しい階層ではなく、Match の状態の一つです。

### ホストは1人ずつ判断しない

ホストは、到着した参加者を一人ずつ審査しません。ホストが行うのは、**条件を提示して部屋を
開くこと**です。参加するかどうかは、あとから来た側が決めます。

ホスト側で行うのは、空席の有無と宣言済み条件を満たすかの**照合**です。参加者ごとの裁量判断ではなく、
提示済みの条件を機械的に適用します。

条件は、軸と値に分けます。ランク、モード、マップなどの**軸**は Protocol で定義します。接続の両端が
同じ軸を知らなければ、拒否理由を説明できないためです。各軸の**値**は Room ごとに指定します。
同じビルドから ranked と casual のどちらの部屋も開けます。

すべての軸を満たす場合だけ参加でき、照合方法は AND に固定します。軸には二つの種類があります。

| 種類 | 部屋が言うこと | 参加する側が持つもの | 一致条件 |
|---|---|---|---|
| **exact** | 値（`mode = "ranked"`） | 求める値、または無指定 | 等しい。どちらかが無指定なら制約なし |
| **band** | 範囲（`rank = 1200..1600`） | **自分の値**（レート1400） | 範囲に入る |

band の照合が非対称なのは、ランクが参加者の**希望条件ではなく属性**だからです。そのため、
参加者側でランクを「指定なし」にはできません。

参加を拒否する場合は、**どの軸が一致しなかったか**を返します。拒否理由がなければ、満席なのか、
レート帯から外れたのかを区別できません。

### Match と Sit は別の行為

Room に接続しても、必ず着席するとは限りません。**入室し、メンバーを確認してから退出する**ことも
できます。

| 状態 | 持っているもの | 抜けたときのコスト |
|---|---|---|
| Discovered | ブラウズリストの行だけ | なし |
| Matched | Room への接続。ロスターが見える | なし |
| Seated | 席 | 席が1つ空く |

Match と Sit を分けることで、ロスターを確認して退出した人が一時的に席を取ることを防げます。

着席には、ローカルかリモートかを問わず **Sit という同じ操作**を使います。違うのは操作者の
実行場所だけで、その場所は席の状態として報告されます。

## Stage — ルールセット

一つの Match に、複数種類のゲームを含めることもできます。たとえば、本編のあとにルールと
tick レートが異なるボーナスステージがある場合、それぞれを一つの Stage として扱います。

Ebitengine では、同じ単位を **Scene** と呼ぶことがあります。

Stage ごとに、次の要素を持ちます。

- **StageRuleSet** — そのルールセットの状態遷移
- **Schema** — その Stage が交換するメッセージの形（次節）
- **tick レート** — ターン制の本編と twitch なボーナスで違ってよい

Stage の処理には、次の三つの型を使います。

| 語 | 型引数 | 意味 |
|---|---|---|
| **World** | `W` | その Stage の世界そのもの。誰にも見せる前の状態 |
| **Action** | `A` | 1つの席が出す1つの決定 |
| **Sight** | `S` | 1つの席が見てよいものだけを取り出したもの |

ジェネリクスの型引数には、この三つの頭文字を使い、`StageRuleSet[W, A, S]` の順に並べます。

Agent の役割は、**Sight を受け取り、Action を返すこと**です。人、ボット、リプレイが同じ
インターフェースを使うため、session からは区別できません。

<Aside type="note" title="なぜ Sight なのか">
「見えるもの」を表す候補には Perspective などもあります。View は、すでに**画面の共有方法**を
表す view arrangement で使っているため、席に配る情報には Sight という名前を使います。
</Aside>

Match は席とリンクを保持したまま、Stage だけを入れ替えられます。これにより、
**同じ相手と、異なるルールで続けて遊べます**。

### ソースコードで宣言するもの

**StageRuleSet** と **Schema** は、設定ファイルではなくソースコードで宣言します。状態遷移と
送信するデータ構造は、型と関数として実装する必要があるためです。

宣言は一行だけです。ゲームがルールを型検査するために書く行を、そのまま Schema の入力として
使います。

```go
var _ session.TickStageRuleSet[Board, Move, Sight] = RuleSet{}
```

`ebigent generate` は、この一行を読みます。同期する **World にはマップ形状の全体と差分**を、
一回ごとに送る **Action には配列形状の全体**を生成します。型引数の位置から役割を判断するため、
別の場所で型を指定する必要はありません。エンコーダ、デコーダ、差分計算も自動生成します。

<Aside type="caution" title="Sight はまだ生成されない">
Sight も本来は生成対象です。Agent が別プロセスにいれば送信する必要があり、記録にも決定ごとに
残るためです。ただし、現在のコーデック生成器には扱えない型があるため、Sight の生成はまだ
要求していません。生成できない型は対象から外し、型名とメンバー名を報告します。
</Aside>

Stage が Match と別の階層なのは、Stage ごとにデータ構造とコーデックを切り替えるためです。
Stage 単位で Schema を宣言するので、本編とボーナスステージで異なる型を使えます。

### 実行時に読む設定 — `config.[env].toml`

tick レートをはじめとする、タイミングと帯域の設定は起動時に読みます。

| 設定 | 値 |
|---|---|
| tick レート | シミュレーションの毎秒ステップ数 |
| send レート | 毎秒の状態送信回数。tick レート以下 |
| スナップショット間隔 | 何回に1回、差分ではなく全体を送るか |
| 履歴の深さ | 差分の基準として保持する世界のバージョン数 |

<Aside type="caution" title="対戦する全員が同じ値を持つこと">
これらは一つのプロセスだけでなく、対戦全体で共有する設定です。クライアントとサーバが同じ
profile を宣言しなければ、状態を復元できません。デプロイ単位で値をそろえ、マシンごとには
変更しません。
</Aside>

## Message — 線を流れる1フレーム

Message は、実際に接続上を流れる一つのフレームです。入力、snapshot、状態差分、イベントなどが
あります。

Message の形は、その Message を送る Stage の Schema が定めます。

<Aside type="note" title="「ワイヤ」は用語ではない">
「ワイヤ」は、バイト列が流れる場所を指す普通名詞としては使えますが、framework の定義語では
ありません。接続上を流れるものを Message、その形を Schema と呼びます。以前は CBOR profile に
wire / world という名前がありましたが、現在は **配列形状 / マップ形状**と呼びます。
</Aside>

## Schema — Stage が定めるメッセージの形

Schema は階層ではなく、Stage が持つ定義です。一つの Stage に一つの Schema があり、
その Stage で使うすべての Message の形を決めます。

<Aside type="tip" title="Protocol と Schema">
**Protocol** は、参加人数、接続方法、ゲームの性質など、ゲーム全体の規約です。
**Schema** は、一つの Stage が交換する Message の形です。Stage が入れ替わると Schema も
入れ替わりますが、Protocol は変わりません。
</Aside>

## 設定はどこに書かれるか

階層とは別に、設定をどこへ書くかも決める必要があります。書き場所は三つです。

<Steps>

1. **ビルド時オプション** — `ebigent.toml` に書き、`ebigent build` が Go を生成します。
   成果物は値を定数として持ち、起動時には読み込みません。

2. **実行時オプション** — 設定ファイルに書き、起動時に configbind が読みます。
   同じ成果物を異なる条件で動かすために使います。

3. **ソースコードに直接** — 型、関数、クロージャなど、設定ファイルでは表せないものを書きます。

</Steps>

次の三つの質問を上から順に確認すると、書き場所が決まります。

| 問い | Yes なら | なぜ |
|---|---|---|
| 関数・型・クロージャで表すものか | ソースコード | StageRuleSet も Schema も画面もコード。設定ファイルに書きようがない |
| 変えたらどのみち再ビルドか | ビルド時 | リンク時に確定済みの値を起動時に引くのは、開いているフリ |
| 同じ成果物の2回の起動で正当に違いうるか | 実行時 | 待ち受けアドレス、トポロジ、ロスター |

Protocol は、この判定では**ビルド時設定**になります。ゲーム全体の規約は、起動ごとには変わらないためです。

<Aside type="tip" title="層を決めても、書く量は決まらない">
分類によって**書き場所**は決まりますが、すべての値を明示する必要はありません。既定値がある項目は、
異なる値だけを指定します。ただし、tick レートや帯域などの tuning 値には既定値がありません。
ジャンルによって適切な値が大きく異なるため、ゲーム側で必ず宣言します。
</Aside>

## 記録と方策の語

ここまでは、実行中のゲームを表す用語でした。ここからは、**対局後に残る記録と方策**を表す用語です。
チュートリアルの step 3 以降と `ai/` の各ページで使います。

用語は一つの流れに沿って並びます。**対局を記録し、記録から規則を見つけ、承認した規則を
Go のコードへ変換します**。

### 記録するとき

**決定（decision）** は、一つの席が一回行った選択です。ただし、行動だけでは決定として扱いません。
**そのとき見えていた視界**と行動を対にします。盤面の履歴から分かるのは、起きた出来事だけです。
視界と行動の対なら、操作者がどの情報から選んだかも分かり、あとから方策を復元できます。

**エピソード（episode）** は一試合分の記録です。一つのディレクトリに複数の JSONL が入ります。
決定の列、状態遷移とバリデータが撥ねた入力、席ごとの決着、そして（再生用に録るときだけ）
再生用に記録する場合だけ、世界そのものも含みます。

**コーパス（corpus）** は、複数のエピソードを集めたものです。コーパスのディレクトリ内に、
エピソードごとのディレクトリを並べます。分析と蒸留はコーパス単位で実行します。

<Aside type="note" title="量は質を保証しない">
コーパスの価値は、局数だけでなく**含まれる局面や判断の違い**で決まります。決定的なボット2体を
1000局対戦させても、すべて同じなら一局を1000回複製しただけです。そのため、対戦相手を変えること
（`concept:continuous-match-loop`）も、局数を増やすことと同じくらい重要です。
</Aside>

**整えたコーパス（curated corpus）** は、蒸留の前に前処理を掛けたコーパスの複製で、
`ebigent curate` が作ります。対象の行を `agent_kind` などで絞り、同一局面の重複に上限を掛け、
エピソード単位で学習用と**検証用（holdout）**——採掘には見せず、答え合わせにだけ使う
取り分け——に分割します。同じ局面に違う行動が記録されている混在は、解決せずに報告へ
一覧します。誰の判断を規則に残すかは人が決めることだからです（`requirement:corpus-curation`）。

### 規則を見つけるとき

**述語（predicate）** は、視界に対する真偽の判断へ**名前を付けたもの**です。「セル4が空いている」
という生のフィールドの確認も述語ですが、「この席は k に置けば勝つ」のような**判断**を表す述語が
特に重要です。盤面に直接ない区別を計算するものを、`data:derived-predicate`（派生述語）と呼びます。

**語彙（vocabulary）** は、規則に使える述語と行動の集合です。語彙にない名前は、規則へ
書けません。**採掘器が表現できる規則は語彙によって決まる**ため、語彙の設計が蒸留結果を大きく
左右します。

**採掘（mining）** は、コーパスから「この条件が成り立つとき、この行動を取っていた」という
規則を見つける処理です。framework の既定実装は、決定リストを貪欲に被覆する方法で、LLM を
必要としません。

**被覆（coverage）** は規則を支持する記録の数です。**反例（counterexample）** は、条件が
成り立っていたのに別の行動を取った記録の数です。この二つを、規則の証拠として使います。

<Aside type="caution" title="反例ゼロは「正しい」ではない">
反例ゼロが示すのは、**このコーパス内では**一度も否定されなかったことだけです。規則を否定する
局面がゲーム内に存在しても、コーパスになければ反例にはなりません。そのため、人が規則を承認し、
最後に playtest でコーパス外の局面も検証します。
</Aside>

### 方策にするとき

**チップ（chip）** は、人が承認した一つの規則です。条件、行動、被覆、反例、証拠を持ち、
ゲームごとの共有ライブラリへ保存します。

**決定リスト（decision list）** は、チップを上から順に評価し、最初に条件が成り立った規則を
選ぶ構造です。`if / else if` の列に相当し、生成する Go では一つの `switch` になります。
上にある規則を優先するため、**順序に意味があります**。

**loadout** は、共有ライブラリから**どのチップを選ぶか**で作る個性です。ライブラリは共有したまま、
チップの選択と順序を変えて、別の性格を組み立てます。

**蒸留（distillation）** は、この流れ全体を指します。目的は、**遅く実行コストの高い教師を、
速く読める生徒へ変換すること**です。`concept:behavior-distillation` では、教師は開発時だけ動けば
よく、生徒は tick の予算内で動く必要があります。記録を残す人、探索、手書きボットなどを
**教師**、生成した方策を**生徒**と呼びます。
