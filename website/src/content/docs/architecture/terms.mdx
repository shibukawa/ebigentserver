このフレームワークは4つの階層を定める。外側から順に **Protocol**、**Match**、**Stage**、
**Message**。各階層は内側をすべて含む。

括弧内は、一般的なゲーム開発や Ebitengine 側で同じものを指すときに使われる呼び方である。

| 階層 | 一般の呼び方 | 単位 | 定めるもの |
|---|---|---|---|
| **Protocol** | Game | プロジェクトに1つ | 通信方式、プレイ人数、リアルタイム性、画面の共有 |
| **Match** | — | 集合してから終わるまで | ロスター、シード、リンク |
| **Stage** | Scene | ルールセット1つ | StageRuleSet、Schema、tick レート |
| **Message** | — | ワイヤ上の1フレーム | 入力、スナップショット、差分、イベント |

## Protocol — ゲームの規約

何人で遊ぶのか。どうやってつながるのか。1フレームの遅れが致命的なのか、
それとも1手に10秒かけるゲームなのか。全員が同じ画面を見るのか、席ごとに視界が違うのか。

これらは**ゲームそのものの規約**である。プレイヤーもボットもサーバも、
何かが始まる前にこの条件に同意している必要がある。だから Protocol と呼ぶ。

プロジェクトに1つで、成果物ができる前に決まる。

Protocol が定めるもの：

- **席の数と参加形態** — 1人、2人、多数。`concept:participant-shape`
- **リアルタイム性** — ターン制／paced／twitch。`concept:realtime-intensity`
- **画面の共有** — 全員が同じ内容を見るか、席ごとに視界を持つか。`concept:view-arrangement`
- **必要なトランスポート能力** — 到達すべき経路の性質。`concept:transport-capability`
- **受け付ける入力デバイス** — 書いていないアダプタのデバイスは受けられない

<Aside type="note" title="人数はトランスポートを決めない">
Protocol は「何人か」と「どの経路が届く必要があるか」の両方を定めるが、
前者が後者を決めるわけではない。決めているのはホストの側である。
</Aside>

### ビルド時に決まる設定 — `ebigent.toml`

dev だろうが prod だろうが変わらず、ビルド時に100%決まる。`ebigent.toml` に書き、
`ebigent build` がそこからコードを生成して成果物に組み込む。起動時には何も読まない。

中心になるのは `ebigent init` が聞く質問である。

| 設定 | 値 |
|---|---|
| Go モジュールパス | `example.com/mygame` |
| プレイスタイル | 1人／2人（リアルタイム必須）／多人数 |
| 最大人数 | 2〜8。多人数のときだけ聞かれる |
| 画面の共有 | 全員が同じ内容を読む／席ごとに視界を持つ |
| 同期モード | `server_authoritative` / `delay` / `rollback` / `hybrid` |

同期モードの選択肢は人数で絞られる。1ホップが成立するのは2人のときだけなので、
3人以上に `rollback` と `delay` は出てこない。

### 席の構成もここで決まる

席は Match で埋まるが、**どういう席があるか**を決めるのは Protocol である。
人数だけでは足りないので、席についてはもう少し細かく宣言する。

| 設定 | 値 |
|---|---|
| 席の数 | 上の最大人数 |
| チーム分け | チームがあるか、何チームか、各チーム何席か |
| 各席の担い手 | 人だけ／bot だけ／どちらでもよい |
| 空席の扱い | 空席のまま始める／bot で埋めてから始める |

**空席の扱い**が実際に効くのは多人数のときだ。8席を宣言して6人しか集まらなかったときに、
残り2席を空のまま始めるのか、bot で埋めて8席揃えてから始めるのか。
ゲームによって答えが違い、そして起動ごとに変わる種類の答えではない。

チーム分けも同じ理由でここにある。どの席とどの席が味方かはゲームのルールの一部であって、
集まった人が決めることではない。

聞かずに、上の答えから導出されるものもある。

- **エントリポイントの構成** — 形が決まればクライアントとサーバのどちらが要るかも決まる
- **tick / send レートの初期値** — 2人までと3人以上で送信頻度が変わる
- **必要なトランスポート能力** — リアルタイム性から決まる

### 実行時に読む設定 — `config.[env].toml`

同じ成果物を dev と prod で違う条件に置くためのもの。起動時に読む。

| 設定 | 値 |
|---|---|
| トポロジ | `standalone` / `listen` / `dedicated` / `p2p` |
| dedicated サーバの URL | 接続先。ホスト側では待ち受けアドレス |
| 使用するトランスポート | 開いてよいリスナーの種類 |

<Aside type="note" title="トポロジはビルド時の値が開始値">
`ebigent init` はプレイスタイルからトポロジの初期値を書き出すが、これは制約ではない。
どの席数でもどちらのホストでも動くので、切り替えは設定の編集であって再生成ではない。
</Aside>

## Match — 1回の対戦

ロスターが確定してから、その対戦が終わるまで。**誰がどの席に座ったか**と、
**リンクがどこに繋がっているか**を持つ。

Match が Protocol と別の階層になっているのは、プレイヤーが起動時には分からないからだ。
現実のゲームは起動してから人が集まるので、席の集合はプロセスの寿命ではなく対戦の寿命を持つ。

1つの Match の中でシミュレーションを回すのが `session` パッケージで、
Match が席とリンクを持つのに対し、こちらはルールだけを持ち、
席の向こうが人か bot かすら知らない。

### 持つ設定

**Match 自身に設定ファイルは無い。** 席の構成もチーム分けも空席の扱いも、
すべて Protocol がビルド時に決めている。Match はその席を埋めるだけで、席を増やすことはない。

動的に決まるのは、**それぞれの席が誰で埋まったか**である。区別は3つしかない。

| 席の状態 | 意味 |
|---|---|
| Empty | 宣言済みだが誰も座っていない |
| Human | 人が座っている |
| Bot | エージェントが座っている |

席には座った相手の ID が付く。人が集まるまで確定しないので、これは設定ではなく実行中の状態である。

### local か remote かは結果である

「このマシンにいる人」「リンクの向こうの bot」といった区別は、**宣言するものではなく報告されるもの**だ。

宣言の側では bot と言えば足りる。その bot が実際にどこで動くかは、トポロジと、
どのプロセスがホストを引き受けたかで決まる。

- **ホストになったプロセスの中** — 誰かのマシンがホストを持つ場合
- **サーバの中** — dedicated server がある場合

どちらで動いても、席から見れば同じ bot である。だから席の宣言はその区別を持たない。

### AI のレベル別はソースコードで登録する

どの難易度がどの実装かは、関数やクロージャの対応づけである。設定ファイルには書けない。

Match は空席を埋めるときにこの登録から引く。**何段階あるか**は Protocol が決めてよいが、
**各段階が何をするか**はコードにしか書けない。

## Stage — ルールセット

Match の中は、1種類のゲームとは限らない。本編のあとにボーナスステージがあり、
ルールも tick レートも違う——それぞれが1つの Stage である。

Ebitengine 側では **Scene** と呼ばれることが多い。同じものを指している。

Stage ごとに持つもの：

- **StageRuleSet** — そのルールセットの状態遷移
- **Schema** — その Stage が交換するメッセージの形（次節）
- **tick レート** — ターン制の本編と twitch なボーナスで違ってよい

Match が席とリンクを持ち続ける一方で、Stage は入れ替わる。
**同じ相手と、違うルールで、続けて遊ぶ**というのがこの分割の目的である。

### ソースコードで宣言するもの

**StageRuleSet** と **Schema** の2つは、設定ファイルではなくソースコードで宣言する。
状態遷移も、ワイヤに乗るデータ構造も、型でしか書けないからだ。

`NewStage` にこの2つを型引数で与える。宣言を受けて、`ebigent build`（`ebigent generate`）の
コードジェネレータが **CBOR のパーサとジェネレータを自動生成する**。
エンコーダもデコーダも差分計算も、手で書くものではない。

Stage が Match と別の階層である理由はここにある。Stage が入れ替わればデータ構造も入れ替わり、
生成されるコーデックも別物になる。本編とボーナスステージが違う型を扱えるのは、
この宣言が Stage 単位だからである。

### 実行時に読む設定 — `config.[env].toml`

tick レートをはじめとするタイミングと帯域の値は、起動時に読む。

| 設定 | 値 |
|---|---|
| tick レート | シミュレーションの毎秒ステップ数 |
| send レート | 毎秒の状態送信回数。tick レート以下 |
| スナップショット間隔 | 何回に1回、差分ではなく全体を送るか |
| 履歴の深さ | 差分の基準として保持する世界のバージョン数 |

<Aside type="caution" title="対戦する全員が同じ値を持つこと">
これらは1プロセスの都合ではなく、その対戦全体の取り決めである。
クライアントはサーバが動かしているのと同じプロファイルを宣言している必要があり、
食い違えば状態の復元ができない。デプロイ単位で揃える設定であって、
マシンごとに変えてよい設定ではない。
</Aside>

## Message — ワイヤ上の1フレーム

実際に線を流れる1つのフレーム。入力、スナップショット、状態差分、イベント。

どういう形をしているかは、そのメッセージを送る Stage の Schema が定める。

## Schema — Stage が定めるメッセージの形

Schema は階層ではなく、Stage が持つものである。1つの Stage に1つの Schema があり、
その Stage の Message すべての形を決める。

<Aside type="tip" title="Protocol と Schema">
**Protocol** はゲームの規約——何人で、どうつながり、どういう性質のゲームか。
**Schema** は1つの Stage が交換するメッセージの形。
階層が違うので、Stage が入れ替われば Schema も入れ替わるが、Protocol は変わらない。
</Aside>

## 設定はどこに書かれるか

階層は「何が何を含むか」の話だった。それとは別に、「どこに書くか」という軸がある。3つある。

<Steps>

1. **ビルド時オプション** — `ebigent.toml` に書き、`ebigent build` が Go を生成する。
   成果物は定数として持ち、起動時に何も読まない。

2. **実行時オプション** — 設定ファイルに書き、起動時に configbind が読む。
   同じ成果物を違う条件で動かすためのもの。

3. **ソースコードに直接** — 他に置き場所がないもの。

</Steps>

どれになるかは、上から順に3つ聞けば決まる。

| 問い | Yes なら | なぜ |
|---|---|---|
| 関数・型・クロージャで表すものか | ソースコード | StageRuleSet も Schema も画面もコード。設定ファイルに書きようがない |
| 変えたらどのみち再ビルドか | ビルド時 | リンク時に確定済みの値を起動時に引くのは、開いているフリ |
| 同じ成果物の2回の起動で正当に違いうるか | 実行時 | 待ち受けアドレス、トポロジ、ロスター |

Protocol はこの判定で**ビルド時**に落ちる。ゲームの規約が起動ごとに変わることはないからだ。

<Aside type="tip" title="層を決めても、書く量は決まらない">
どの層かは**どこに書くか**の答えであって、**書かねばならないか**の答えではない。
設定はデフォルトを持てるので、書くのはデフォルトと違うところだけでいい。
唯一の例外が tick レートや帯域といった tuning の値で、ジャンルごとに正解が違いすぎるため、
フレームワークは意図的にデフォルトを持たない。
</Aside>
