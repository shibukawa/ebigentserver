「4人で遊びたいので、4人に対応したトランスポートを選びたい」——この考え方から入ると、
たいてい選べない。人数はトランスポートを決めないからだ。

決めているのは**ホスト**の方だ。専用サーバなら名前と証明書を持っているので、ブラウザは
WebTransport で届く（届かなければ WebSocket に落ちる）。プレイしているプロセスがホストなら、
名前も証明書もなく、たいてい NAT の内側にいる。だから WebRTC か、リンクローカルアドレスか、
さもなくば届かない。人数はこの事情を何一つ変えない。

## 3つの軸

<Steps>

1. **席の数** — 1人 / 2人 / 多数。決まるのは slot の集合、着席の容量、そして誰かが抜けたときに
   セッションを生かし続けるかどうか。

2. **ホスト** — プロセス内にいない（standalone）／プレイしているプロセス（listen）／
   プレイしない専用プロセス（dedicated）。**どのリンクが届くかを決めるのはここ**。

3. **リンクとシグナリング** — pipe / WebRTC / WebTransport / WebSocket / QUIC-UDP と、
   相手の接続情報をどうやって知るか。

</Steps>

## それでも人数が効く場所がある

人数がトランスポートを決めない、と書いた。ただし**ネットコードの選択肢**には効く。

ピア同士のリンクは star 型なので、あるピアが別のピアに届くにはホストを経由する。つまり2ホップ。
専用サーバも2ホップ。ならば1ホップの直結が成立するのは、ホストが対戦相手その人である
**ちょうど2人のとき**だけということになる。

これは机上の話に聞こえるかもしれないが、結論はかなり乱暴に効く。rollback と delay は
短くて対称な経路を前提にした技法で、プレイヤーのマシンを経由する2ホップはそのどちらでもない。
だから3人以上は、ピアを選ぼうがサーバを選ぼうが、結局サーバ権威に落ち着く。

2人と3人以上を別のスタイルとして扱っているのは、2席と6席で配線が違うからではない。
**2人だけが1ホップのネットコードに手が届く**からだ。

## データ経路か、制御経路か

リンクが張れたあとに残る最も鋭い問いは、サーバが**トラフィックを運ぶ**のか、それとも
**仲介するだけ**なのか、である。

| | データ経路にサーバがいる | 制御経路だけにいる |
|---|---|---|
| ホップ数 | プレイヤー間の全交換が2ホップ | ピア同士は直結（2人なら1ホップ） |
| 権威 | サーバが持つ。結果は信用できる | プレイヤーのマシンが持つ。結果は偽造可能 |
| 運用 | サーバを動かし続ける必要がある | 立てるものがない |
| 帰結 | ランク戦の成績として扱える | カジュアル戦や身内戦の範囲 |

制御経路だけにしてホップを消す選択には、もう一つ見えにくい代償がある。行動だけを交換する
ピアは、そこから**同じ世界を再現しなければならない**。つまり入力同期であり、
シミュレーションのビット単位の再現性が要求される。ホップを1つ削るために、これから書く
すべてのゲームルールに決定性の制約がかかる。

<Aside type="caution" title="無料ではない">
「サーバを立てなくていい」は運用コストの話であって、実装コストの話ではない。P2P のデータ経路は
`rule:deterministic-simulation-required-for-rollback` を丸ごと引き受ける選択になる。
</Aside>

## トランスポートは2つ要る、あるいは1つでいい

WebTransport は専用ホストの行を全部カバーし、WebRTC はプレイ中ホストの行を全部カバーする。
そして互いに相手の行には届かない。

つまり、必ずサーバを運用すると決まっているプロジェクトは WebTransport（+ WebSocket
フォールバック）だけでよい。バックエンドなしの経路を持ちたいプロジェクトは WebRTC が要る。
ブラウザが別のブラウザからの接続を受け付けられる API は、ほかに存在しないからだ。

## ウィザードが聞く3つのこと

`ebigent init` の質問は、ここまでの話をそのまま3問に落としたものになっている。

<Steps>

1. **プレイスタイル** — 1人 / 2人 / マルチ

2. **最大人数** — マルチのときだけ

3. **1台で複数人が遊べるようにするか** — 1人以外

</Steps>

生成されるコードパターンは5通り。3問目が「カメラを共有するか」ではないのは、画面分割が
「カメラは各自 + 1台を共有」という二択に収まらない形をしているからで、1台を共有するかを
聞いてしまえば、その中のカメラ配置は描画の詳細に落ちる。

ホストがプレイするか専用かは、コードの差ではない。`cmd/server/` の1ディレクトリを `listen`
ビルドタグで切り替えるだけで、ピアか dedicated かに至っては実行時設定の値でしかない。
**マルチでも listen は許される**——ブラウザが WebRTC で N 人をホストする構成には、
バックエンドが要らない。
