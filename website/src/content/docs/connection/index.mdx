「4人で遊ぶので、4人用のトランスポートを選ぶ」と考えても、候補は絞れません。
トランスポートを決めるのは、参加人数ではないためです。

先に決めるべきなのは**ホスト**です。専用サーバには名前と証明書があるため、ブラウザから
WebTransport で接続できます。WebTransport が使えない場合は WebSocket に切り替えます。
一方、プレイ中のプロセスがホストになる場合は、通常は名前も証明書もなく、NAT の内側にあります。
そのため、WebRTC かリンクローカルアドレスを使わなければ接続できません。参加人数が変わっても、
この条件は変わりません。

ここで扱うのは、対局へ到達するまでのデータ経路です。アカウント管理や常設ロビーなど、
control plane の運用は扱いません。

## 3つの軸

<Steps>

1. **席の数** — 1人 / 2人 / 多数から選びます。slot の集合、着席できる人数、誰かが抜けたあとも
   セッションを続けるかどうかが決まります。

2. **ホスト** — プロセス内にホストを置かない standalone、プレイ中のプロセスが担う listen、
   プレイしない専用プロセスが担う dedicated から選びます。**利用できるリンクはここで決まります**。

3. **リンクとシグナリング** — pipe / WebRTC / WebTransport / WebSocket / QUIC-UDP からリンクを選び、
   相手の接続情報を取得する方法を決めます。

</Steps>

## それでも人数が効く場所がある

参加人数はトランスポートを決めませんが、**利用できる同期方式**には影響します。

ピア同士のリンクは star 型なので、ホスト以外のピア同士が通信するときはホストを経由します。
この経路は2ホップで、専用サーバを使う場合と同じです。1ホップで直結できるのは、ホスト自身が
相手になる**2人対戦だけ**です。

このホップ数によって、同期方式も制限されます。rollback と delay は、短く対称な経路を前提にします。
別のプレイヤーのマシンを経由する2ホップの経路は、その前提を満たしません。そのため3人以上では、
ピアと専用サーバのどちらを選んでも、最終的にはサーバ権威を使います。

2人と3人以上で選択肢が異なるのは、席数によって配線が変わるためではありません。
**2人だけが1ホップの同期方式を使える**ためです。

## データ経路か、制御経路か

次に決めるのは、サーバが対局中の**データを運ぶ**のか、接続の**仲介だけを行う**のかです。

| | データ経路にサーバがいる | 制御経路だけにいる |
|---|---|---|
| ホップ数 | プレイヤー間の全交換が2ホップ | ピア同士は直結（2人なら1ホップ） |
| 権威 | サーバが持つ。結果は信用できる | プレイヤーのマシンが持つ。結果は偽造可能 |
| 運用 | サーバを動かし続ける必要がある | 立てるものがない |
| 帰結 | ランク戦の成績として扱える | カジュアル戦や身内戦の範囲 |

サーバを制御経路だけにしてホップを減らす場合は、別のコストが生じます。行動だけを交換するピアは、
同じ入力から**同じ世界を再現しなければなりません**。つまり、入力同期にはシミュレーションを
ビット単位で再現できる決定性が必要です。1ホップ減らす代わりに、すべてのゲームルールがこの制約を
受けます。

<Aside type="caution" title="無料ではない">
「サーバを運用しなくてよい」という利点は、実装が簡単になるという意味ではありません。P2P の
データ経路を選ぶと、`rule:deterministic-simulation-required-for-rollback` の制約を引き受けます。
</Aside>

## トランスポートは2つ要る、あるいは1つでいい

WebTransport は専用ホストの構成を、WebRTC はプレイ中のプロセスがホストになる構成をカバーします。
一方のトランスポートで、もう一方の構成を置き換えることはできません。

必ずサーバを運用するプロジェクトでは、WebTransport と WebSocket フォールバックだけで足ります。
バックエンドを経由しない接続も必要なら、WebRTC を追加します。ブラウザ同士が直接接続するために
利用できる API は、WebRTC だけです。

## ウィザードが聞く3つのこと

`ebigent init` は、この選択を三つの質問にまとめています。

<Steps>

1. **プレイスタイル** — 1人 / 2人 / マルチ

2. **最大人数** — マルチのときだけ

3. **1台で複数人が遊べるようにするか** — 1人以外

</Steps>

生成するコードパターンは5通りです。三問目では、カメラを共有するかどうかではなく、一台のマシンを
複数人で共有するかを尋ねます。複数の個別カメラと共有画面を同時に使う構成もあるため、カメラ配置は
この二択には収まりません。マシンの共有だけを決め、カメラ配置は描画側に委ねます。

ホストがプレイに参加するか、専用サーバとして動くかによって、ゲームのコードは変わりません。
`cmd/server/` を `listen` ビルドタグで切り替え、ピアか dedicated かは実行時設定で選びます。
**多人数でも listen を選べます**。ブラウザが WebRTC で複数人をホストする場合は、
バックエンドが不要です。
