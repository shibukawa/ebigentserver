[トランスポート](/connection/transports/)を使うには、その前に相手の接続情報が必要です。
**相手の接続情報をどうやって知るか**という問題は、トポロジや Conn とは別に扱います。

## 4つのシグナリング方法

| 方法 | 使う場面 | ブラウザ |
|---|---|---|
| none | standalone。プロセス内トランスポート | — |
| control plane | dedicated server。エンドポイントはチケットの中に入って届く | 可 |
| LAN ディスカバリ | 同じネットワーク上のネイティブビルド | **不可** |
| 手動トークン | 静的ホスト構成。offer と answer をプレイヤーが帯域外で運ぶ | 可 |

どの方法を使えるかは、ゲームのジャンルではなく、ビルドターゲットとデプロイ方法で決まります。

### LAN ディスカバリ

UDP ブロードキャストのビーコンと、受動的なリスナを使います。プロトコルバージョンで候補を絞り、
TTL を過ぎた候補は失効します。ブラウザは UDP ブロードキャストを送れないため、ネイティブ限定です。

### 手動トークン

シグナリングサーバを使わない場合の経路です。WebRTC の offer / answer をテキストとして安全な
形式に変換し、チャット、wiki、メールなどで相手へ渡します。

base64 に変換する前のレイアウトは、次のとおりです。

```
version byte | type byte (invitation / answer) | expiry (unix秒)
| 宣言ペイロード長 | ペイロード
```

ペイロードには、`{session_id, sdp}` の JSON を格納します。よく使われる SDP の部分文字列を
固定辞書で置き換えてから flate で圧縮し、全体を `base64.RawURLEncoding` でエンコードします。

**宣言したペイロード長は、余分な文字を除外するために使います**。チャットソフトや wiki が末尾に
文字を追加しても、宣言した長さまでしか読まないため、追加部分を無視できます。

トークンは URL のフラグメントに載せます。フラグメントは HTTP サーバへ送信されません。
起動時にメモリへ読み込んだら、表示中の URL からも削除します。また、トークンには
**TURN の資格情報を含めません**。TURN の資格情報はページのメモリ内だけに保持します。

<Aside type="caution" title="トークンは bearer データ">
トークンを入手した人は誰でも使えるため、短い有効期限と一回限りの利用で保護します。`Decode` が
期限を検査し、受け入れ側の `Redeemer` が二回目以降の利用を拒否します。
</Aside>

## 着席（admission）

接続後の最初の往復で、利用する席を決めます。

<Steps>

1. **バージョン照合** — 最初に照合し、異なる版の間では交渉しません。不一致の場合は、双方の
   バージョンを示す明示的なエラーで拒否します。

2. **ローカル検証** — チケットの署名とクレームを、その場で検証します。接続経路上の control plane へ
   問い合わせる必要はありません。

3. **jti の償還** — 一度だけ受け付けます。同じチケットが再提示された場合は拒否します。

4. **接続への束縛** — 検証した身元を、現在の接続へ結び付けます。

5. **席とロールの適用** — player / spectator / observer の席とロールを適用します。

6. **シード配布** — 最初の snapshot で、共有 RNG シードを送ります。

</Steps>

ハンドシェイクの封筒には JSON を使い、**ゲームのスキーマバージョンに依存させません**。生成された
CBOR スキーマが異なる相手同士でも、プロトコルバージョンを比較して明示的に拒否する必要があるためです。

```go
type Hello struct {
	Protocol string `json:"protocol"` // data:game-version
	Ticket   string `json:"ticket"`   // compact JWT
}
```

### チケット

チケットは Ed25519 で署名した JWT です。共有の対称鍵は使いません。listen server や p2p では、
**プレイヤーのマシンがチケットを検証します**。対称鍵を配布すると、その鍵で全セッションの
チケットを偽造できてしまうためです。

```go
type Claims struct {
	Subject   string `json:"sub"`        // プレイヤー ID
	Audience  string `json:"aud"`        // 受理してよいエンドポイント
	ExpiresAt int64  `json:"exp"`        // 秒〜数分
	ID        string `json:"jti"`        // セッションごとに1回だけ償還
	SessionID string `json:"session_id"`
	Seat      uint16 `json:"seat"`
	Role      string `json:"role"`
}
```

`kid` で検証鍵を指定するため、鍵をローテーションしても発行済みのチケットを検証できます。

## 認証しない構成をどう守るか

身内だけで遊ぶ場合に、チケット発行サーバを必須にするのは過剰です。そこで、ネットワークの到達範囲を
制限できる場合に限り、チケットなしの着席を許可します。認証なしでは、**ローカルまたは
プライベートネットワーク上のアドレスだけを listen できます**。

```go
if err := admission.GuardUnauthenticated(listenAddr); err != nil {
	return err // 起動を止める
}
```

許可するのは loopback、RFC1918 のプライベート範囲、リンクローカルだけです。それ以外は
fail closed で拒否します。全インターフェースを公開する `0.0.0.0` と `::`、名前を解決できない
ホストも拒否します。

WebRTC には、このガードは必要ありません。手動トークンで着席する WebRTC セッションには
**待ち受けポートがない**ため、外部からスキャンして列挙できません。代わりに、一回限りで期限付きの
招待トークンが接続を制限します。

<Aside type="note" title="呼ぶ場所">
このガードは、設定の読み込み時だけでなく、セッション起動時と着席時にも呼びます。制限の解除には
オペレータの明示的な opt-in が必要で、既定では解除しません。
</Aside>
