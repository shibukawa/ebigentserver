格闘ゲーム、FPS、戦略ゲームでは、適切な tick レート、送信レート、履歴の保持数が異なります。
そのため framework は、これらの**既定値を持ちません**。リアルタイムセッションごとに tuning profile を
宣言し、起動前に値の整合性を検査します。

```go
tuning := session.TuningProfile{
	TickRate:     60,
	SendRate:     20,
	HistoryDepth: 16,
	BaselineMode: session.BaselineBounded,
	SpeculationDepth: 8,
}
if err := tuning.Validate(); err != nil {
	return err
}
```

検査で拒否する条件は具体的です。たとえば `SendRate` が `TickRate` を超える場合、`TickRate` が
`SendRate` の倍数ではなく送信間隔が整数 tick にならない場合、`BaselineBounded` なのに
`SpeculationDepth` がない場合、`SpeculationDepth` が `HistoryDepth` 以上で確定 baseline が
保持範囲から外れる場合です。

## 主な宣言項目

| 項目 | 意味 |
|---|---|
| `TickRate` | 毎秒のシミュレーションステップ数。必須 |
| `SendRate` | 毎秒の下り状態更新数。`TickRate` 以下かつ約数 |
| `SnapshotEvery` | N 回に1回は完全な snapshot を送る。0 なら join と resync のときだけ |
| `HistoryDepth` | 受信者ごとに保持する世界のバージョン数。delta の baseline の上限 |
| `BaselineMode` | どのバージョンとの差分を取るか |
| `AckMode` | ack をどう運ぶか |
| `InputIntake` | 1 tick に何件の入力を取り込むか |
| `RejectionThreshold` | 拒否された行動が何件たまったら疑うか |
| `SilenceDeadline` | 何 tick 落としたら沈黙とみなすか |
| `BandwidthBudget` / `MaxSnapshotSize` | 受信者あたりの目標バイト/秒、snapshot 1件の上限 |

## baseline の3モード

delta を作るには、比較元となる baseline を決める必要があります。三つのモードには、帯域使用量と
損失からの復帰しやすさのトレードオフがあります。

| モード | 差分の相手 | 性質 |
|---|---|---|
| `BaselineSpeculative` | 最後に**送った**バージョン | 最小帯域。1つ落ちると resync まで連鎖が壊れる |
| `BaselineConfirmedOnly` | 相手が**ack した**最新バージョン | 届いた delta は必ずデコードできる。RTT と損失の分だけ delta が太る |
| `BaselineBounded` | 確定 baseline から `SpeculationDepth` まで先読み、超えたら確定側に戻る | 中間 |

128ユニットの4人戦に ack 遅延と RTT スパイクを注入し、三つのモードを計測するテストがあります
（[`samples/rtslite`](https://github.com/shibukawa/ebigentserver/tree/main/samples/rtslite)）。
測定結果の順序は毎回 **speculative < bounded(16) < confirmed_only** となり、confirmed_only は
speculative より約4割多くの帯域を使います。テストが固定するのはこの順序です。絶対値は、
リンクの状態によって変わります。

損失のないローカルリンクでは、帯域の小さい speculative を選びます。損失や RTT スパイクがある
回線では、confirmed_only の追加帯域を、再同期を避けるためのコストとして選べます。

<Aside type="note" title="baseline は保持されていなければならない">
`HistoryDepth` より古い baseline を要求された場合は delta を作れないため、snapshot を送ります。
snapshot への切り替え自体は正常です。ただし、頻繁に起きる場合は profile を見直す必要があります。
</Aside>

## ack の運び方

| モード | 動作 |
|---|---|
| piggyback_only | 送信する datagram に ack を相乗りさせるだけ |
| dedicated | ack 専用の datagram を出す |
| delayed_piggyback | 少し待って相乗りを狙い、来なければ出す |

入力を送らない観戦者のように上りトラフィックがほとんどない役では、ack を相乗りさせる送信が
ありません。そのため dedicated を使います。

## 入力の取り込み方

1 tick に取り込む入力の件数は、同期モードで選びます。

```go
session.IntakeNewest // 最新の1件だけ
session.IntakeAll    // キューを到着順に全部
```

パドルやスティックのような連続操作では、新しい入力が古い入力を置き換えるため、`IntakeNewest` を
使います。一方、RTS の命令ストリームでは、1 tick に届いた三つの命令すべてに意味があります。
この場合は `IntakeAll` を使います。席ごとの FIFO を保つため、決定的コミットに必要な席内の順序も
維持できます。

## 1 tick の往復

```
上り  : agent → data:player-input
     ↓
権威側 : 検証 → slot ID 順にコミット → Advance
     ↓
下り  : data:state-delta ＋ data:game-event
     ↓
例外  : join したとき、あるいは同期が壊れたとき → data:snapshot
```

上りでは行動を送り、下りでは**席ごとに投影した状態の差分**を送ります。これがハイブリッド同期です。
RTS のように一つの席が多数のユニットを操作するゲームでも、同じ形を使えます。たとえば、上りの
コマンドを13バイトの固定配列、下りの view snapshot を600バイト超の map として、異なる二つの
CBOR プロファイルを同じセッションで併用できます。

## 遅い agent、消えた agent

リアルタイムペーシングでは、`Decide` が期限に間に合わなかった agent の入力を、その tick では
受け取りません。セッションも待機しません。これは例外ではなく、`InputIntake` と組み合わせて
宣言する通常の動作です。

入力のない状態が `SilenceDeadline` を超えるか、トランスポートが閉じた場合は離脱とみなします。
その後の扱いはゲーム側で決められます。席を空けたまま続けることも、新しい agent を着席させることも
できます。後者は「AI 引き継ぎ」と呼べますが、実装上は
[新しい Agent の着席](/integration/agent/)です。
