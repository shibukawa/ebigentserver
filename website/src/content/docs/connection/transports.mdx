上位のコードで「WebSocket なら〜」と分岐すると、ブラウザビルドとネイティブビルドに同じ選択処理が
重複します。そこで、プロトコル名ではなく**必要な能力**からトランスポートを選びます。

```go
type Capability struct {
	ReliableStream     bool // 順序保証つきの確実な配送
	UnreliableDatagram bool // 落ちるし並べ替わる
	PeerToPeer         bool // 間にサーバを置かずにつながる
	Browser            bool // ブラウザビルドから届く
}
```

datagram が必要なコードは `UnreliableDatagram` を確認します。WebSocket では `false` になるため、
確実チャネルへのフォールバックを選びます。上位のコードは、WebSocket かどうかを直接問いません。

## Conn

```go
type Conn interface {
	SendReliable(ctx context.Context, payload []byte) error
	SendUnreliable(ctx context.Context, payload []byte) error
	Receive(ctx context.Context) (Message, error)
	Close() error
	Capability() Capability
}
```

複数の goroutine から同時に送信できますが、順序を保証するのは一つの確実チャネル内だけです。
`Receive` は一度に一つの Message を返し、返したペイロードをトランスポート側で再利用しません。
`Close` は何度呼んでも安全で、待機中の `Receive` を解除します。

実装固有のエラーは、`ErrClosed` / `ErrTooLarge` / `ErrBackpressure` / `ErrUnsupported` の四つに
まとめます。

<Aside type="caution" title="再送はしない">
framework は、一度受理した行動を `Conn` 経由で再送しません。再接続は、新しいチケットを使った
[着席のやり直し](/connection/signaling/)であり、同じセッションの継続ではありません。
</Aside>

## 4つの実装

<Tabs>
<TabItem label="pipe">

プロセス内で接続する `Conn` のペアです。ローカル構成でそのまま使えるほか、**障害注入**を
設定すると、品質の悪い回線を再現する試験装置になります。

```go
faults := pipe.Faults{
	LossPercent:    20,
	Latency:        25 * time.Millisecond,
	Jitter:         8 * time.Millisecond,
	ReorderPercent: 10,
	Seed:           1234, // 障害 PRNG のシード
}
a, b := pipe.Pair(faults, faults) // 方向ごとに違う宣言もできる
```

確実チャネルには遅延とジッタだけを適用し、Message は失いません。非確実チャネルには、すべての
障害を適用します。ドロップと並べ替えのパターンはシード付き PRNG で再現できますが、配送には
実時間のタイマーを使うため、到着時刻までは再現しません。

</TabItem>
<TabItem label="WebSocket">

確実かつ順序保証付きの通信だけを提供し、ブラウザから利用できます。datagram はありません。

`SendUnreliable` も確実ストリーム上を通るため、呼び出し側が要求していない順序保証と到達保証が
付きます。[seqack](#seqack) は、この追加保証があっても動作します。一つのストリーム内にある
二つの論理チャネルは、先頭1バイトのプレフィックスで区別します。

datagram トランスポートを使えない場合のフォールバック先です。

</TabItem>
<TabItem label="WebTransport">

ブラウザ向けリアルタイム通信の主経路です。制御用の確実な双方向ストリームを一つ、状態送信用の
非確実 datagram を持ちます。

確実チャネルは接続時にクライアントが開く1本の双方向ストリームで、長さプレフィックス付きの
Message を流します。datagram は、そのまま QUIC datagram に対応します。

quic-go を使うサーバとネイティブクライアントは js/wasm をターゲットにできないので、この
ファイルはネイティブビルドだけでリンクします。ブラウザ側では、ブラウザの WebTransport API が
同じインターフェースを実装します。

</TabItem>
<TabItem label="WebRTC">

ピア間を直接接続できる唯一の経路です。二つのチャネルを**事前交渉**します。

- `reliable`（ordered, reliable）— snapshot、制御メッセージ、着席
- `state`（unordered, maxRetransmits 0）— 入力と状態差分

ストリーム ID は固定しているため、相手からチャネルの告知が届くのを待つ必要はありません。
SCTP アソシエーションが開くまで待つだけです。

ICE は non-trickle に限定し、上限時間内に候補収集を終えてから SDP を作ります。手動
シグナリングには、候補をあとから trickle する経路がないためです。同じ理由で mDNS による候補の
難読化も無効にします。手動で接続するピア間には、`.local` 名を解決する rendezvous がありません。

シグナリング方法は、呼び出し側が選びます。`NewOffer` / `Accept` / `Complete` は SDP をそのまま
返すため、control plane と[手動トークン](/connection/signaling/#手動トークン)のどちらで運ぶかを
上位のレイヤで決められます。

</TabItem>
</Tabs>

## framing

WebRTC のデータチャネルには Message サイズの上限があり、snapshot は簡単に超えてしまいます。
そこで、確実チャネルの上に分割・再構成を行う層を置きます。

```
byte 0     : 0xEB マーカー
byte 1     : バージョン (1)
bytes 2-5  : メッセージ ID
bytes 6-7  : チャンク番号
bytes 8-9  : チャンク総数
bytes 10.. : ペイロード
```

壊れたフレーム、範囲外の番号、重複、大きすぎるセットは、**framing 層で破棄します**。
セッション層には渡しません。tick ごとの入力は、この層を通りません。

## seqack

非確実な状態ストリームの前段で動き、接続の両端が同じ処理を実行します。

```
0xEA, version(1), flags, seq uint32, ackSeq uint32, ackBits uint32, payload
```

上位の層に渡すのは、ピアが確認済みの最新タグ（statesync が
[confirmed baseline](/connection/sync/) に使う tick）、RTT サンプル、損失推定、最終受信時刻の四つです。
沈黙したかどうかは、呼び出し側が欠落した tick 数から判定します。

すでに配送した番号以下の古い datagram には **ack を返しますが、上位へは配送しません**。
状態ストリームは last-writer-wins なので、順序が入れ替わって届いた古い状態は不要だからです。
