決定性を、人の注意だけで守り続けることはできません。あとから `math.Sin` を1行追加すると、
再生結果はビット単位で一致しなくなります。しかも、通常のプレイでは**すぐに気付けない**可能性があります。

そこで、決定性や依存方向の境界を破ると、ビルドまたはテストが失敗するようにしています。

## 浮動小数点を足すとビルドが落ちる

Message の構造体に `float64` を加えると、CBOR コーデックの生成を拒否します。同様に拒否するのは、
`float` のほか、素の `int`（幅がプラットフォーム依存）、`map`（順序が不定）、`interface`、
`time.Time` です。

```go
type Ball struct {
	X, Y fixmath.F64 // s32.32 固定小数点。OK
	VX   float64     // ← 生成が落ちる
}
```

数値には [fixmath](https://github.com/shibukawa/fixmath) を使います。F64（s32.32）、BAM 角度、Vec2、
宣言スケール間の変換を提供します。FixPointCS を移植しているため、`Sin`、`Atan2`、`Sqrt` も、
アーキテクチャが異なっても同じビット列を返します。

## RNG はシードからしか引けない

```go
func (RuleSet) Start(seed uint64) State {
	return State{Rand: fixmath.NewRand(seed | 1)}
}
```

PRNG を状態に含めると、乱数列はシミュレーションステップを通じてだけ進み、チェックポイントにも
保存されます。シードはエピソードログのヘッダへ記録するため、再生時に同じ乱数列を再現できます。

## コミットは席の順番で

各ステップの冒頭で、判断する席のスナップショットを取り、`SlotID` の昇順で行動をコミットします。
`ActingSlots` が返す順序には依存しません。これにより、map のイテレーション順や goroutine の
完了順が結果へ影響する余地をなくします。

## engine はクライアントエントリの中だけ

ゲームルールのパッケージから Ebitengine を import すると、テストが失敗します。

```go
func TestModuleImportBoundary(t *testing.T) {
	importcheck.Enforce(t, ".", importcheck.Default())
}
```

`go list -deps -json` で import グラフを検査し、違反したパッケージと**import の連鎖**を報告します。
単に違反があると示すだけでなく、「A → B → C で入った」と経路まで表示します。

Ebitengine を許可するのはクライアントのエントリポイントだけで、パスのパターンとして宣言します。

```go
cfg.Rules[0].AllowedEntries = append(cfg.Rules[0].AllowedEntries,
	"samples/*/cmd/*client*",
	"samples/*/cmd/*listen*",
	"samples/*/cmd/*static*",
)
```

同じ仕組みで cgo も検査します。cgo が依存に入ると wasm ターゲットをビルドできないため、
クライアントエントリ以外からの依存を拒否します。

<Aside type="note" title="ゲーム側にも1つ置く">
framework だけでなく、ゲームのモジュールにも
`importcheck.Enforce(t, ".", importcheck.Default())` を一つ置きます。許可するエントリのパターンは、
自分のリポジトリ構成に合わせて指定します。
</Aside>

## 入力デバイスはゲームロジックに入らない

`concept:action` はゲームが定義する**意図**であり、生のデバイス入力ではありません。
「W キーが押された」ではなく、「上に加速する」を行動として扱います。

この境界を守ると、同じ行動をキーボード、ゲームパッド、ボット、リプレイのどれからでも作れます。
生の入力を行動に含めると、`Agent` を共通化できません。

## 何が保証されるのか

四つの制約を守ると、次の性質を保証できます。

- 記録した対局を再生すると、4つのログストリームが**バイト単位で一致する**
- arm64 の開発機と amd64 の CI で、最終チェックポイントのダイジェストが一致する
- ログに記録された局面を、後から実際に復元できる

三つ目は、[AI 育成](/ai/)の前提です。「この局面でこの手を指した」という記録を再現できるため、
提案されたルールの根拠を人が確認できます。

<Aside type="caution" title="演出は状態ではない">
プレゼンスメッセージ（カーソル位置、絵文字、装飾）は、シミュレーションにも分析にも含めず、
記録もしません。状態へ混ぜると、実時間に依存する再現不能な情報が入ってしまいます。
</Aside>
