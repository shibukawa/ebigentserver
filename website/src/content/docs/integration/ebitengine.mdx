import { Aside, Steps, Tabs, TabItem, LinkCard } from '@astrojs/starlight/components';

クライアントのエントリには、世界を進める契約と、画面を描く契約が並びます。
Ebitengine 側は `Game` の `Update` / `Draw` / `Layout` という三つです。ebigentserver 側は
[`StageRuleSet`](/integration/stage-rule-set/)——`Start` / `ActingSlots` / `Apply` / `Project` /
`Evaluate` の五つです。

framework 側の契約を `Game` と呼ばないのは、二つの役割を名前から区別するためです。無関係な
インターフェースが同じ名前では、どちらが世界を進めるのか分かりません。描画側へルールを書いても、
最初は動く可能性があります。しかし、あとからボット、リプレイ、ヘッドレスサーバを追加できなくなります。

役割は明確に分けます。**`Update` はキー入力を行動へ変換し、inbox に入れるだけです**。
**`Draw` は受け取った世界を描くだけです**。世界を進めるシミュレーションは、別の goroutine で
実行します。

Ebitengine は main goroutine で実行する必要があります。そのため、session を別の goroutine で動かし、
main goroutine は `ebiten.RunGame` に渡します。

```go
func serve(ctx context.Context, h *host) error {
	go func() {
		if err := h.session.RunRealtime(ctx, session.Paced); err != nil {
			fatal(err)
		}
	}()
	ebiten.SetWindowSize(game.FieldW*scale, game.FieldH*scale)
	ebiten.SetWindowTitle("flappy")
	return ebiten.RunGame(&app{inboxes: h.local})
}
```

## キーボードが行動になる場所

生のデバイス入力をゲームの行動へ変換するのは、**クライアントエントリの中だけ**です。

```go
// 座席ごとに1キー。この規模ではこれが api:input-adapter の全部
var flapKeys = []ebiten.Key{
	ebiten.KeySpace, ebiten.KeyS, ebiten.KeyK, ebiten.KeyV,
	ebiten.KeyN, ebiten.KeyComma, ebiten.KeyQ, ebiten.KeyZ,
}

func (a *app) Update() error {
	for i, inbox := range a.inboxes {
		if i >= len(flapKeys) {
			break
		}
		if inpututil.IsKeyJustPressed(flapKeys[i]) {
			inbox.Submit(game.Action{Flap: true})
		}
	}
	return nil
}
```

`Update` は入力を変換して送るだけで、世界を更新する判断を行いません。同じ `game.Action` を、
ボット、リプレイストリーム、リモートピアも engine に依存せずに作れます。

<Aside type="caution" title="Draw で入力を読まない">
Ebitengine は `Update` を毎秒 TPS 回（既定60）呼び、`Draw` は画面のリフレッシュに合わせて
呼びます。二つの**呼び出し回数は一致しません**。`Draw` で `IsKeyJustPressed` を読むと、入力を
取りこぼしたり、二重に処理したりします。入力は `Update`、描画は `Draw` で扱います。
</Aside>

## 人間の席は Detached

ウィンドウが担当する人間の席には、実体のある Agent ではなく **`Detached` を着席させます**。

```go
local := localSeats()
for i, slot := range game.Slots() {
	if i < local {
		// この席の視界は、描画のために持っている world がすでに担っている
		s.Admit(slot, session.Detached[game.Sight, game.Action]{})
		inbox, _ := s.Inbox(slot)
		h.local = append(h.local, inbox)
		continue
	}
	// ボットの席は直接着席する。最終視界と Ended を受け取りたいので
	bot := &game.Bot{}
	s.Admit(slot, bot)
	inbox, _ := s.Inbox(slot)
	drivers = append(drivers, &game.Driver{Slot: slot, Agent: bot, Inbox: inbox})
}
```

これは、同じ情報の二重配送を避けるためです。ウィンドウは broadcast された世界をすでに
受け取っています。session がコールバックでも同じ視界を渡すと、**二つの経路が競合します**。

リモートプレイヤーにも同じ形を使います。リモートピアの席にも `Detached` が座り、視界は下りの
状態ストリームで届き、行動は `Inbox` へ入ります。そのため `netplay` の追加は `cmd/` 内で完結し、
`game/` のコードは変更しません。

<Aside type="note" title="ボットだけは直接 Admit">
ローカルボットには最終視界と `Ended` を渡すため、`Detached` ではなく Agent 本体を着席させます。
`Driver` が broadcast された世界を投影し、`Observe` / `Decide` へ渡します。
</Aside>

## 描画は世界を借りない

`Broadcast` は session の goroutine、`Draw` は Ebitengine の goroutine で実行します。session は
値を渡したあとも同じメモリを書き換えるため、`Draw` 側でポインタを保持してはいけません。

```go
func (v *view) store(w *gameState) {
	v.mu.Lock()
	defer v.mu.Unlock()
	v.world = *w
	v.world.Pipes = append([]game.Pipe(nil), w.Pipes...) // スライスは別途コピー
	v.got = true
}
```

構造体を代入するだけでは、スライスの背後にある配列を共有したままです。そこで `append` を使い、
別の配列へコピーします。

描画処理では、浮動小数点を使えます。ピクセル座標への変換には浮動小数点が必要です。

```go
// wire のスケールは 1/1024。表示の計算が float なのは、ここでだけ合法
px := func(v msg.Fixed1024) float32 { return float32(v) / 1024 }
```

固定小数点を使う目的は、シミュレーションの決定性を保つことです。描画で作った
**float の値をシミュレーションへ戻さない**限り、固定小数点から float への一方向の変換は安全です。

## 1つのディレクトリ、2つのリンク形態

同じ `cmd/` から、描画するビルドとヘッドレスビルドを作れます。一つのビルドタグで切り替えます。

<Tabs>
<TabItem label="描画するビルド">

```go
//go:build !dedicated

package main

import (
	"github.com/hajimehoshi/ebiten/v2"
	// ...
)

func localSeats() int { return game.Seats } // 1台で全員が遊ぶ場合

func onWorld(w *gameState) { shown.store(w) }

func serve(ctx context.Context, h *host) error {
	go func() {
		if err := h.session.RunRealtime(ctx, session.Paced); err != nil {
			fatal(err)
		}
	}()
	return ebiten.RunGame(&app{inboxes: h.local})
}
```

</TabItem>
<TabItem label="ヘッドレスビルド">

```go
//go:build dedicated

package main

// renderer の import が1つもない。この「なさ」が全部だ

func localSeats() int { return 0 } // 席は全部ボットかリモート

func onWorld(*gameState) {} // 誰も見ていない

func serve(ctx context.Context, h *host) error {
	return h.session.RunRealtime(ctx, session.Paced)
}
```

</TabItem>
</Tabs>

ビルドタグで切り替えるファイルが提供するのは、`localSeats()` と `serve()` の**二つだけ**です。
切り替える関数が増える場合は、描画とセッションの責任分担を見直します。

```bash
go build ./cmd/flappy
```

```bash
go build -tags dedicated ./cmd/flappy
```

タグは、通常のビルドへレンダラを追加するのではなく、**dedicated ビルドからレンダラを外す**ために
使います。開発中に頻繁に使う描画ビルドを既定とし、出荷用サーバを明示的な変種にします。

<Aside type="tip" title="なぜここだけタグを使うのか">
二つの形を一つのプロセス内で共存させることはできません。ヘッドレスサーバは engine を
**リンクしてはいけない**ためです。ビルドタグをこのディレクトリ内だけで使うことで、タグの指定漏れを
入口で検出できます。
</Aside>

## 境界はテストが守る

```go
func TestModuleImportBoundary(t *testing.T) {
	// 素のビルドは描画するので、その入口だけは engine をリンクしてよい
	playing := importcheck.Default()
	playing.Rules[0].AllowedEntries = append(playing.Rules[0].AllowedEntries, renderingEntries...)
	playing.AllowedCgoEntries = append(playing.AllowedCgoEntries, renderingEntries...)
	importcheck.Enforce(t, ".", playing)

	// 出荷するのはこちら。入口も含め、何一つレンダラに届いてはいけない
	headless := importcheck.Default()
	headless.BuildTags = []string{"dedicated"}
	importcheck.Enforce(t, ".", headless)
}

var renderingEntries = []string{"cmd/flappy"}
```

**タグなしと dedicated タグ付きの両方を検査します**。タグなしの import グラフだけでは、
タグ付きビルドの依存関係を検証できません。

`game/` に描画呼び出しを一つ移しても、描画ビルドのコンパイルは通る可能性があります。しかし、
境界テストは失敗し、**どの import の連鎖で engine が入ったか**まで表示します。

<Aside type="caution" title="キャッシュに注意">
この検査は Go ツールチェーンを呼び出しますが、その結果をテストキャッシュは追跡しません。
import グラフを変更したあとに確認するときは、`-count=1` を付けて実行します。
</Aside>

## 動かしてみる

pong の描画クライアントで、この構成を確認できます。ウィンドウは、ボットと同じループバックリンクの
クライアントとして動きます。snapshot / delta のストリームから世界を再構成し、inbox へ入力を送ります。

```bash
go run ./samples/pong/cmd/pong-client
```

W/S または ↑/↓ キーで、左のパドルを操作します。

```bash
go run ./samples/pong/cmd/pong-client -left=bot
```

こちらは、ボット同士の対戦を観戦します。観戦時のウィンドウは受信専用で接続し、inbox を持ちません。

## ゼロから作る

```bash
ebigent init
```

ウィザードの[三つの質問](/connection/#ウィザードが聞く3つのこと)に答えると、Ebitengine で動く
Flappy Bird 風のプロジェクトが生成されます。2羽が同じパイプ列を飛び、操作は flap だけです。
リアルタイム session、固定小数点物理、シード付き RNG、engine をクライアントエントリだけに
閉じ込める構成が、最初から動く状態で含まれます。

<Steps>

1. **プレイスタイル** — 1人 / 2人 / マルチ

2. **最大人数** — マルチのときだけ

3. **1台で複数人が遊べるようにするか** — 1人以外

</Steps>

三問目の答えは、そのまま `localSeats()` へ反映されます。1台を共有する場合は全席がローカルになり、
一人に一つずつキーを割り当てます。共有しない場合は `return 1` となり、残りの席は別プロセスから
参加します。

## すでにゲームがある場合

`go.mod` があるディレクトリで `init` を実行すると、既存のプロジェクトとして扱います。
モジュールパスとエントリポイントがすでにあるため、サンプルゲームは生成しません。framework 用の
ファイルだけを追加し、既存のコードには触れません。

```
ebigent.toml           プロトコルと build target の宣言
corpus/                エピソードの置き場
behavior/chips.json    チップライブラリ
cmd/distill/main.go    ebigent distill が go run するエントリ
.claude/skills/        解析スキル(環境によっては .agents/skills/)
```

エントリポイントの種類は import グラフから判断します。Ebitengine に依存するものは描画用の client、
依存しないものは simulation として扱います。これは
[rule:engine-import-confined-to-client-entry] と同じ境界を、既存コードの依存関係から判定する方法です。

`.gitignore` と `README.md` は変更しません。これらはリポジトリ側の方針で管理するファイルだからです。
コーパスを無視するための二行はコマンドの出力に表示されるので、必要に応じて自分で追加します。

## 踏み外しやすいところ

| やってしまうこと | 何が起きるか |
|---|---|
| `Draw` で入力を読む | `Update` と呼ばれる回数が違うので、入力が抜けるか二重になる |
| `Update` で世界を進める | session の tick と二重に進む。`Update` は投函するだけ |
| `game/` で `ebiten.IsKeyPressed` を呼ぶ | 境界テストが落ち、ヘッドレスビルドがコンパイルできなくなる |
| broadcast された `*State` をそのまま保持する | session が同じメモリを書き続けるので、`Draw` が壊れた世界を読む |
| 描画で作った float をシミュレーションに戻す | 再生がビット一致しなくなる。[ログが証拠でなくなる](/integration/boundaries/) |
| 人間の席に本体の agent を着席させる | broadcast とコールバックの二重配送になる。`Detached` を使う |
