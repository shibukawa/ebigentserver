## 型パラメータが3つある理由

`S`（世界状態）、`A`（行動）、`O`（視界）。三目並べのように全員が同じ盤面を見るゲームでは、
`S` と `O` はほとんど同じ形になる。それでも別の型として分けてある。

分けておくと何が起きるかは、ダンジョンのサンプルを見ると分かりやすい。ダンジョンマスターは
マップ全体を受け取り、冒険者は探索済みのセルと発見済みの罠しか受け取らない。この2つは
**別の生成 struct** で、ネットワーククライアントも別の view 型でインスタンス化される。

そして変わったのは `Project` の中身だけだ。セッションのループも、差分生成も、配送も、
一行も変わっていない。

<Aside type="note" title="投影はシリアライズより前">
隠れている状態は「送るときに落とす」のではなく、**エンコードすらされない**。可視性は
表示フィルタではなく、プレイヤー同士の間の境界になっている。
scout のクライアントに届いた全バイト列を捕捉して独立にデコードし直し、未発見の罠が
一つも載っていないことを確かめるテストがある。
</Aside>

## 誰が何を持つか

ここは混ざりやすいところなので、線をはっきり引いておく。

| ゲームが決める | framework が持つ |
|---|---|
| 視界に何を載せるか | 視界をいつ届けるか |
| 何が合法手か | 拒否されたときのエスカレーション |
| 誰に何が見えるか（可視性の述語） | 保持・差分・送信 |
| 評価をどう計算するか | 評価を**呼ぶこと**（agent は自分を採点しない） |
| 席の集合と役割 | 席の順序でコミットすること |
| 行動と世界の型 | それを CBOR で運ぶこと |

右の列は、ゲームが増えても変わらない。左の列は、ゲームごとに全部違う。

## 呼ばれる順番

```
Start(seed)
  ↓
┌─ ActingSlots(state)          ← 今ステップ判断する席
│    ↓
│  Project(state, slot)        ← 席ごとの視界
│    ↓  Observe(obs)
│  Decide(ctx) → action        ← agent
│    ↓
│  Legal(state, slot, action)  ← 合法性（省略可）
│    ↓
│  Apply(state, slot, action)  ← 失敗してはいけない
│    ↓
│  Evaluate(state, slot)       ← 評価シグナル
│    ↓
└─ 記録・差分生成・送信
```

`Apply` が失敗してはいけないのは、合法性がその前に確定しているからだ。判定と適用を分けて
おくと、判定の方だけを rollback で全ピアが走らせられる。
