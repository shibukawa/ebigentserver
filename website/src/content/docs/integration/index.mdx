セッションランタイムを導入すると、ゲーム側のコードをどこまで書き換える必要があるのでしょうか。

ゲームと framework の接点は四つのインターフェースに限られ、そのうち必須なのは一つだけです。

ここで扱うのは、ゲームルールと session runtime の接点です。ウィンドウ、入力、描画の配線は、
別のページで扱います。

## 型パラメータが3つある理由

`S` は世界状態、`A` は行動、`O` は視界です。三目並べのように全員が同じ盤面を見るゲームでは、
`S` と `O` はほとんど同じ形になります。それでも、役割の違いを別の型で表します。

この違いは、ダンジョンのサンプルで明確になります。ダンジョンマスターはマップ全体を受け取りますが、
冒険者が受け取るのは探索済みのセルと発見済みの罠だけです。二つの視界には**別の生成 struct** を使い、
ネットワーククライアントもそれぞれの view 型でインスタンス化します。

この違いを実装するために変更するのは、`Project` の中身だけです。セッションループ、差分生成、
配送処理は変更しません。

<Aside type="note" title="投影はシリアライズより前">
隠れている状態は送信時に除外するのではなく、**最初からエンコードしません**。可視性は表示上の
フィルタではなく、プレイヤー間で情報を分ける境界です。
scout のクライアントに届いた全バイト列を捕捉して独立にデコードし直し、未発見の罠が
一つも含まれないことをテストで確認しています。
</Aside>

## 誰が何を持つか

ゲーム側と framework 側の責任は、次のように分かれます。

| ゲームが決める | framework が持つ |
|---|---|
| 視界に何を載せるか | 視界をいつ届けるか |
| 何が合法手か | 拒否されたときのエスカレーション |
| 誰に何が見えるか（可視性の述語） | 保持・差分・送信 |
| 評価をどう計算するか | 評価を**呼ぶこと**（agent は自分を採点しない） |
| 席の集合と役割 | 席の順序でコミットすること |
| 行動と世界の型 | それを CBOR で運ぶこと |

右の列はゲームが増えても変わりません。左の列は、ゲームごとに実装します。

## 呼ばれる順番

```
Start(seed)
  ↓
┌─ ActingSlots(state)          ← 今ステップ判断する席
│    ↓
│  Project(state, slot)        ← 席ごとの視界
│    ↓  Observe(obs)
│  Decide(ctx) → action        ← agent
│    ↓
│  Legal(state, slot, action)  ← 合法性（省略可）
│    ↓
│  Apply(state, slot, action)  ← 失敗してはいけない
│    ↓
│  Evaluate(state, slot)       ← 評価シグナル
│    ↓
└─ 記録・差分生成・送信
```

`Apply` が失敗しない前提なのは、その前に合法性を検証しているためです。判定と適用を分けることで、
rollback では判定だけをすべてのピアで実行できます。
