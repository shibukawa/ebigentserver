「相手の手札はクライアントに送るけど、描画しないから大丈夫」——これが破られたときの被害を
知っている人は多いと思う。表示フィルタは防御ではない。

ここでの可視性は、描画の話ではなくプレイヤー同士の間の**境界**として設計されている。
効いているのは順番だ。**投影がシリアライズより前に走る**ので、隠れている状態は送られないの
ではなく、そもそもエンコードされない。

```
world → Project(state, slot) → view → 保持 → diff → 送信
         ↑ ここで落ちたものは、この先のどこにも存在しない
```

## 観測に何を載せるか

観測の中身は全面的にゲームの権限で、framework は一度も検査しない。おおむね次のような部品が
入る。

- 自分（席、役割、能力）
- 見えているエンティティ
- 目的
- **評価シグナル** — 合法手の集合だけでは、agent は勝っているのかどうか分からない
- 直近のイベント
- 環境

合法手を観測に載せることには副作用がある。オセロのサンプルでは `Observation.Legal` が
（返せる石の数という affordance 付きで）合法手を列挙するので、**ボットはルールエンジンを
持たなくてよくなる**。

## scope の種類

| scope | 例 |
|---|---|
| global | 全員が同じ盤面を見る（三目並べ、オセロ） |
| self | 自分の状態だけ |
| team | チームで共有される事実 |
| role | 役割ごとに種類の違う view |

ダンジョンのサンプルでは、scout（視界が広い）／engineer（罠を解除できる）／carrier（宝を運ぶ）／
navigator（出口を知っている）で、行動も情報も役割でゲートされている。ダンジョンマスターは
マップ全体を、冒険者は探索済みのセルと発見済みの罠だけを受け取る。この2つは半径が違うのではなく、
**別の型**だ。

## 可視性アノテーション

分析の側から見ると、観測の JSON に「値がない」ことの意味は二通りある。**見えなかった**のか、
**使わなかった**のか。この区別が付かないと、ランタイムの agent には評価できない条件を
提案してしまう。

そこでゲームが明示的に宣言する。

```go
type VisibilityAnnotation struct {
	Scope           string   // "self" / "team" / "role" / "spectator" / "global"
	Schema          string   // どの観測の形を受け取ったか
	VisibleEntities []uint32 // いま知覚できた id
	Stale           []uint32 // 以前見た。覚えてはいるが確認されていない
	Derived         []string // 受け取ったのではなく計算した値
	Affordances     []string // インターフェースが実際に提示した選択肢
	EvaluationScope string   // "scoped" / "privileged"
}
```

`Affordances` は「そのプレイヤーが選べたはずの選択肢の範囲」を後から絞るためにある。
`EvaluationScope` は評価シグナルの出どころの申告で、`privileged`（ground truth から計算した）
なら、対局中は agent に渡してはいけない。

推測ではなく宣言なのは、**なぜ見えたのかを知っているのはゲームだけ**だからだ。

## 評価は可視性を尊重する

ダンジョンのパーティに配られる評価シグナルは、チームに見えている事実だけから計算される。
ダンジョンマスターが隠し罠をいくつ置いても、パーティの signal は変わらない。これはテストで
確かめてある——罠を置いた前後で値が動かないこと。

一方でダンジョンマスター側の評価は ground truth を使ってよく、その場合は
`EvaluationScope: "privileged"` と申告する。

## 載っていないことを確かめる

「送っていないつもり」を信じないためのテストがある。scout のクライアントに届いた**全バイト列**を
捕捉し、独立したデコード鎖で再構成して、180パケットすべてについて次を検証する。

- 未発見の罠が含まれていない（その間、サーバ側には罠が8個存在する）
- 未探索セルの壁情報が含まれていない
- 出口の座標が含まれていない

<Aside type="tip" title="この形は流用できる">
自分のゲームで同じことをやるなら、クライアントの受信ハンドラでバイト列を貯めて、テストの中で
デコードし直せばよい。view の型ではなく**バイト列**から始めるのが要点で、view 型を経由すると
「型に載っていないから安全」という循環した検証になる。
</Aside>

## framework 側は何も変わらない

可視性を導入しても、差分生成の機構はそのまま再利用される。

```go
sender, err := statesync.NewProjectedSender[World, ScoutView, ScoutDelta](
	codec, tuning,
	func(w *World) ScoutView { return projectScout(w) }, // ゲームが書くのはここだけ
)
```

保持も diff も baseline も送信も、世界を送るときと同じコードが動く。ゲームが書くのは
可視性の述語とフィールドの選択だけ。fog of war と interest management は、この述語を
書くだけで成立する。
