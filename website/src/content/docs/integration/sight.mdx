「相手の手札もクライアントへ送るが、描画しなければ問題ない」という設計では、受信データを
調べるだけで手札が見えてしまいます。表示フィルタは、情報を守る境界にはなりません。

ここでの可視性は、描画ではなくプレイヤー間の**情報境界**です。**シリアライズより前に投影を
行う**ため、隠れた状態はネットワークへ送られないだけでなく、最初からエンコードされません。

```
world → Project(state, slot) → view → 保持 → diff → 送信
         ↑ ここで落ちたものは、この先のどこにも存在しない
```

## 視界に何を載せるか

視界に何を含めるかはゲーム側が決め、framework は中身を検査しません。一般的には、次の情報を
含めます。

- 自分（席、役割、能力）
- 見えているエンティティ
- 目的
- **評価シグナル** — 合法手の集合だけでは、agent は勝っているのかどうか分からない
- 直近のイベント
- 環境

合法手を視界に含めると、Agent 側の実装も簡単になります。オセロのサンプルでは `Sight.Legal` が
（返せる石の数という affordance 付きで）合法手を列挙するので、**ボットはルールエンジンを
持つ必要がありません**。

## scope の種類

| scope | 例 |
|---|---|
| global | 全員が同じ盤面を見る（三目並べ、オセロ） |
| self | 自分の状態だけ |
| team | チームで共有される事実 |
| role | 役割ごとに種類の違う view |

ダンジョンのサンプルでは、scout（視界が広い）／engineer（罠を解除できる）／carrier（宝を運ぶ）／
navigator（出口を知っている）に分かれ、行動と情報を役割ごとに制限します。ダンジョンマスターは
マップ全体を受け取りますが、冒険者が受け取るのは探索済みのセルと発見済みの罠だけです。この二つは
同じ型で半径が違うのではなく、**別の型**です。

## 可視性アノテーション

視界の JSON に値がない場合、分析側だけでは理由を判断できません。情報が**見えなかった**のか、
見えていたが**使わなかった**のかという二つの可能性があるためです。この区別がないと、実行時の
agent には評価できない条件を提案してしまいます。

そこで、ゲーム側が可視性を明示的に宣言します。

```go
type VisibilityAnnotation struct {
	Scope           string   // "self" / "team" / "role" / "spectator" / "global"
	Schema          string   // どの視界の形を受け取ったか
	VisibleEntities []uint32 // いま知覚できた id
	Stale           []uint32 // 以前見た。覚えてはいるが確認されていない
	Derived         []string // 受け取ったのではなく計算した値
	Affordances     []string // インターフェースが実際に提示した選択肢
	EvaluationScope string   // "scoped" / "privileged"
}
```

`Affordances` は、そのプレイヤーが選べた選択肢の範囲を、あとから特定するために使います。
`EvaluationScope` は評価シグナルの出どころを示します。ground truth から計算した `privileged` の
値は、対局中の agent に渡してはいけません。

可視性を分析側で推測せず、ゲーム側で宣言するのは、**その情報が見える理由を知っているのが
ゲームだけ**だからです。

## 評価は可視性を尊重する

ダンジョンのパーティへ配る評価シグナルは、チームに見えている情報だけから計算します。
ダンジョンマスターが隠し罠を追加しても、パーティの signal は変わりません。テストでは、
罠を置く前後で signal が変化しないことを確認します。

一方、ダンジョンマスター側の評価には ground truth を使えます。その場合は、
`EvaluationScope: "privileged"` と宣言します。

## 載っていないことを確かめる

隠し情報を本当に送っていないことは、バイト列から検証します。scout のクライアントに届いた
**すべてのバイト列**を捕捉し、独立したデコード処理で再構成します。そして、180パケットすべてに
ついて次を確認します。

- 未発見の罠が含まれていない（その間、サーバ側には罠が8個存在する）
- 未探索セルの壁情報が含まれていない
- 出口の座標が含まれていない

<Aside type="tip" title="この形は流用できる">
自分のゲームで同じ検証を行う場合は、クライアントの受信ハンドラでバイト列を保存し、テスト内で
デコードし直します。view 型ではなく**受信したバイト列**から始めることが重要です。view 型から
確認すると、「型に含まれないから安全」という実装と同じ前提に依存した検証になります。
</Aside>

## framework 側は何も変わらない

可視性を導入しても、差分生成の仕組みはそのまま再利用できます。

```go
sender, err := statesync.NewProjectedSender[World, ScoutView, ScoutDelta](
	codec, tuning,
	func(w *World) ScoutView { return projectScout(w) }, // ゲームが書くのはここだけ
)
```

保持、diff、baseline、送信には、世界を送る場合と同じコードを使います。ゲーム側で実装するのは、
可視性の述語と、視界に含めるフィールドの選択だけです。この投影によって、fog of war と
interest management を実現できます。
