ゲームサーバーを設計しはじめると、わりと早い段階で「サーバ権威にするか、P2P にするか」を
決めさせられる。だがこの質問には、実は独立した二つの問いが押し込まれている。
**プロセスをどこに置くか**と、**どのタイミングで誰の判断を正とするか**だ。前者を変えても後者は
変わらないし、その逆もない。ebigentserver がこの二つを別々の軸として持っているのは、混ぜたまま
実装すると片方を変えるたびにもう片方まで書き直すことになるからだ。

もっとも、その話に入る前に片付けておくべき、もっと手前の分岐がある。

## 一つの抽象で足りるのか

視界を受け取って行動を返す。人間もボットもリプレイも、やっていることはそれだけだ——と言い切って
しまうのは簡単だが、本当に足りるのかは疑わしい。人間には入力デバイスがあり、ボットには探索の時間が
必要で、リプレイに至っては「判断」すらしていない。

```go
type Agent[O, A any] interface {
	Joined(slot SlotID)
	Observe(obs O)
	Decide(ctx context.Context) (action A, ok bool)
	Ended(result Result)
}
```

この4つで足りている、という主張には検証条件がある。ゲームのルールを書いたパッケージに、
操作者の種別で分岐する行が一つもないこと。三目並べのサンプル
（[`samples/tictactoe/ttt`](https://github.com/shibukawa/ebigentserver/tree/main/samples/tictactoe/ttt)）は
その検証のために存在していて、agent の実装型を一切参照しない。人間かボットかを選ぶのは
起動時のフラグだけで、ルールの側は最後まで知らない。

効いてくるのはむしろ後の方だ。プレイヤーが試合中に切断したとき、その席をボットに引き継がせる
処理は「AI 引き継ぎ機能」ではなく、**新しい agent がその席に着席するだけ**になる。8人対戦に
切断とAI引き継ぎを注入したテストが通っているのは、そのための機構を足したからではない。
足すものが何もなかったからだ。

<Aside type="note" title="agent の種類">
人間クライアント、スクリプトボット、蒸留された行動ツリー、LLM、リモートピア、リプレイストリーム。
いずれも同じ `Agent` を実装する。違うのは「視界 → 行動」の中身だけで、session からは区別が付かない。
</Aside>

## 配置と同期は別の質問

冒頭の話に戻る。session と agent を**どこに置くか**（実行トポロジ）と、**どうやって整合を
保つか**（同期モード）は、直交する。

| 実行トポロジ | 中身 |
|---|---|
| standalone | 1プロセスの中に session も agent も全部いる |
| listen server | プレイしているプロセスの一つが session を持つ |
| dedicated server | プレイしない専用プロセスが session を持つ |
| p2p | ピア同士が直接つながる（リンクは star 型） |

| 同期モード | 中身 |
|---|---|
| delay | 入力を一定量遅らせて全員のタイミングを揃える |
| rollback | 予測して進め、入力が届いたら巻き戻して再実行する |
| server authoritative | 権威プロセスの結果だけが正 |
| hybrid | 上りは入力、下りは投影された状態差分 |

listen server で rollback を使うこともできるし、dedicated server で hybrid を使うこともできる。
組み合わせを縛るのはトポロジそのものではなく、**ホップ数**だ。ピアのリンクは star 型なので、
3人以上ではピア経由でもサーバ経由でも等しく2ホップになる。1ホップが成立するのは、
相手がホストその人である2人のときだけ。だから rollback や delay が射程に入るのも2人までで、
3人以上はどちらを選んでもサーバ権威に落ち着く。

## 記録が土台になる

固定小数点で計算し、RNG はシードから引き、行動は slot ID 順にコミットする。この三つを守ると、
同じ入力からは同じ世界が再現される。地味な制約に見えるが、これが効いてくる場所は二つある。

一つは検証。記録した対局を再生すると、4つのログストリームが**バイト単位で一致**する。
arm64 の開発機と amd64 の CI で最終チェックポイントのダイジェストが同じになることも、
定数で固定したテストが確かめている。

もう一つは AI だ。ビット一致で再現できるログは、単なる記録ではなく**証拠**になる。
「この局面でこの手を指した」と言われたとき、その局面を実際に復元して確かめられる。
ログから条件→行動のルールを提案させ、人間が承認したものだけを Go のコードに落とす、という
パイプラインが成り立つのは、この再現性が下敷きにあるからだ。

<LinkCard title="ログが AI になるまで" href="/ai/" description="JSONL の4ストリームから、承認済みチップ、そして生成された Go コードまで。" />

## 動かして確かめる

サンプルは飾りではなく、framework の回帰テストそのものになっている。各サンプルが担当する
能力は一つずつずれていて、前のサンプルにない何かを一つだけ足す。

| サンプル | 足している能力 | 起動 |
|---|---|---|
| tictactoe | セッション核、step ペーシング、人間とボットの同居 | `go run ./samples/tictactoe/cmd/ttt` |
| reversi | 合法手つき視界、エピソード記録と再生 | `go run ./samples/reversi/cmd/reversi` |
| pong | リアルタイム tick、固定小数点物理、snapshot / delta | `go run ./samples/pong/cmd/pong` |
| tron | 多人数（2〜8席）、観戦者、離脱と不正入力への耐性 | `go run ./samples/tron/cmd/tron` |
| dungeon | 役割ごとに種類の違う視界、隠し情報がワイヤに載らない検証 | テストのみ |
| rtslite | 命令ストリームと fog 投影のハイブリッド同期 | テストのみ |

reversi と pong は `-record=DIR` を付けるとエピソードログを吐く。AI 育成の話は、
そこで出てきたディレクトリから始まる。
