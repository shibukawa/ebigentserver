ゲームサーバーを設計し始めると、早い段階で「サーバ権威にするか、P2P にするか」を迫られます。
しかし、この質問には別々に考えるべき二つの問いが含まれています。**プロセスをどこに置くか**と、
**どのタイミングで誰の判断を正とするか**です。一方を変えても、もう一方が変わるとは限りません。
ebigentserver が二つを別の軸として扱うのは、混ぜて実装すると、片方を変えるたびにもう片方まで
書き直すことになるためです。

ただし、その二つを考える前に、さらに手前の分岐を整理する必要があります。

## 一つの抽象で足りるのか

Agent は視界を受け取って行動を返します。人間もボットもリプレイも、それだけで表せるのでしょうか。
人間には入力デバイスがあり、ボットには探索時間が必要です。リプレイは「判断」さえしていません。

```go
type Agent[O, A any] interface {
	Joined(slot SlotID)
	Observe(obs O)
	Decide(ctx context.Context) (action A, ok bool)
	Ended(result Result)
}
```

この4つで足りるかどうかは、ゲームのルールを書いたパッケージを見れば確認できます。
そこに、操作者の種類で分岐する行が一つもないことが条件です。三目並べのサンプル
（[`samples/tictactoe/ttt`](https://github.com/shibukawa/ebigentserver/tree/main/samples/tictactoe/ttt)）では、
agent の実装型を一切参照していません。人間かボットかは起動時のフラグで選びますが、ルール側は
最後までその違いを知りません。

この設計は、試合中の切断で効いてきます。切断したプレイヤーの席をボットに引き継ぐ処理は、
専用の「AI 引き継ぎ機能」ではありません。**新しい agent がその席に着席するだけ**です。
8人対戦で切断と AI 引き継ぎを試すテストも、専用の機構を追加せずに通ります。

<Aside type="note" title="agent の種類">
人間クライアント、スクリプトボット、蒸留された行動ツリー、LLM、リモートピア、リプレイストリームの
いずれも、同じ `Agent` を実装します。違うのは「視界 → 行動」の中身だけで、session からは区別できません。
</Aside>

上の一層だけがゲーム固有です。下の五層は、差し替え可能な部品として並んでいます。この境界は、
人の注意力ではなく [`importcheck`](/integration/boundaries/) が検査します。ゲームルールの
パッケージから Ebitengine を import すると、**ビルドが失敗します**。

## 配置と同期は別の質問

ここで最初の問いに戻ります。session と agent を**どこに置くか**（実行トポロジ）と、
**どのように整合性を保つか**（同期モード）は、別々に選べます。

| 実行トポロジ | 中身 |
|---|---|
| standalone | 1プロセスの中に session も agent も全部いる |
| listen server | プレイしているプロセスの一つが session を持つ |
| dedicated server | プレイしない専用プロセスが session を持つ |
| p2p | ピア同士が直接つながる（リンクは star 型） |

| 同期モード | 中身 |
|---|---|
| delay | 入力を一定量遅らせて全員のタイミングを揃える |
| rollback | 予測して進め、入力が届いたら巻き戻して再実行する |
| server authoritative | 権威プロセスの結果だけが正 |
| hybrid | 上りは入力、下りは投影された状態差分 |

listen server で rollback を使うことも、dedicated server で hybrid を使うこともできます。
組み合わせを制限するのは、トポロジそのものではなく**ホップ数**です。ピアのリンクは star 型なので、
3人以上ではピア経由でもサーバ経由でも同じ2ホップになります。1ホップで届くのは、2人対戦で
相手がホスト本人の場合だけです。そのため、rollback や delay を選べるのも2人までです。
3人以上では、どのトポロジを選んでもサーバ権威になります。

## 記録が土台になる

固定小数点で計算し、RNG はシードから値を取り、行動は slot ID 順にコミットします。この三つを
守ると、同じ入力から同じ世界を再現できます。地味な制約に見えますが、二つの場面で重要になります。

一つは検証です。記録した対局を再生すると、4つのログストリームが**バイト単位で一致**します。
arm64 の開発機と amd64 の CI で最終チェックポイントのダイジェストが同じになることも、
定数を使ったテストで確認しています。

もう一つは AI です。ビット単位で再現できるログは、単なる記録ではなく**証拠**になります。
「この局面でこの手を指した」という記録から局面を復元し、実際に確かめられるためです。
この再現性があるからこそ、ログから条件→行動のルールを提案し、人が承認したものだけを Go の
コードに変換するパイプラインが成り立ちます。

## 動かして確かめる

サンプルは単なる展示ではなく、framework の回帰テストでもあります。各サンプルは、前のサンプルに
なかった能力を一つずつ追加します。

| サンプル | 足している能力 | 起動 |
|---|---|---|
| tictactoe | セッション核、step ペーシング、人間とボットの同居 | `go run ./samples/tictactoe/cmd/ttt` |
| reversi | 合法手つき視界、エピソード記録と再生 | `go run ./samples/reversi/cmd/reversi` |
| pong | リアルタイム tick、固定小数点物理、snapshot / delta | `go run ./samples/pong/cmd/pong` |
| tron | 多人数（2〜8席）、観戦者、離脱と不正入力への耐性 | `go run ./samples/tron/cmd/tron` |
| dungeon | 役割ごとに種類の違う視界、隠し情報がワイヤに載らない検証 | テストのみ |
| rtslite | 命令ストリームと fog 投影のハイブリッド同期 | テストのみ |

reversi と pong に `-record=DIR` を付けると、エピソードログが出力されます。AI の育成には、
このディレクトリを使います。
