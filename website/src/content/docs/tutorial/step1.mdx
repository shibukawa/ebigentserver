## ルールの側

```go
// Place takes cell for the side to move and reports whether it happened.
// An illegal cell leaves the state untouched, so a caller may hand it
// any click without checking first.
func (s *State) Place(cell int) bool {
	if !s.Legal(cell) {
		return false
	}
	mark := s.Turn
	s.Board[cell] = mark
	s.Moves++
	if line, won := s.Board.lineFor(mark); won {
		s.Winner, s.Line, s.Over, s.Turn = mark, line, true, Empty
		return true
	}
	if s.Moves == len(s.Board) {
		s.Over, s.Turn = true, Empty
		return true
	}
	s.Turn = mark.Other()
	return true
}
```

`Place` は不正な手を拒み、その場合は状態を1バイトも変えません。そのため呼び出し側は、盤面上の
クリックを事前に検査せず、そのまま渡せます。この動作はテストで固定しています。

```go
func TestOccupiedCellIsRefusedAndChangesNothing(t *testing.T) {
	s := play(t, 4)
	before := s
	if s.Place(4) {
		t.Fatal("Place on an occupied cell reported success")
	}
	if s != before {
		t.Fatalf("refused move mutated the state:\n got %+v\nwant %+v", s, before)
	}
}
```

## ピクセルがセルになる場所

```go
// cellAt maps a cursor position to a board cell — the one place a pixel
// turns into a move.
func cellAt(x, y int) (int, bool) {
	x, y = x-margin, y-margin
	if x < 0 || y < 0 || x >= boardPx || y >= boardPx {
		return noCell, false
	}
	return (y/cellPx)*3 + x/cellPx, true
}
```

この関数から先の処理は、マウスの存在を知りません。`Update` が行うのは、変換結果を `Place` に
渡すことだけです。

```go
func (a *app) Update() error {
	mx, my := ebiten.CursorPosition()

	a.hover = noCell
	if cell, ok := cellAt(mx, my); ok && a.state.Legal(cell) {
		a.hover = cell
	}

	if inpututil.IsMouseButtonJustPressed(ebiten.MouseButtonLeft) {
		if a.state.Over {
			a.state = game.New() // any click starts the next game
		} else if cell, ok := cellAt(mx, my); ok {
			a.state.Place(cell)
		}
	}
	if inpututil.IsKeyJustPressed(ebiten.KeyR) {
		a.state = game.New()
	}
	return nil
}
```

<Aside type="note" title="入力は Update、描画は Draw">
Ebitengine は `Update` を固定レートで呼び、`Draw` は画面のリフレッシュに合わせて呼びます。
呼び出し回数は一致しないため、`Draw` で `IsMouseButtonJustPressed` を読むと入力を取りこぼします。
この違いは、[Ebitengine への統合](/integration/ebitengine/)でも詳しく説明します。
</Aside>

## あとで効く2つの継ぎ目

ここまでに入れた構造のうち、二つが後のステップで重要になります。

**`cellAt` の出口** — ピクセルをセル番号に変えた結果は、step 2 で `Submit` の引数になります。
この行は、結果がローカルの inbox に入るのか、別のマシンのソケットへ届くのかを知る必要がありません。

**`game` パッケージが engine を知らないこと** — step 2 では `StageRuleSet[W, A, S]` を実装しますが、
ルールを別の場所へ移す必要はありません。`Project` と `Evaluate` を**追加する**だけで済みます。

型引数が三つあるのは、step 2 で `State` の役割が三つに分かれるためです。現在の `State` は、
ゲームの正しい状態であり、画面に出す状態であり、判断の材料でもあります。1台だけなら、同じ型で
問題ありません。しかし、2台目が同じ盤面を見るようになると、三つの状態は別々の場所に、
異なる頻度で存在するようになります。

## まだないもの

まだボット、記録、ネットワーク、シードはありません。`Update` が世界を直接書き換えており、
tick という概念もありません。2人が同じマシンで遊ぶ限り、これで問題は起きません。

問題が表れるのは、三つ目の操作者である CPU を追加するときです。`Update` の中に
「いま O の番ならボットに考えさせる」と書くことはできます。しかし、その1行こそが、
[最初に避けた分岐](/overview/#一つの抽象で足りるのか)です。
