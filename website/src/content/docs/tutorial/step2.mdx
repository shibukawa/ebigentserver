step 1 で三目並べが動くようになりました。ただし、2人とも同じマウスを使います。このステップでは、
アドレスを1文字も入力せずに、**別のマシンにいる相手と対戦できる**ようにします。

## ロビーとは

**ロビーは、一緒にゲームを始めるメンバーを決める画面です。** ゲームによっては、事前に作った
パーティの全員がそろうのを待ったり、自分のランクやレベルに近い相手を検索したりします。誰と遊ぶかを
確定し、必要な席が埋まってから対局へ進むところまでが、ロビーの役割です。

この framework では、対局のルールから見ると、人も AI ボットも同じように席を操作する参加者です。
ロビーは、人が取った席とボットで埋める席を組み合わせ、今回一緒に遊ぶメンバーを確定します。

ただし、step 2 で用意するのは**人と人の対戦だけ**です。二つある席のうち、一つ目には最初に起動した
人が座ります。二つ目は空席のまま残し、別のマシンでアプリを起動した人が来るのを待ちます。
この段階では、次のことができるようになります。

- 同じ LAN にある対局を、アドレス入力なしで見つけます
- 見つけた対局の参加者を確認してから、空席に座ります
- 二つのマシンから交互に着手し、同じ盤面を共有します
- 決着後に最終盤面を確認し、ロビーへ戻ります

先に CPU を追加したくなるかもしれません。しかし、ここでは先に対人戦を作ります。step 1 の
`Update` に「いま O の番ならボットに考えさせる」と書けば、ルールが操作者の種類を知ることに
なるためです。これは、framework が避けようとしている分岐そのものです。

そこで、まずは**もう一人を別のマシンから座らせます**。

## オンラインゲームのために構造を変える

step 1 の盤面は、`State` という**一つの状態**で表していました。メモリ上の `State` を、
`Update` が直接書き換えます。1台だけで完結する限り、これで十分でした。

ところが、2台目が同じ盤面を見るには、一つの状態だけでは足りません。step 2 では、状態を
**三つの役割に分けます**。

| 型 | 何を表すか | なぜ分かれるか |
|---|---|---|
| **World** | 権威ある世界そのもの | 通信量を抑えるには、前の版と比べて**変わった分だけ**送れる形が要る |
| **Action** | 1つの席が出す1つの決定 | 上りに流れるのはこれだけ。世界は上らない |
| **Sight** | 1つの席が見てよいものだけ | 席ごとに適切なロジックを動かすには、席ごとの見え方が要る |

`State` を `World` に変えたのは、単なる改名ではありません。`State` が担っていた役割を
減らしたためです。step 1 の `State` は、正しい状態、画面に出す状態、判断の材料という三つの
役割を兼ねていました。ネットワーク越しでは、それぞれが別の場所に異なる頻度で存在します。
そこで、名前と型も三つに分けます。

型引数にも、この三つを同じ順序で並べます。型の名前は `World` / `Action` / `Sight` でなくても
構いません。**型引数の位置が役割を決める**ため、各型にはゲームに合った名前を付けられます。

```go
eb.Options[msg.TTTWorld, msg.Move, game.Sight]{ ... }
```

盤面と着手はネットワークを通るため `msg` パッケージに置きます。視界はネットワークを通らないため、
`game` パッケージに置きます。

<Aside type="note" title="三目並べに Sight が要るのか">
三目並べでは盤面がすべて見えるため、`Sight` の中身は `World` とほとんど同じです。それでも
**別の型**にするのは、隠し情報を持つゲームでも `Project` だけを変えれば済むようにするためです。
手札や戦場の霧があっても、変わるのは `Project` の1メソッドだけです。セッションのループは、
視界の中身を知りません。
</Aside>

## `ebiten.RunGame` との差分

step 1 では、Ebitengine の `Game` を一つ書き、`ebiten.RunGame` に渡していました。

```go
type Game struct{ /* 状態 */ }
func (g *Game) Update() error                    { /* 入力を読み、世界を進める */ }
func (g *Game) Draw(screen *ebiten.Image)        { /* 描く */ }
func (g *Game) Layout(w, h int) (int, int)       { /* 論理解像度 */ }

ebiten.RunGame(&Game{})
```

step 2 では `eb.Run` に変わりますが、内部では引き続き
**`ebiten.RunGameWithOptions` を呼びます**。`Engine *ebiten.RunGameOptions` はそのまま渡されるため、
エンジン側の設定は失われません。Ebitengine の要件に合わせて、メインの goroutine も渡します。

変わるのは、`Game` の位置と `Update` の役割です。

| Ebitengine | eb.Run |
|---|---|
| `Game` を1つ渡す | 画面（Screen）を渡り歩き、ロビーは最初から付いてくる |
| `Update` が入力も世界の前進も両方やる | **`Intake` と `Apply` に割れる** |
| `Draw` が描く | 同じ。何も決めない |
| `Layout` が論理解像度を決める | 同じ。そのまま呼ばれる |

### `Update` が2つに割れる

最も大きな違いは、処理を二つに分け、それぞれを**別の goroutine で動かす**ことです。

| | どこで | いつ |
|---|---|---|
| `Intake` | Ebitengine の goroutine | フレームごと |
| `Apply` | セッションの goroutine | tick ごと |

step 1 の `Update` は、入力を読み、世界を書き換えるところまでを一つの関数で行っていました。
つまり、フレームレートがそのままシミュレーションの速度になっていました。

step 2 では、**シミュレーションをフレームループから切り離します**。tick は専用の goroutine で
一定の速度で進み、描画はフレーム側のタイミングで行います。`Apply` が呼ばれるのは tick が
確定したときであり、Ebitengine のフレームループからは独立しています。

`Intake` に残るのは入力を渡す処理だけで、**世界を決める処理はありません**。

```go
func (v *view) Intake(controls run.Controls[msg.Move]) {
	for _, seat := range controls.LocalSeats() {
		// 不正なセルは上流のバリデータが弾くので、盤上ならどこでも送ってよい
		_ = controls.Submit(seat.Slot, msg.Move{Cell: cell})
	}
}
```

ここでは印を直接置きません。**Action を提出し、更新後の World が `Apply` に届くまで待ちます**。

`Submit` の送信先は、ホストなら1 goroutine 先の inbox、ゲストなら別のマシンのソケットです。
このコードだけを見ても、**どちらのインスタンスがルールを実行したかは分かりません**。

<Aside type="note" title="run.Controls">
`Intake` が受け取るのは `Match` 全体ではなく、**このマシンが操作する席と、Action の出し方**だけです。
画面から見たホストとゲストの違いは、`Submit` の送信先だけです。そのため、一つのプレイ画面を
ホストとゲストの両方で使えます。
</Aside>

<Aside type="caution" title="Apply は借りずに写す">
`Apply` は別の goroutine から呼ばれます。さらに、渡されたポインタの参照先は、セッションが
**書き換え続けます**。`Draw` で使う値は、`Apply` の中でコピーしなければなりません。
step 2 の `view.Apply` は、スライスも含めて深くコピーしています。
</Aside>

### 画面が入れ替わる

Ebitengine では、`ebiten.RunGame` に渡した `Game` の内部で表示する画面を切り替えます。
`eb.Run` はこの切り替えを引き受け、**最初からロビーを提供します**。

`Client` として渡すのは、**プレイ画面一つだけ**です。ロビー、対局結果、接続先を表示する画面は、
framework 側にあります。独自の集合画面が必要なら、`Screen` を渡して差し替えられます。

## ゲームのライフサイクルが変わる

step 1 では、起動するとすぐに対局が始まりました。プレイヤーが最初から2人そろっている前提だった
ためです。相手が別のマシンにいる場合は、起動時に参加者を確定できません。プレイヤーは
**起動してから集まります**。

そこで、Stage の前に二つの階層を追加します。

| 階層 | 何が起きるか |
|---|---|
| **Matchmaking** | 誰がいるか探し、部屋を開くか入るかを決め、席を取る |
| **Match** | 席が埋まってから終わるまで。ロスターとリンクを持つ |
| **Stage** | その中で実際に遊ぶルールセット1つ |

step 1 にあったのは Stage だけでした。一つしかなかったため、名前を付ける必要もありませんでした。

ゲームのルールは、**Stage 側の `StageRuleSet` に実装します**。step 1 の `Legal` はそのまま残し、
周囲に `StageRuleSet` のメソッドを追加します。

```go
type RuleSet struct{}

func (RuleSet) Start(uint64) World { ... }
func (RuleSet) ActingSlots(w *World) []session.SlotID { ... }
func (RuleSet) Apply(w *World, slot session.SlotID, a Action) { ... }
func (RuleSet) Advance(*World) {}
func (g RuleSet) Project(w *World, slot session.SlotID) Sight { ... }
func (RuleSet) Evaluate(w *World, slot session.SlotID) session.EvaluationSignal { ... }
```

引数には、先ほど分けた三つの型が現れます。`Apply` は Action を World に適用し、`Project` は
World から Sight を作ります。ゲームのルールは、**この6メソッドに収まります**。
Matchmaking と Match は、ルールの中身を一切知りません。

`Advance` が空なのは、実装漏れではありません。リアルタイムループは、すべてのゲームに毎 tick の
前進を求めます。しかし、三目並べの**盤面は着手したときにしか動きません**。ターン制ゲームが
「この tick では何も起きない」と答えられるため、同じループ、記録、リンクをボードゲームと
シューターの両方で使えます。

<Aside type="note" title="物理・投影・検証とは">

- **物理** — 位置、速度、衝突などを計算し、World を tick ごとに進める処理です。三目並べでは
  動き続けるものがないため、`Advance` は空です。リアルタイムゲームに組み込む方法は
  [Ebitengine への統合](/integration/ebitengine/)で扱います。
- **投影** — World から、その席に見せてよい Sight を作る処理です。このゲームでは `Project` が
  担い、隠し情報を持つゲームでの考え方は[視界と可視性](/integration/sight/)で詳しく扱います。
- **検証** — 提出された Action が合法かを確かめ、問題がなければ `Apply` へ渡す処理です。
  `Project` と `Apply` を含む呼び出し順は[接点は4つしかない](/integration/#呼ばれる順番)で整理します。

</Aside>

この三つの型引数には、コンパイル時の検査以外にも役割があります。

```go
var _ session.TickStageRuleSet[msg.TTTWorld, msg.Move, Sight] = RuleSet{}
```

`ebigent build` はこの1行を読み、**World と Action を運ぶコードを生成します**。World には、
毎 tick 盤面全体を送らずに済むように差分コーデックを生成します。Action は1回だけ送る Message なので、
全体を送ります。運ぶ型を別の場所で重ねて指定する必要はありません。

<Aside type="caution" title="運べる型には制限がある">
`msg.TTTWorld` の `Cells` は `[]uint8` で、`game.Sight` の `Cells` は `[]Mark` です。同じ9マスを
表しますが、World だけがネットワークを通るため、型が異なります。

生成器は、他パッケージの名前付き型（`session.Tick`、`fixmath.F64`）や、名前付き要素の
コレクション（`[]Mark`）を運べません。また、**運べるフィールドだけを選んで生成することもありません**。
一部のフィールドが欠けたまま送信する方が危険なため、型全体のコーデックを生成対象から外します。
除外した型は `ebigent generate` の出力に表示されますが、ビルド自体は成功します。

視界はネットワークを通らないため、`[]Mark` のまま使えます。固定小数点を使うゲームでは、
World に生の `int64` を置き、物理計算の入口と出口で `fixmath.FromRaw` / `.Raw()` を使います。
</Aside>

<Aside type="note" title="Stage が別の階層である理由">
このゲームには Stage が一つしかないため、Match と Stage の違いはまだ表れません。
違いが必要になるのは、**本編のあとにボーナスステージ**を追加するときです。ルール、World の型、
送るデータが変わっても、席とリンクは維持できます。同じ相手と、別のルールで続けて遊べます。
</Aside>

## 生成器にプロジェクトを教える

この1行は宣言であり、実行する命令ではありません。`msg` に codec を追加するには、生成器が
宣言を読んでコードを書く必要があります。その役割を担うのが `ebigent generate` です。

ただし、生成器はどのディレクトリが一つのゲームに当たるのかを知りません。モジュールパス、席数、
各席を操作できる主体も、ソースコードからは決まりません。これらを一か所にまとめるのが
`ebigent.toml` で、`ebigent init` が生成します。

ツールは、リポジトリのルートで一度インストールします。

```bash
go install ./cmd/ebigent
```

`init` はステップのディレクトリで実行します。`ebigent.toml` は現在のディレクトリから上へ
探すため、実行する場所によって対象が変わります。

```bash
cd tutorial/step2-lobby && ebigent init
```

step 2 のディレクトリには、実際に `init` を実行した結果が入っています。ここには `go.mod` が
あるため、**`init` はゲーム本体を生成しません**。すでにモジュールパスと実行用のエントリポイントが
あるからです。framework 用のファイルだけを追加し、既存のコードには触れません。

```
ebigent.toml           プロトコルと build target の宣言
corpus/                エピソード（一局分の記録）を集めるコーパス。step 3 で使う
behavior/chips.json    チップ（条件と、そのとき取る行動を組み合わせた規則）の一覧。step 4 で使う
cmd/distill/main.go    ebigent distill が go run するエントリ
.claude/skills/        コーパスを読むための解析スキル
```

**エピソード**は一局分の記録、**コーパス**は複数のエピソードを集めた分析対象です。step 3 で
対局の記録を始めると、この二つが実際のファイルとして現れます。**チップ**は、その記録から step 4 で
作るボット用の小さな規則です。`init` の時点では、どの置き場も空です。

エントリポイントは import グラフから読み取ります。この step のウィンドウは `main.go` 一つなので、
`entry = "."` の client として登録されます。`game/` と `msg/` は、その下にある通常の
パッケージとして扱われます。

`init` が推測した値のうち、このリポジトリでは二か所を修正しています。`realtime` は、プレイ人数が
duo であることから `twitch` と推測されました。しかし、このゲームは着手を待てるため、
`turn_based` に直します。また、`cmd/distill` の生成先は慣例に従って `game.Action` になりましたが、
このゲームの着手は `msg.Move` です。**推測値は出発点であり、確認が必要です**。

`[protocol]` はゲーム全体の契約であり、**起動時には読みません**。接続する二つのビルドで、
値が異なってよい項目はないためです。`ebigent generate` が Go の定数へ変換し、ビルドに含めます。

```bash
cd tutorial/step2-lobby && ebigent generate
```

実行すると、`msg/` に四つの生成物が加わり、`internal/ebigentgen/protocol_gen.go` も生成されます。
後者は `[protocol]` を Go に変換したものです。この段階では、ゲームのコード自体はまだ解析しません。

<Aside type="note" title="init は使わないものまで置いていく">
コーパスの置き場とチップライブラリは、step 2 では使いません。それでも `init` が用意するのは、
**過去の対局をあとから遡って記録することはできない**ためです
(`decision:ai-pipeline-always-scaffolded`)。記録を始める前に、保存先を用意しておく必要があります。
</Aside>

## ロビーにルールを渡す

必要な宣言はこれでそろいました。ゲームは **`Binding`** を通して、ルールを framework に渡します。
`Binding` が持つのは、席の一覧、1試合分のセッションの組み立て方、空席の埋め方です。物理、投影、
検証は、すでにセッション設定に含まれています。

```go
// tutorial/step2-lobby/game/bind.go — ルールの隣
func Binding() run.Binding[World, Action, Sight] {
	return run.Binding[World, Action, Sight]{
		Slots:             Slots(),
		Config:            Config,
		ProtocolVersion:   Protocol,
		EvaluationVersion: Evaluation,
	}
}
```

`Protocol` は、生成されたスキーマの指紋です。**送るバイト列が一つでも変わると値も変わる**ため、
異なる版の相手は着席前に拒否されます。人がバージョン番号を更新する必要はありません。

```go
// tutorial/step2-lobby/main.go — ウィンドウの隣
func matchmaking() run.Matchmaking[msg.TTTWorld, msg.Move, game.Sight] {
	return lan.Preset(lan.Options[...]{ /* codec と入出力 */ })
}
```

`Matchmaking` は `Discover` / `Host` / `Match` の三つに分かれています。プレイヤーが、
**見つかった相手を確認してから参加先を選べる**ようにするためです。一つの呼び出しにまとめると、
最初に応答した相手の試合へ自動的に参加することになります。

`Match` は、参加しただけでは席を取りません。部屋に入り、ロスターを確認してから `Sit` します。
この順序なら、**入って、見て、参加をやめる**こともできます。ホストは条件を提示して部屋を開きますが、
到着した人を一人ずつ審査する役割は持ちません。

ネットワークの宣言は、**ルールの隣ではなくエントリポイントに置きます**。利用できるトランスポートは、
ゲームの内容ではなく、ビルドを実行する環境によって決まるためです。LAN プリセットには待ち受け
ソケットと UDP ブロードキャストが必要なので、ブラウザでは動きません。一方、`game/` と `msg/` は
すべてのターゲットでビルドできます。同じルールをブラウザで動かす場合は、別の経路を指定します。

ここには **`NewAgent` がありません**。空席はボット用ではなく、**まだ起動していない人の席**だからです。
ロビーは `NoBots: true` でこの条件を宣言し、最後の席が埋まると対局を始めます。開始ボタンを押す
操作は必要ありません。

## 「繋がる Agent」とは何か

「リモートの Agent が着席する」と聞くと、Agent 自体がネットワークを通るように思えるかもしれません。
しかし、**Agent がネットワークを通ってホストへ移動するわけではありません**。

ホスト側では、操作者が人である席に、ローカルかリモートかを問わず `session.Detached` が座ります。
これは何もしないスタブです。セッションは、代わりにその席の `Inbox` を読みます。したがって、
セッションから見た「人が入ってきた」とは、**Agent が到着することではなく、Inbox に入力が届き
始めること**です。実際に接続されるのは、admission が席に結び付けた通信路です。

実際の Agent はゲスト側にいます。状態が届くたびに `Observe` → `Decide` を呼び、返された行動を
ホストへ送ります。ホストは、入力元が人かボットかを知りません。そのため step 3 では、同じ席に
別の `Agent` を置くだけでボットを参加させられます。

## 順序という制約

ここで問題になるのは、ロビーとセッションが作られる順序です。

**ピアが着席するには、席に inbox が必要です**。inbox はセッションとともに作られますが、
参加者はロビーが募集中の段階で接続してきます。

そこで LAN プリセットは、**接続を先に受け付けて待機させ、試合開始時にセッションへ渡します**。
ゲストはハンドシェイクの途中で待つため、ポーリングは不要です。この待機状態がロビーになります。

また、**席の付与と接続処理は分かれています**。`Join` はチケットを受け取り、リンクを開いた時点で
戻ります。ハンドシェイクの完了は `Play` の中で待ちます。二つを分けないと、ホストが開始するまで
ゲストのウィンドウを表示できません。起動後に何も映らなければ、利用者には待機中ではなく、
壊れているように見えます。

## 実装したロビーを動かす

この構成でアプリを起動すると、一つ目のインスタンスはホストとして空席を残し、二つ目の
インスタンスはその対局を見つけます。設定ファイルとアドレス入力は必要ありません。

```bash
go run ./tutorial/step2-lobby
```

アプリを二つ起動します。別々のマシンでも、同じマシンで2回起動しても構いません。

<Steps>

1. 一つ目のターミナルでアプリを起動します。アプリは LAN に「参加できる対局はありますか」と
   問い合わせます

2. 最初に起動した側には誰も応えないため、**自分がホストとして着席し、待ちます**

3. 同じコマンドを、別のマシンか二つ目のターミナルで実行します。二つ目の画面には、
   **見つかったゲームの一覧が表示されます**

4. 一覧の `tictactoe` をクリックします。部屋の参加者と空席を確認し、もう一度クリックして
   二つ目の席に座ります

5. 二人目が着席すると、対局が始まります。一つ目のウィンドウで空いているマスをクリックし、
   二つ目のウィンドウにも同じ印が表示されることを確認します

6. 今度は二つ目のウィンドウで別のマスをクリックします。手番を交代しながら、どちらの画面にも
   同じ盤面が表示されることを確認します

</Steps>

![二つ目のインスタンスがLAN上のtictactoe対局を発見したロビー画面](/images/tutorial/step2-lobby-discovery.jpg)

*二つ目のインスタンスには、先に起動した対局と現在の着席人数が表示されます。参加先を自分で選んでから席に着きます。*

![別々のインスタンスから着手したXとOが同じ盤面に反映された画面](/images/tutorial/step2-two-player-board.jpg)

*XとOは別々のインスタンスから送っています。片方が着手すると、もう片方にも同じ盤面が届き、手番表示が切り替わります。*

プレイヤーから見ると、step 1 と同じ三目並べです。変わったのは、同じマウスを交互に渡す代わりに、
各プレイヤーが自分のマシンから一つの席を操作できることです。どちらでクリックしても、ホストが
確定した一つの World が両方へ届きます。これが、このステップで完成する対人戦です。

ホスト側に確認ボタンがないのは意図的です。誰もおらず、自分の席しか空いていない状況では、
選択肢が一つしかありません。確認が必要なのは、参加する側が「この人のゲームに入るか」を
選ぶときです。

対局が終わると、**最終盤面がそのまま残ります**。クリックするとロビーに戻ります。終了と同時に
画面を切り替えず、どのように決着したかを確認できるようにしています。

## 確かめ方

ウィンドウを開かずに一連の動作を検証するテストがあります。

- `TestTwoInstancesPlayOneBoard` — ホストが集め、ゲストが実 WebSocket で空席に着き、**両方の席が実際に指し**、ゲストはルールを一度も走らせずに同じ最終盤面に到達する
- `TestPresetDiscoversThenJoins` — 誰もいなければ発見は空で、ホストが立った後は1件だけ見え、参加は人が選んでから起きる
- `TestRebindMovesTheOfferToTheNextMatch` — roster は1試合のもの。次の試合の roster に付け替えないと、到着した人がどこにも座らない
- `TestCodecRoundTripsTheBoard` — snapshot と delta の両方が盤面を復元する
- `TestSightCarriesTheLegalMoves` — 手番でない席の合法手は空

<FileTree>
- tutorial/step2-lobby/
  - go.mod このステップ自身のモジュール
  - ebigent.toml ebigent init が書いた宣言
  - main.go ウィンドウ・入力・描画・ネットワークの宣言
  - game/
    - game.go ルール。session.StageRuleSet の実装
    - bind.go Options / Binding の宣言
    - net_test.go 2インスタンスの通し
    - boundary_test.go engine が game/ に届いていないことの検査
  - msg/
    - types.go World と Action の型
    - wire_gen.go / tinybind_gen.go / delta_gen.go / schema_gen.go すべて生成物
  - internal/ebigentgen/ [protocol] が Go の定数になったもの
  - corpus/ まだ空のコーパス。step 3 でエピソードを記録する
  - behavior/ まだ空のチップライブラリ。step 4 で規則を追加する
</FileTree>

各ステップは、**独立したモジュール**になっています。`ebigent init` は `go.mod` を基に対象を
判断するため、読者が実行するものと同じ構成で検証するには、ステップごとに `go.mod` が必要です。
`replace` は現在のチェックアウトを指しているので、リリース版ではなく手元の framework を試せます。

## まだないもの

**対戦相手が来ないときに選べるボットは、まだありません**。`Binding.NewAgent` は意図的に空です。
空席は、まだ起動していない人の席として扱っています。しかし、待っているプレイヤーがボットとの
対戦に切り替える選択肢はあってもよいはずです。step 3 で、この選択肢を追加します。

**対局の記録も、まだ取りません**。一局指しても、終了すると結果は残りません。保存先は `init` が
すでに作っています。`eb.Options.Record` にその場所を指定すると、対局はあとから読み返せる
記録の集まり、つまり**コーパス**になります。step 3 では、ここから記録を始めます。

**コードは、生成済みの設定値をまだ使っていません**。`internal/ebigentgen` には席数と同期モードが
定数としてありますが、`game/` は席数を自分で数えています。同じ値を二重に書くと、いずれ
食い違います。ただし、この重複の解消はこのステップでは扱いません。
