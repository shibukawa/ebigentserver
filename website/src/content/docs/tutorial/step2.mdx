step 1 の三目並べに CPU を足そうとすると、`Update` の中に「いま O の番ならボットに考えさせる」と
書きたくなる。その1行が、この framework が最初に禁じた分岐そのものになる。

なのでその前に、**もう一人を別のマシンから座らせる**。

```bash
go run ./tutorial/step2-lobby
```

2つ起動する。別のマシンでも、同じマシンで2回でも構わない。設定はなく、アドレスも打たない。

<Steps>

1. どちらもまずネットワークに「誰かいますか」と聞く

2. 最初に起動した方は誰も応えないので、**自分がホストになって着席し、待つ**

3. 次の方には**見つかったゲームの一覧が出る**。クリックで選んで参加する

4. 二人目が着席した瞬間に対局が始まる

</Steps>

ホスト側で押す操作がないのは意図的だ。**選択肢が1つしかない問いを出しても仕方がない**——
そこには他に誰もおらず、空いているのは自分の席だけになる。押す操作は、二択がある方の判断、
つまり「この人のゲームに入るか」に取ってある。

対局が終わったら**最終盤面がそのまま残る**。クリックするとロビーに戻る。終わった瞬間に
画面を取り上げると、どう終わったのかを見る機会がなくなるからだ。

## オンラインゲームのために構造を変える

step 1 の盤面は `State` という**1つの状態**だった。それをメモリに置いて、`Update` が直接
書き換える。1台で完結する限り、これで足りていた。

2台目が同じ盤面を見た瞬間に、1つでは足りなくなる。step 2 は状態を**3つに分ける**。

| 型 | 何を表すか | なぜ分かれるか |
|---|---|---|
| **World** | 権威ある世界そのもの | 通信量を抑えるには、前の版と比べて**変わった分だけ**送れる形が要る |
| **Action** | 1つの席が出す1つの決定 | 上りに流れるのはこれだけ。世界は上らない |
| **Sight** | 1つの席が見てよいものだけ | 席ごとに適切なロジックを動かすには、席ごとの見え方が要る |

`State` が `World` になったのは改名ではない。**役割が減った**からだ。step 1 の `State` は
「全部」だった——真実であり、画面に出すものであり、判断の材料でもあった。ネットワーク越しでは
その3つが別々の場所に、別々の頻度で存在する。だから名前も3つに分かれる。

型引数もそのまま3つ並ぶ。名前は `World` / `Action` / `Sight` でなくてよい——
**型引数の位置が役割を決める**ので、型そのものはゲームの言葉で名乗れる。

```go
eb.Options[msg.TTTWorld, msg.Move, game.Sight]{ ... }
```

盤面と着手は線を渡るので `msg` パッケージに、視界は渡らないので `game` に置いてある。

<Aside type="note" title="三目並べに Sight が要るのか">
盤面が全部見えるゲームなので、`Sight` の中身は `World` とほとんど同じになる。それでも
**別の型**にしてあるのは、隠し情報を持つゲームがここだけを変えれば済むようにするためだ。
手札も、視界も、戦場の霧も、変わるのは `Project` の1メソッドで、セッションのループは
何も知らない。
</Aside>

## `ebiten.RunGame` との差分

step 1 は Ebitengine そのものだった。`Game` を1つ書いて渡す。

```go
type Game struct{ /* 状態 */ }
func (g *Game) Update() error                    { /* 入力を読み、世界を進める */ }
func (g *Game) Draw(screen *ebiten.Image)        { /* 描く */ }
func (g *Game) Layout(w, h int) (int, int)       { /* 論理解像度 */ }

ebiten.RunGame(&Game{})
```

step 2 は `eb.Run` に変わるが、**`ebiten.RunGameWithOptions` は中で呼ばれている**。
`Engine *ebiten.RunGameOptions` はそのまま素通しされるので、エンジン側の設定は何も失わない。
メインの goroutine も Ebitengine に渡される——あちらがそれを要求するからだ。

変わるのは `Game` の位置と、`Update` の中身になる。

| Ebitengine | eb.Run |
|---|---|
| `Game` を1つ渡す | 画面（Screen）を渡り歩き、ロビーは最初から付いてくる |
| `Update` が入力も世界の前進も両方やる | **`Intake` と `Apply` に割れる** |
| `Draw` が描く | 同じ。何も決めない |
| `Layout` が論理解像度を決める | 同じ。そのまま呼ばれる |

### `Update` が2つに割れる

これが一番大きい差分で、しかも**動く goroutine が違う**。

| | どこで | いつ |
|---|---|---|
| `Intake` | Ebitengine の goroutine | フレームごと |
| `Apply` | セッションの goroutine | tick ごと |

step 1 の `Update` は「入力を読んで世界を書き換える」を1つの関数の中でやっていた。
フレームレートがそのままシミュレーションの速度だった、とも言える。

step 2 では**シミュレーションがフレームループから外れる**。tick は自分の goroutine で自分の
速度で回り、フレームは描きたいときに描く。`Apply` が呼ばれるのは tick が確定した瞬間で、
そこはもう Ebitengine の世界ではない。

残った `Intake` の側は、**決める仕事が抜けた**姿になる。

```go
func (v *view) Intake(controls run.Controls[msg.Move]) {
	for _, seat := range controls.LocalSeats() {
		// 不正なセルは上流のバリデータが弾くので、盤上ならどこでも送ってよい
		_ = controls.Submit(seat.Slot, msg.Move{Cell: cell})
	}
}
```

印を置くのではなく、**Action を提出して、World がどうなったかを `Apply` で教えてもらうまで待つ**。

`Submit` の行き先は、ホストなら1 goroutine 先の inbox、ゲストなら1マシン先のソケットだ。
**どちらのインスタンスが実際にルールを走らせたのかは、このファイルからは見えない。**

<Aside type="note" title="run.Controls">
`Intake` が受け取るのは `Match` ではなく、**このマシンが操作する席と、その出し方**だけだ。
1つのプレイ画面がホストとゲストの両方を務められるのは、画面の側から見た差が
「`Submit` の行き先」しかないからである。
</Aside>

<Aside type="caution" title="Apply は借りずに写す">
`Apply` は別の goroutine から呼ばれ、しかも渡されたポインタの先はセッションが**書き換え続ける**。
`Draw` が読むものは、`Apply` の中で写しておかなければならない。step 2 の `view.Apply` が
スライスまで深くコピーしているのはこのためだ。
</Aside>

### 画面が入れ替わる

`ebiten.RunGame` に渡す `Game` を差し替えて画面を切り替えるのは、Ebitengine のゲームが
もともとやっているやり方だ。`eb.Run` はそれを引き受けて、**ロビーを最初から持っている**。

`Client` として渡すのは**プレイ画面1つだけ**でよく、ロビーも、対局結果の画面も、
リンクの向こうを描く画面も、フレームワーク側にある。自前の集合画面を出したければ
`Screen` を渡して差し替えられる。

## ゲームのライフサイクルが変わる

step 1 は起動したら即プレイだった。プレイヤーは最初から2人そろっていて、そう決まっていた
からだ。相手が別のマシンにいる瞬間、それは決めておけない——**起動してから集まる**。

だから間に階層が2つ入る。

| 階層 | 何が起きるか |
|---|---|
| **Matchmaking** | 誰がいるか探し、部屋を開くか入るかを決め、席を取る |
| **Match** | 席が埋まってから終わるまで。ロスターとリンクを持つ |
| **Stage** | その中で実際に遊ぶルールセット1つ |

step 1 にあったのは Stage だけで、しかも名前が要らなかった。1つしかないものに名前は要らない。

そして**ゲームのロジックは Stage の側に入っていく**。step 1 の約束どおり `Legal` はそのまま
残り、その周りに `StageRuleSet` のメソッドが5つ増えただけだ。

```go
type RuleSet struct{}

func (RuleSet) Start(uint64) World { ... }
func (RuleSet) ActingSlots(w *World) []session.SlotID { ... }
func (RuleSet) Apply(w *World, slot session.SlotID, a Action) { ... }
func (RuleSet) Advance(*World) {}
func (g RuleSet) Project(w *World, slot session.SlotID) Sight { ... }
func (RuleSet) Evaluate(w *World, slot session.SlotID) session.EvaluationSignal { ... }
```

引数を見ると、さっきの3つがそのまま出てくる。`Apply` は Action を World に適用し、`Project` は
World から Sight を作る。**この6メソッドがゲームの全部**で、Matchmaking も Match も
1行も知らない。

`Advance` が空なのは手抜きではない。リアルタイムループは全てのゲームに毎 tick の前進を尋ねるが、
**盤面は着手でしか動かない**。ターン制が「何も起きていない」と答えるのは欠落ではなく、
同じループ・同じ記録・同じリンクがボードゲームにもシューターにも使える理由になっている。

そしてこの型引数3つは、コンパイラにルールを検査させるためだけのものではない。

```go
var _ session.TickStageRuleSet[msg.TTTWorld, msg.Move, Sight] = RuleSet{}
```

`ebigent build` はこの1行を読んで、**World と Action を運ぶコードを生成する**。
World は差分つき——毎 tick 盤面をまるごと送らないため——で、Action は1回きりのメッセージ
なので全体だけ。どの型を送るかを別の場所にもう一度書く必要はない。

<Aside type="note" title="Stage が別の階層である理由">
このゲームには Stage が1つしかないので、Match と Stage の区別は今は効いてこない。効くのは
**本編のあとにボーナスステージ**を足したときだ。ルールも、World の型も、送るデータも変わるが、
席とリンクはそのまま——同じ相手と、違うルールで、続けて遊べる。
</Aside>

## 相手が来るのを待つ

宣言はこれで全部だ。

```go
// tutorial/step2-lobby/game/bind.go — ルールの隣
func Binding() run.Binding[World, Action, Sight] {
	return run.Binding[World, Action, Sight]{
		Slots:             Slots(),
		Config:            Config,
		ProtocolVersion:   Protocol,
		EvaluationVersion: Evaluation,
	}
}
```

`Protocol` は生成されたスキーマ指紋そのものだ。**送るバイト列が1つでも変われば版も変わる**ので、
版の違う相手は席をもらう前に断られる。手で上げ忘れることがない。

```go
// tutorial/step2-lobby/main.go — ウィンドウの隣
func matchmaking() run.Matchmaking[msg.TTTWorld, msg.Move, game.Sight] {
	return lan.Preset(lan.Options[...]{ /* codec と入出力 */ })
}
```

`Matchmaking` が `Discover` / `Host` / `Match` の3つに分かれているのは、**プレイヤーには
誰がいるかを見て決める権利がある**からだ。1つの呼び出しで済ませると、最初に応えた相手の
試合に放り込むことになる。

そして `Match` は席を取らない。部屋に入ってロスターを読み、それから `Sit` する——
**入って、見て、やめる**が成立するように分けてある。ホストは条件を出して部屋を開くだけで、
到着した人を1人ずつ審査したりはしない。

ネットワークの宣言が**ルールの隣ではなくエントリポイントにある**のは意図的だ。どのトランスポートで
相手に届くかは、そのビルドがどこで走るかの性質であって、ゲームが何であるかの性質ではない。
LAN プリセットは待ち受けソケットと UDP ブロードキャストを要るのでブラウザでは動かないが、
`game/` と `msg/` は全ターゲットでビルドできる——同じルールのブラウザ版は別の経路を名指すことになる。

**`NewAgent` がない。** 空席はボットの席ではなく、**まだ起動していない人の席**だからだ。
ロビーは `NoBots: true` でそれを宣言し、最後の席が埋まった瞬間に対局を始める——
誰かが画面を見ていて押す必要はない。

## 「繋がる Agent」とは何か

ここが分かりにくいところなので、はっきりさせておく。**Agent が回線を渡ってくるわけではない。**

ホスト側では、操作者が人である席には——ローカルでもリモートでも——`session.Detached` が座る。
何もしないスタブで、セッションは代わりにその席の `Inbox` を読む。つまりセッションから見た
「人が入ってきた」は、**Agent の到着ではなく Inbox に入力が届き始めること**だ。実際に繋がるのは
admission が席に束ねた接続になる。

本物の Agent はゲスト側にいる。状態が届くたびに `Observe` → `Decide` が呼ばれ、返った行動が
上流に送られる。**ホストはどちらか知らない**——だから step 3 でボットを座らせるのは、
同じ席に別の `Agent` を置くだけの話になる。

## 順序という制約

このステップで一番読み応えがあるのは、実は framework 側の制約だ。

**ピアは席に inbox があって初めて着席できる。** つまりセッションが存在してからだ。ところが
人はロビーが集めている最中に来る。

なので LAN プリセットは、**接続を早期に受けて駐機させ、試合開始と同時に流し込む**。
ゲストはハンドシェイクの中で待つので、ポーリングは要らない。待っている状態がそのままロビーになる。

そして**席の付与と接続は分けてある**。`Join` はチケットをもらってリンクを開いた時点で戻り、
ハンドシェイクは `Play` の中で待つ。分けていないと、ホストが開始するまでゲストのウィンドウが
出てこない——起動したのに何も映らない画面は、待っているのではなく壊れて見える。

## 確かめ方

ウィンドウなしで全体が通ることをテストが固定している。

- `TestTwoInstancesPlayOneBoard` — ホストが集め、ゲストが実 WebSocket で空席に着き、**両方の席が実際に指し**、ゲストはルールを一度も走らせずに同じ最終盤面に到達する
- `TestPresetDiscoversThenJoins` — 誰もいなければ発見は空で、ホストが立った後は1件だけ見え、参加は人が選んでから起きる
- `TestRebindMovesTheOfferToTheNextMatch` — roster は1試合のもの。次の試合の roster に付け替えないと、到着した人がどこにも座らない
- `TestCodecRoundTripsTheBoard` — snapshot と delta の両方が盤面を復元する
- `TestSightCarriesTheLegalMoves` — 手番でない席の合法手は空
