import { Aside, FileTree, Steps, LinkCard } from '@astrojs/starlight/components';

step 1 の三目並べに CPU を足そうとすると、`Update` の中に「いま O の番ならボットに考えさせる」と
書きたくなる。その1行が、この framework が最初に禁じた分岐そのものになる。

なのでその前に、**もう一人を別のマシンから座らせる**。

```bash
go run ./tutorial/step2-lobby
```

2つ起動する。別のマシンでも、同じマシンで2回でも構わない。設定はなく、アドレスも打たない。

<Steps>

1. どちらもまずネットワークに「誰かいますか」と聞く

2. 最初に起動した方は誰も応えないので、**自分がホストになって着席し、待つ**

3. 次の方には**見つかったゲームの一覧が出る**。クリックで選んで参加する

4. 二人目が着席した瞬間に対局が始まる

</Steps>

ホスト側で押す操作がないのは意図的だ。**選択肢が1つしかない問いを出しても仕方がない**——
そこには他に誰もおらず、空いているのは自分の席だけになる。押す操作は、二択がある方の判断、
つまり「この人のゲームに入るか」に取ってある。

対局が終わったら**最終盤面がそのまま残る**。クリックするとロビーに戻る。終わった瞬間に
画面を取り上げると、どう終わったのかを見る機会がなくなるからだ。

## `Update` が何も決めなくなる

描画はほぼ step 1 のままだ。変わったのはここになる。

```go
func (v *view) Intake(seating run.Seating[game.Action]) {
	for _, seat := range seating.LocalSeats() {
		// 不正なセルは上流のバリデータが弾くので、盤上ならどこでも送ってよい
		_ = seating.Submit(seat.Slot, game.Action{Cell: cell})
	}
}
```

step 1 の `Update` は盤面に印を置いていた。こちらは行動を提出して、盤面がどうなったかを
教えてもらうまで待つ。

そして `Submit` の行き先は、ホストなら1 goroutine 先の inbox、ゲストなら1マシン先のソケットだ。
**どちらのインスタンスが実際にルールを走らせたのかは、このファイルからは見えない。**

<Aside type="note" title="run.Seating">
`Intake` が受け取るのは `Match` ではなく席の抽象で、ローカルの試合もリンクも同じように満たす。
1つの再生シーンがホストとゲストの両方を務められるのは、シーンの側から見た差が
「`Submit` の行き先」しかないからだ。
</Aside>

## ルールは移らず、メソッドが増える

step 1 の約束どおり、`Legal` はそのまま残った。その周りに5つ増えただけだ。

```go
type Simulation struct{}

func (Simulation) Start(uint64) State { ... }
func (Simulation) ActingSlots(s *State) []session.SlotID { ... }
func (Simulation) Apply(s *State, slot session.SlotID, a Action) { ... }
func (Simulation) Advance(*State) {}
func (g Simulation) Project(s *State, slot session.SlotID) Observation { ... }
func (Simulation) Evaluate(s *State, slot session.SlotID) session.EvaluationSignal { ... }
```

`Advance` が空なのは手抜きではない。リアルタイムループは全てのゲームに毎 tick の前進を尋ねるが、
**盤面は着手でしか動かない**。ターン制が「何も起きていない」と答えるのは欠落ではなく、
同じループ・同じ記録・同じリンクがボードゲームにもシューターにも使える理由になっている。

## 盤面にワイヤ形式ができる

step 1 は盤面をただの Go 配列に持っていて、それがどう運ばれるかを言う必要がなかった。
2台目が同じ盤を見る以上、**バイト列の形は2つのビルドの間の契約**になる。

```go
// tutorial/step2-lobby/msg/types.go
type TTTState struct {
	Cells  []uint8 `json:"cells"`
	Turn   uint16  `json:"turn"`
	Winner uint16  `json:"winner"`
	Line   []uint8 `json:"line"`
	Moves  uint8   `json:"moves"`
	Over   bool    `json:"over"`
}

// この2つの呼び出しがコーデックの依頼そのものになる。
func AppendTTTState(dst []byte, v TTTState) []byte { return cborbind.AppendCBORInMapTo(dst, v) }
func DecodeTTTState(data []byte) (TTTState, error) { return cborbind.DecodeCBORInMapFrom[TTTState](data) }
```

宣言を書く場所は無く、**エントリポイントを呼ぶことが依頼**になる。そして呼んだ名前が
形を決める。

| | 配列 | マップ |
|---|---|---|
| ワイヤ上 | 位置決め、メンバ名を載せない | キー付き |
| 知らないメンバ | 存在しえない | デコード時に読み飛ばす |
| フィールド追加 | 両端を同時に作り直す | 古いビルドが読み続けられる |

着手（`Move`）は配列だ。小さく、両端が一緒に更新される。盤面はマップで、だから
**片方だけ先に出荷できる**。

```bash
go generate ./tutorial/step2-lobby/msg/   # コーデック
ebigent generate                          # 差分とスキーマ版
```

2つ目が要るのは、コーデックを生成するライブラリが**差分を生成しないから**だ。
2つの盤面の diff、それを戻す patch、変わった分だけを運ぶエンコード——
これはフレームワーク側の仕事になっている。マップ形式を要求した型が world state だと
分かるので、どの型に差分が要るかは設定せずに済む。

生成された `SchemaVersion` がそのままハンドシェイクの版になるので、
**ワイヤが1バイト動けば版も動く**。版の違う相手は席をもらう前に断られる。

<Aside type="caution" title="スライスを持つ状態の罠">
盤面がスライスになったので、`Codec.Clone` は深いコピーでなければならない。値コピーだと
保持された全ての baseline が最新の盤面を指してしまい、差分が常に空になる。
これはテストで固定してある（`TestCloneDoesNotAliasTheBoard`）。
</Aside>

## 相手が来るのを待つ

宣言はこれで全部だ。

```go
// tutorial/step2-lobby/game/bind.go — ルールの隣
func Binding() run.Binding[State, Action, Observation] {
	return run.Binding[State, Action, Observation]{
		Slots:             Slots(),
		Config:            Config,
		ProtocolVersion:   Protocol,
		EvaluationVersion: Evaluation,
	}
}
```

```go
// tutorial/step2-lobby/main.go — ウィンドウの隣
func network() run.Networking[game.State, game.Action, game.Observation] {
	return lan.Preset(lan.Options[...]{ /* codec と入出力 */ })
}
```

`Networking` が `Discover` / `Host` / `Join` の3つに分かれているのは、**プレイヤーには
誰がいるかを見て決める権利がある**からだ。1つの呼び出しで済ませると、最初に応えた相手の
試合に放り込むことになる。

ネットワークの宣言が**ルールの隣ではなくエントリポイントにある**のは意図的だ。どのトランスポートで
相手に届くかは、そのビルドがどこで走るかの性質であって、ゲームが何であるかの性質ではない。
LAN プリセットは待ち受けソケットと UDP ブロードキャストを要るのでブラウザでは動かないが、
`game/` と `msg/` は全ターゲットでビルドできる——同じルールのブラウザ版は別の経路を名指すことになる。

**`NewAgent` がない。** 空席はボットの席ではなく、**まだ起動していない人の席**だからだ。
ロビーは `NoBots: true` でそれを宣言し、最後の席が埋まった瞬間に対局を始める——
誰かが画面を見ていて押す必要はない。

## 「繋がる Agent」とは何か

ここが分かりにくいところなので、はっきりさせておく。**Agent がワイヤを渡ってくるわけではない。**

ホスト側では、操作者が人である席には——ローカルでもリモートでも——`session.Detached` が座る。
何もしないスタブで、セッションは代わりにその席の `Inbox` を読む。つまりセッションから見た
「人が入ってきた」は、**Agent の到着ではなく Inbox に入力が届き始めること**だ。実際に繋がるのは
admission が席に束ねた接続になる。

本物の Agent はゲスト側にいる。状態が届くたびに `Observe` → `Decide` が呼ばれ、返った行動が
上流に送られる。**ホストはどちらか知らない**——だから step 3 でボットを座らせるのは、
同じ席に別の `Agent` を置くだけの話になる。

## 順序という制約

このステップで一番読み応えがあるのは、実は framework 側の制約だ。

**ピアは席に inbox があって初めて着席できる。** つまりセッションが存在してからだ。ところが
人はロビーが集めている最中に来る。

なので LAN プリセットは、**接続を早期に受けて駐機させ、試合開始と同時に流し込む**。
ゲストはハンドシェイクの中で待つので、ポーリングは要らない。待っている状態がそのままロビーになる。

そして**席の付与と接続は分けてある**。`Join` はチケットをもらってリンクを開いた時点で戻り、
ハンドシェイクは `Play` の中で待つ。分けていないと、ホストが開始するまでゲストのウィンドウが
出てこない——起動したのに何も映らない画面は、待っているのではなく壊れて見える。

## 確かめ方

ウィンドウなしで全体が通ることをテストが固定している。

- `TestTwoInstancesPlayOneBoard` — ホストが集め、ゲストが実 WebSocket で空席に着き、**両方の席が実際に指し**、ゲストはルールを一度も走らせずに同じ最終盤面に到達する
- `TestPresetDiscoversThenJoins` — 誰もいなければ発見は空で、ホストが立った後は1件だけ見え、参加は人が選んでから起きる
- `TestRebindMovesTheOfferToTheNextMatch` — roster は1試合のもの。次の試合の roster に付け替えないと、到着した人がどこにも座らない
- `TestCodecRoundTripsTheBoard` — snapshot と delta の両方が盤面を復元する
- `TestObservationCarriesTheLegalMoves` — 手番でない席の合法手は空
