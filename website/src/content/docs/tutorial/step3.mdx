import { Aside, FileTree, Steps, LinkCard } from '@astrojs/starlight/components';

step 2 で、LAN 上の相手と対戦できるようになりました。ただし、相手が来なければ何も始まりません。
このステップでは、空席に座る **CPU** を作ります。`if` 4本の単純なアルゴリズムですが、
**人間の席と同じインターフェース**を実装します。

さらに、CPU の判断を人間の判断と同じ形式で記録できるようになります。CPU も framework の席に
座るため、専用の記録処理は必要ありません。対局するたびに、判断の記録が**コーパスへ蓄積されます**。

step 2 を一人で起動すると、ロビーは次の表示で止まります。

```
waiting for another player to join...
```

相手が来なければ対局は始まりません。また、誰かと一局指しても、対局が終わると記録は残りません。
step 2 には、待つ以外の選択肢と、対局を蓄積する仕組みがありませんでした。

step 3 では、この二つを同時に解消します。対局を記録するには、まず相手がいないときでも対局を
始められる必要があります。

## CPU も席に座る

CPU を追加するために、ゲームのループへ分岐を書く必要はありません。CPU は `session.Agent` として
実装します。これは、**人間の席にも使うインターフェース**です。

```go
type Agent[S, A any] interface {
	Joined(slot SlotID)
	Observe(obs S)
	Decide(ctx context.Context) (action A, ok bool)
	Ended(result Result)
}
```

人が座る席には、`session.Detached` という何もしないスタブが入ります。セッションは、代わりに
その席の Inbox を読みます。セッションから見ると、人間の席もボットの席も同じ `Agent` です。
そのため、ルールには操作者の種類を問い合わせる手段がありません
（`decision:no-ai-game-mode`）。

四つのメソッドのうち、**方策を実装するのは `Decide` だけ**です。残りの三つ、二つの型パラメータ、
`session.Agent` を満たすことを確認する宣言には、ゲーム固有の判断がありません。型パラメータは、
このファイルではなく[ルールセットの宣言](/tutorial/step2/#生成器にプロジェクトを教える)から
決まり、その一方は別のパッケージにあります。これらを間違えずに書くため、ひな型を生成します。

```bash
cd tutorial/step3-record && ebigent add agent tactic --type Bot --file bot.go
```

step 2 で作った `ebigent.toml` があるため、`add` は `var _ session.TickStageRuleSet[...]` を
読み、視界と行動の型を特定します。そして、`game/bot.go` に型、インターフェースを確認する宣言、
ファクトリ、四つのメソッドを生成します。

`agent` の後ろに渡すオプションは、対話形式で尋ねる質問の初期値です。`ebigent add agent` だけを
実行しても、三つの質問に答えれば同じ結果になります。最初の回答から型名を、型名からファイル名を
推測するため、二問目以降は多くの場合 Enter を押すだけです。名前には**方策の名前**を指定します。
ここでは、既存のゲームが使っている `Bot` という型名と `bot.go` というファイル名に合わせます。

生成器は、最後に `Binding` へ追加する次の行を表示します。

```
NewAgent: NewBot,
```

ひな型を生成すると、あとは `Decide` の中身を実装します。この CPU が実際に使うメソッドは、
四つのうち二つだけです。

```go
type Bot struct {
	sight Sight
}

// Observe は視界を持っておくだけ。判断は Decide でやる。
func (b *Bot) Observe(sight Sight) { b.sight = sight }
```

`Observe` では判断しません。セッションは、まず全席に視界を配り、そのあと手番の席に `Decide` を
呼びます。`Observe` で時間を使うと、手番ではない席の処理によっても tick が長くなります。

判断は `Decide` に実装します。

```go
func (b *Bot) Decide(context.Context) (msg.Move, bool) {
	s := b.sight

	// 手番でないか、対局が終わっている。視界がそう言っている。
	if len(s.Legal) == 0 {
		return msg.Move{}, false
	}
	// 1. 勝てるなら勝つ
	if cell, ok := completes(s.Cells, s.Mark); ok {
		return msg.Move{Cell: cell}, true
	}
	// 2. 負けるなら止める
	if cell, ok := completes(s.Cells, rival(s.Mark)); ok {
		return msg.Move{Cell: cell}, true
	}
	// 3. 中央 → 角 → 辺
	for _, cell := range preference {
		if slices.Contains(s.Legal, int(cell)) {
			return msg.Move{Cell: cell}, true
		}
	}
	return msg.Move{Cell: uint8(s.Legal[0])}, true
}
```

このボットは探索、内部状態、乱数を使いません。ただし、その単純さのために framework の機能を
制限しているわけではありません。

ここでは、三つの点を確認します。

**`b.sight` だけを読んでいます。** `msg.TTTWorld` は参照しません。三目並べではどちらも同じ盤面を
持つため、違いは見えません。しかし、視界だけを読むという制約があるため、隠し情報を持つゲームでも
同じ Agent インターフェースを使えます。

**ルールエンジンを持ちません。** 合法なセルを自分では計算せず、`Sight.Legal` に含まれる値を
使います。step 2 で合法手を視界へ加えたため、操作者側でルールを重複して実装せずに済みます。

**手番でないときは行動を返しません。** ローカルの Agent は、World がコミットされるたびに
呼ばれます。毎回行動を返すと、その大半は validator に拒否され、events ストリームに rejection として
残ります。`len(s.Legal) == 0` の1行で、不要な行動を防ぎます。

<Aside type="tip" title="この CPU は記録のために何もしていない">
CPU は席に座っているだけで、記録用の処理を持ちません。それでも、`Decide` が返した手は
**そのとき見えていた視界とともに**残ります。`Update` に直接書いた敵の更新関数には、この記録先が
ありません。step 4 では、Agent として残した記録を使います。
</Aside>

## 空席は誰のものか

step 2 のホストは、確認操作なしで着席しました。他に誰もおらず、自分の席しか空いていないため、
選択の余地がなかったからです。クリックによる確認は、参加者が「この人のゲームに入るか」を
選ぶときだけ必要でした。

今回は、待っている側にも二つの選択肢があります。人を待ち続けるか、ボットと対戦するかです。
そのため、ホスト側にもクリック操作を追加します。

```go
Lobby: eb.LobbyOptions{
	NoBots:  true, // 空席は人のもの。勝手に埋めない
	StandIn: true, // ただし待つのをやめる権利は本人にある
},
```

`NoBots` は step 2 と同じです。空席は引き続き人のための席であり、人が来れば対人戦を始めます。
`StandIn` が追加するのは、**待つのをやめてボットを選ぶ選択肢**だけです。

<Aside type="note" title="タイムアウトにしなかった理由">
「30秒待っても誰も来なければボットを座らせる」という実装もできます。しかし、それでは
**プレイヤーが選べません**。あと5秒で友達が起動する可能性があっても、自動的に別の相手が
着席します。そこで、待ち続けるかどうかをプレイヤーが明示的に選ぶ形にしています。
</Aside>

## 席に着けるのは Binding の1フィールド

ルールを framework に渡す `Binding` には、空席を埋める Agent のファクトリを指定できます。
step 2 では空でしたが、ここに `add` が最後に表示した1行を追加します。

```go
NewAgent: NewBot,
```

変更はこれだけです。ルールは1行も変わりません。`RuleSet` はボットの存在を知らず、`main.go` も
この関数を直接参照しません。[step 2](/tutorial/step2/) の冒頭で想定した「`Update` の中で
O の番だけボットに考えさせる」という分岐は、必要ありませんでした。

同じ関数を、二つの場面で使います。ロビーでクリックした場合は、**来なかった人の代わり**を
一席に座らせます。`run.Serve` では、**全席**をこの関数で埋め、無人の対局を実行します。
どちらも Agent を席に置く処理なので、同じファクトリで対応できます。

## 実装したボットと一人で遊ぶ

`Decide` と `Binding.NewAgent` がそろいました。ここでアプリを起動し、相手を待たずに対局できる
ところまで確認します。

```bash
go run ./tutorial/step3-record
```

<Steps>

1. アプリはネットワーク上の対戦相手を探します。誰もいなければ、自分がホストとして着席します

2. ロビーに `waiting for another player - click to play the bot instead` と表示されるまで待ちます

3. 画面をクリックします。空席にボットが座り、一人プレイの対局が始まります

4. 人は X を担当します。空いているマスをクリックして着手します

5. ボットが O を自動で置き、再び人の手番になることを確認します

6. 対局を最後まで進めます。終了すると `corpus/tictactoe-0000/` に記録が作られます

</Steps>

![人が左上に X を置き、CPU が中央へ O を返した一人プレイ画面](/images/tutorial/step3-single-player-bot.jpg)

*人が X、CPU が O を担当します。人が左上へ着手すると、CPU は `Decide` の「中央 → 角 → 辺」
という優先順に従って中央へ応答し、手番が人へ戻ります。*

これで、一つのアプリだけで対局を始められるようになりました。人の入力とボットの判断は同じ
`Agent` の行動として扱われるため、ルール側に「一人プレイ用」の分岐はありません。

別のマシンでもう一つ起動すれば、step 2 と同じ対人戦も始められます。ボットを選べるのは、
**その人が来るまでの間だけ**です。

## ボットはわざと弱い

三目並べを完璧に指すコードは、上の四つの規則より短く書けます。それでも単純なボットにした理由は、
二つあります。

一つ目は、**完璧な相手からは引き分けと負けしか記録できない**ことです。勝った対局が一つもない
コーパスでは、step 4 で勝つための判断を抽出できません。この用途では、相手を強くすると記録の
多様性が下がります。`TestTheBotCanBeBeaten` は、人が勝てる手順を一つ固定しています。このテストが
失敗するほどボットを強くすると、対戦相手としては強くなりますが、教材としての記録は偏ります。

二つ目は、この四つの規則が、**step 4 で記録から取り出したい形**だからです。ここで確かめたいのは、
生成した Agent の強さではありません。記録だけから、手書きと同じ方策を持つ決定リストを復元できるか
どうかです。その比較対象として、規則が明確なボットを用意します。

## 記録は Options の1フィールド

```go
Record: run.RecordOptions{Root: *corpus},
```

一局につき一つのディレクトリが作られます。**一局分のディレクトリを「エピソード」、複数の
エピソードを集めた `corpus/` 全体を「コーパス」と呼びます**。分析と step 4 の蒸留は、
コーパス単位で実行します。

<FileTree>
- corpus/
  - tictactoe-0000/
    - decisions.jsonl 誰が何を見て何をしたか
    - events.jsonl 状態遷移と、validator が撥ねた入力
    - outcomes.jsonl 席ごとの決着
  - tictactoe-0001/
</FileTree>

既定の記録モードは `analysis_sampled` なので、`world.jsonl` はありません。分析に不要な World を
記録対象から外します。ビット単位で一致する再生にも使う場合は、`Record.Mode` に
`episode.ReplayComplete` を指定します。すると、世界ストリームとチェックポイントも記録されます。

アプリを起動し直しても、既存の記録は上書きされません。エピソード番号は、コーパス内の続きから
割り当てられます。今日3局、明日3局指せば、合計6局が残ります。

この番号は、ファイル名だけでなく**乱数のシードにも使います**。起動するたびに0番から振り直すと、
前回と同じシードの対局をもう一度記録することになります。同じ内容のファイルを増やしても、
コーパスの多様性は増えません。

<LinkCard title="エピソードログの収集" href="/ai/episode-log/" description="4つの JSONL ストリーム、2つの記録モード、そして視界そのものを記録することの意味。" />

## 記録されているのは盤面の履歴ではない

`decisions.jsonl` の一行は、次のようになります。

```json
{"tick":1,"slot":1,"agent_kind":"human",
 "sight":{"you":1,"mark":"X","cells":["-","-","-","-","-","-","-","-","-"],
          "turn":1,"legal":[0,1,2,3,4,5,6,7,8],"winner":0,"over":false,
          "signal":{"score":0,"progress":0,"evaluation":0,"reward_delta":0,
                    "terminal":"not_terminal"}},
 "action":{"cell":0},
 "evaluation":{"score":0,"progress":0,"evaluation":0,"reward_delta":0}}
```

盤面の履歴から分かるのは、何が起きたかだけです。この行には、行動に加えて
「**選んだ Agent に何が見えていたか**」も記録されています。

この違いは重要です。9マスが空いている盤で 0 を選ぶ場合と、1マスしか空いていない盤で 0 を
選ぶ場合では、同じ `{"cell":0}` でも意味が異なります。前者は選択で、後者は消去法です。
`legal` を見れば、この二つを区別できます。step 2 で操作者側のルール実装を不要にするために加えた
`Sight.Legal` が、そのまま記録を分析する際の判断材料になります。

`agent_kind` が `human` なのは、その席を人が操作していたためです。ボットの行も同じ形で、
この列だけが `tactic` になります。`NewBot` が返した ID を、そのまま記録します。人とボットの
判断は**一つのコーパスに共存し**、step 4 で蒸留する対象をこの列から選べます。

この列は「ボットかどうか」だけでなく、**どのボットか**を表します。ボットが2種類に増えたときも、
それぞれの記録を区別できます。席番号で区別すると、ボットが別の席へ移った時点で判別できなくなります。

<Aside type="note" title="signal と evaluation が同じ値を持っている">
`sight` の中の `signal` と、行の `evaluation` 列は、同じ
[評価シグナル](/integration/stage-rule-set/#evaluate)です。行の `evaluation` 列は、セッションが
決定ごとに計算するため、常に記録されます。`sight` 内にも同じ値があるのは、**このゲームが視界に
含めると決めた**ためです。視界から外しても、行の列は残ります。ここでは、操作者が合法手だけでなく、
判断の基準も使えるように視界へ含めています。
</Aside>

```

  0464a0ebb7358018: 3
by recording mode:
  analysis_sampled: 3

outcomes by slot:
  slot 1: win=1 lose=1 draw=1
  slot 2: win=1 lose=1 draw=1

  bot: win=1 lose=1 draw=1
  human: win=1 lose=1 draw=1

  with action: 22
  sight-only: 6

```

人とボットは、`outcomes by agent kind` の同じ表に並びます。ゲーム側は席の操作者を一度も
問い合わせませんが、記録には Agent の ID があるため、**分析時には区別できます**。

`with action` と `sight-only` を分けて数えるのは、決着後の局面も全席に配られるためです。
決着後は誰も行動しませんが、勝敗を含む視界が記録されます。3局なら、この行が6行できます。

`rejection reasons` が空なのは、ボットが手番でないときに行動を返さないためです。ローカルの
Agent は World がコミットされるたびに呼ばれるため、毎回答えると大半の行動を validator に
拒否されます。その記録も events に残ります。`TestBotPassesWhenTheSeatIsNotItsTurn` は、
不要な行動を返さないことを検証します。

## 視界が「文書」になった

step 2 までの `Sight` は、1 tick の間だけプロセス内に存在する値でした。外部へ保存しないため、
フィールド名を変更しても影響はコード内に限られます。しかし、記録を始めると、その名前は
**ログの列名**になります。

そこで `json` タグを追加し、`Mark` には `MarshalText` を実装します。

```go
func (m Mark) MarshalText() ([]byte, error) { return []byte(m.String()), nil }
```

これがない場合、`encoding/json` は `[]Mark` をバイト列とみなし、base64 で出力します。

```json
"cells":"AAAAAAAAAAAA"
```

この形式でも正しく復元できますが、人がログを読んだり、述語を書いたりする際には役立ちません。
`Legal` を `[]uint8` ではなく `[]int` にするのも同じ理由です。**通信では小ささが重要ですが、
ログでは値を読んで選べることが重要です**。用途に応じて型が異なることを、記録を始める前に
明示します。

同じ問題は framework 側の型にもあります。`signal` の `terminal` を `3` ではなく `"draw"` と
記録するため、`session.Terminal` にも `MarshalText` を実装しています。この対応は、
このステップでログを実際に読んだことで必要だと分かりました。

古いコーパスに残る数値形式も、引き続き読み込めます。**記録形式の改善によって、過去の記録を
失わない**ようにしています。

## この記録を AI に変える方法

コーパスから方策を作る方法は、大きく四つあります。

| 道 | 要るもの | 出るもの | なぜそう決めたか説明できるか |
|---|---|---|---|
| 手で書く | コーパスは要らない | 思ったとおりのボット | できる。ただしバランスを触るたび全部書き直し |
| 探索（minimax など） | コーパスは要らない | ほぼ最適な手 | 手は出るが、理由は木の中にしかない |
| **記録から蒸留** | 数百の決定 | 読める決定リスト、そこから Go | できる。しかも差分が出る |
| 学習（NN など） | 数万から | 強い方策 | できない |

この framework では、三つ目の「記録から蒸留」を選びます。生成された相手の判断が不自然なときに、
理由を確認して修正できることを重視するためです。

ただし、方法を選ぶだけではコーパスはできません。最初に、**誰かが対局を記録する必要があります**。

- **自分で打つ** — 数十局が現実的な上限ですが、人が選びたい行動を記録できます
- **ボット同士を回す** — 何局でも実行できます。ただし決定的なボット2体では、100局回しても
  内容は1局分です。`TestTwoCopiesOfTheBotRecordTheSameGameEveryTime` がこの性質を固定しています
- **自己対戦・リーグ** — 相手の違いを意図的に作ります。最終的にはこの方法を使います

この順番には意味があります。まず人が指し、その記録を蒸留して Agent を作り、生成した Agent を
相手に次の記録を集めます。シミュレーションによる自動収集が役立つのは、Agent を生成したあとです。
最初から自動収集しようとしても、動かす方策がありません。step 3 が人の対局から始まるのは、
**人の判断が最初の種になる**ためです。

<Aside type="note" title="ヘッドレスの回し方はもうある">
`run.Serve` に `session.Unlimited` を渡すと、全席をボットで埋めた対局を画面なしで実行できます。
速度は描画ではなく、マシンの処理能力だけで決まります。この仕組みはすでに使えますが、現時点では
**多様な記録を作れる相手**がまだありません。
</Aside>

## 確かめ方

ウィンドウを開かずに、次の性質をテストで検証します。

| 主張 | テスト |
|---|---|
| 人が打った手が、そのとき見えていた視界つきで記録される | `TestYourOwnPlayIsWhatGetsRecorded` |
| 記録された行動は隣にある視界の上で合法だった（局面がずれていない） | 同上 |
| 人の行とボットの行が、ラベル1列だけ違う同じ形で1つのログに入る | 同上 |
| 窓なし・人なしでも同じルールがコーパスを産む | `TestPlayingWithNobodyWatchingProducesACorpus` |
| 同じボット2体を何局回しても記録は1局分にしかならない | `TestTwoCopiesOfTheBotRecordTheSameGameEveryTime` |
| ボットは勝てるとき勝ち、負けるとき止める | `TestBotTakesTheWin` / `TestBotBlocksTheLoss` |
| ボットは自分の手番でないとき黙る（events を汚さない） | `TestBotPassesWhenTheSeatIsNotItsTurn` |
| ボットは人間に負けうる | `TestTheBotCanBeBeaten` |
| step 2 の LAN 対戦は壊れていない | `TestTwoInstancesPlayOneBoard` |

二行目の検証は、視界と行動のタイミングがずれていないことを確認します。記録された `sight` が
指し手の**あとの**盤面でも、行数とラベルだけなら一致します。「その手が、その視界で合法だったか」を
照合することで、判断時点の視界が記録されていると確認できます。

## まだないもの

**ゲスト側では記録しません**。セッションを実行するのはホストだけで、ゲスト側には記録元となる
視界の生成処理がありません。LAN 対戦の記録は、ホスト側のマシンにだけ残ります。

**蒸留はまだ行いません**。step 4 では、`corpus/` を語彙で分析して条件→行動の候補を作り、
承認した候補を Go に変換します。そして、生成された Agent を同じ席に座らせます。

現在のボットは、比較対象として手で実装しています。生成したボットの方が強いかどうかではなく、
**記録だけから、手書きと同じ方策を復元できるか**を step 4 で確かめます。
