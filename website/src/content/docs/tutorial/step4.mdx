import { Aside, FileTree, LinkCard } from '@astrojs/starlight/components';

step 3 の記録には、人が打った手と、手書きボットが返した手の両方が入っています。どちらを学習対象に
するのでしょうか。このステップで取り出すのは、**手書きボットの判断だけ**です。ユーザーの着手は
まだ使いません。

また、step 3 で人が数局遊んで作った `corpus/` を、そのまま読み込むわけでもありません。同じ
手書きボットを教師として十分な数の判断を用意し、そこから教師の方策を復元します。判断記録を
自動対局で用意する仕組みは step 5 で扱います。

手書きボットを教師として対局を記録し、その記録から規則を取り出して Go のコードへ変換します。
最後に、生成したボットと元のボットを同じ局面で動かし、同じ手を選ぶか確かめます。

| 入力 | 処理 | 出力 |
|---|---|---|
| 手書きボットが見た盤面と選んだ手 | 判断を表す規則を記録から採掘する | 同じ方策を再現する Go の決定リスト |

<Aside type="note" title="ユーザーの打ち方を再現するステップではない">
step 3 で保存した `agent_kind: human` の記録も、同じ仕組みで蒸留できます。ただし、数局分の記録では
局面が足りません。ここでは正解のソースと比較できる手書きボットを教師にし、記録から元の方策を
復元できるかを検証します。
</Aside>

生成物は、次のような読みやすい Go のコードです。

```go
func Decide(obs game.Sight) (msg.Move, bool) {
	switch {
	case pred.PreferredCellIs(obs, 4):
		// chip preferred_cell_is_4 → play_4 (coverage 800, counterexamples 0)
		return msg.Move{Cell: 4}, true
	case pred.PreferredCellIs(obs, 0):
		// chip preferred_cell_is_0 → play_0 (coverage 706, counterexamples 0)
		return msg.Move{Cell: 0}, true
	case pred.WinningMoveIs(obs, 8):
		// chip winning_move_is_8 → play_8 (coverage 516, counterexamples 0)
		return msg.Move{Cell: 8}, true
	...
```

この switch が**決定リスト**です。上から順に条件を評価し、最初に当てはまった行動を選びます。
一つの case が、一つの**チップ**、つまり人が承認した規則に対応します。コメントの `coverage` は、
その規則を支持した記録の数です。コードとして読めるだけでなく、生成し直した際に diff も確認できます。

蒸留パイプラインは framework の `behavior` パッケージが提供します。ゲーム側で用意するのは、
判断記録を集めたコーパスと、**規則に使える判断の一覧**です。後者を**語彙**と呼びます。

このステップでは、すでに用意されたコーパスから正しい規則を取り出せるかに集中します。自動対局で
コーパスを作る `simulate` と、生成コードを作り直す `distill` の実行手順は、[step 5](/tutorial/step5/)
で一続きの処理として扱います。

<LinkCard title="用語の整理" href="/architecture/terms/#記録と方策の語" description="コーパス・述語・語彙・チップ・被覆・反例。このページで出てくる語の一覧。" />

## 最初の語彙は失敗する

盤面から最初に思い付く**述語**、つまり視界に対する名前付きの真偽判定は、
「セル k が空いている」でしょう。9個のセルについてこの述語を用意し、コーパスから
「この条件のとき、この手を指していた」という規則を**採掘**すると、次の結果になります。

```
naive: 8 chips, 4 approved, 386/652 decisions covered (59.2%)
```

エラーは出ず、`Propose` は「どの条件にも当てはまらなかった決定」を0件と報告します。それでも、
承認されたチップで説明できるのは、ボットの決定の**6割弱**です。この割合を**被覆率**と呼びます。

原因は**反例**です。反例とは、条件に当てはまるのに、別の行動を選んだ記録を指します。
「セル8が空いている → 8に置く」は多くの局面に当てはまりますが、**勝てる手があるとき**と
**相手の勝ちを止める必要があるとき**は、別のセルを選びます。その一手ずつが反例になります。
反例があるチップは自動承認されず、生成コードにも含まれません。

その結果、間違った手を指すボットではなく、**4割の局面で行動を返さないボット**ができます。

<Aside type="caution" title="失敗が失敗の形をしていない">
被覆率は、承認済みチップで説明できる決定の割合です。一方、`uncovered` は、どの規則の条件にも
当てはまらなかった決定の数です。最初の語彙では、すべての決定が何らかの「セルが空いている」に
当てはまるため、`uncovered` は0件になります。条件に当てはまったうえで別の行動を選んだ記録は、
反例として扱われるため `uncovered` には現れません。
</Aside>

## 判断に名前を付ける

そこで、単なる空きセルではなく、判断の違いに名前を付けます。

| 述語 | 意味 |
|---|---|
| `winning_move_is_k` | この席は k に置けばラインが揃う |
| `blocking_move_is_k` | k を取らないと相手が次に揃える |
| `preferred_cell_is_k` | 急ぎがないとき取るのは k（中央→角→辺） |

同じコーパスを新しい語彙で採掘し直すと、すべての決定を説明できます。

```
judgement: 19 chips, all approved, 2632/2632 decisions covered
```

ここでは、述語名が単数形であることが重要です。勝てるセルが同時に二つある局面で、両方に true を
返すと、二つのチップが同じ局面に異なる行動を主張します。そこで、同点の候補から一つを選ぶ処理を
**述語の中に含めます**。順序は `game.Lines` と同じです。オセロの `BestMoveIs` が argmax を
述語に含めるのも、同じ理由です。

**採掘器の表現力は、意図的に制限しています**。各条件に使える述語は一つだけで、複数条件の連言を
学習しません。どのような判断を表現できるかは、すべて人が定義する語彙で決まります。

<LinkCard title="語彙とチップ" href="/ai/vocabulary/" description="data:derived-predicate がなぜ座標演算ではなく判断語なのか、チップライブラリが何を共有するのか。" />

## 採掘器は人間とは違う順序を見つける

生成された19ケースの先頭は、次の順序です。

```
 1  preferred_cell_is_4    coverage 800
 2  preferred_cell_is_0    coverage 706
 3  winning_move_is_8      coverage 516
```

手書きと同じ「勝ち → ブロック → 好み」を予想すると、**先頭の二つが違って見えます**。
好みの規則が、勝ちの規則より上にあります。

しかし、この順序でも正しく動きます。X は必ず中央から始めるため、`preferred_cell_is_4` が
成立するのは X の初手だけです。その時点では、勝ちもブロックも成立しません。どちらにも二つ以上の
マークが必要だからです。`preferred_cell_is_0` も、相手のマークが一つしかない局面でしか成立しません。
この二つは勝ちやブロックと**同時に成立しない**ため、上に置いても行動を奪いません。13行目以降の
好みの規則は勝ちやブロックと同時に成立する可能性があるため、それらの下に並びます。

`SequentialCovering` は、コーパス内に反例がない規則を優先します。このため採掘器は、人が書いた
順序そのものではなく、**コーパス内の到達可能な局面で等価な別の順序**を復元しました。

順序が違っても本当に等価なのかは、コードを読むだけでは判断できません。そこで、到達可能な局面を
すべて列挙し、手書きの方策と生成した方策を照合するテストを置いています。

## 元の方策を再現できたか

記録した局面だけで同じ手を返しても、元の方策を再現したとは限りません。記録にない局面では、
決定リストの規則が異なる順序で衝突する可能性があるからです。

そこで、到達可能な123局面をすべて列挙し、手書きボットと生成ボットの行動を照合します。
記録への一致ではなく、**元の方策への一致**を確かめます。

| 主張 | テスト |
|---|---|
| ナイーブな語彙は、エラーなしにボットの大半を落とす | `TestTheNaiveVocabularyQuietlyLosesMostOfTheBot` |
| 判断語なら全決定が説明され、反例が1つも出ない | `TestJudgementVocabularyExplainsEveryDecision` |
| 生成エージェントは、**到達可能な123局面すべて**で手書きと一致する | `TestGeneratedAgentPlaysExactlyLikeTheBot` |
| 採掘時の述語と実行時の述語が食い違っていない | `TestMinerAndRuntimeAgree` |
| 生成エージェントは実セッションで同じ試合をする | `TestTheDistilledAgentPlaysTheSameMatches` |

四つ目のテストは、同じ述語を二つの場所へ実装したことによるずれを検出します。採掘時には `Eval` が
記録 JSON を読み、実行時には生成コードが `GoExpr` を呼びます。両者を自動的に一致させる仕組みは
ありません。実装がずれると、ライブラリの検証とコードのビルドは通るのに、Agent が
**コーパスに存在しない方策**を実行します。このテストで、二つの実装を直接照合します。

```bash
cd tutorial/step4-distill && go test ./distill
```

## ルールは1文字も変わっていない

<FileTree>
- tutorial/step4-distill/
  - main.go ウィンドウ。生成エージェントを席に着けるのはここ
  - game/ ルール。step 3 から1文字も変えていない
  - distill/
    - distill.go 語彙2つ、コーパス、採掘、playtest
    - pred/pred.go 判断語。人が書き、人がレビューする
    - gen/ 生成物（コミット済み）
</FileTree>

`game` は `distill/gen` を import しません。生成 Agent は `Sight` を判定する述語を呼ぶため、
`gen` が `game` に依存します。逆にルール側から `gen` を参照すると、相互依存になり、
コンパイラが import cycle として拒否します。

そこで、席に置く Agent は entry point で選びます。[step 2](/tutorial/step2/) でトランスポートを
entry point に置いたのと同じく、ルールの外側で差し替える構成です。

```go
func binding() run.Binding[msg.TTTWorld, msg.Move, game.Sight] {
	b := game.Binding()
	b.NewAgent = func(session.SlotID) (string, session.Agent[game.Sight, msg.Move]) {
		return "distilled", &gen.Distilled{}
	}
	return b
}
```

`gen.Distilled` を `game.HandWritten` に替えると、元の手書きボットと対戦できます。
**変更するのはこの1行だけです**。手書きと生成のどちらも、同じ Agent として席に座ります。

## 生成したボットと対戦する

生成した `gen.Distilled` は、すでに `Binding.NewAgent` へ設定されています。アプリを起動し、
step 3 と同じように空席へボットを着席させます。

```bash
go run ./tutorial/step4-distill
```

人が盤面をクリックすると、相手は生成された決定リストから手を選びます。見た目と操作は step 3 と
変わりません。違うのは、相手の `Decide` が手書きの条件分岐ではなく、記録から作られた
`gen.Distilled` を実行していることです。

これで Step 4 の確認は完了です。**手書きボットの判断記録から、同じ方策で動くボットを再構成できました**。

## このステップで扱わないもの

**対戦相手はランダムに指すだけです**。`distill.Corpus` の相手は合法手から一様に選ぶため、
作れる局面の多様性は最低限です。必要な局面が現れるかどうかも運に左右されます。

**教師は手書きボットです**。蒸留で再現できるのは教師の方策までで、教師より強くはなりません。
step 4 で手書きボットを対象にしたのは、生成物を元のソースと比較して**答え合わせできる**ためです。
より強い教師を使う場合、この比較方法は使えません。

**人の記録はまだ蒸留していません**。同じパイプラインで `agent_kind: human` の行を選べば、
人の打ち方を決定リストにできます。ただし、[step 3](/tutorial/step3/) で集められる数十局では
十分ではありません。
