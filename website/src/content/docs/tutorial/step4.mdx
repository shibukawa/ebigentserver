step 3 で、遊んだ分だけ対局が記録として貯まるようになった。このステップの終わりには、
**その記録から作ったボット**が相手をしている——手で書いたのではなく、記録から掘り出して
Go に落としたものが。

```bash
go run ./tutorial/step4-distill
```

step 3 と同じように遊べる。違うのは、相手をしているボットを**誰も書いていない**ことだ。

中身は生成された Go で、読める。

```go
func Decide(obs game.Sight) (msg.Move, bool) {
	switch {
	case pred.PreferredCellIs(obs, 4):
		// chip preferred_cell_is_4 → play_4 (coverage 800, counterexamples 0)
		return msg.Move{Cell: 4}, true
	case pred.PreferredCellIs(obs, 0):
		// chip preferred_cell_is_0 → play_0 (coverage 706, counterexamples 0)
		return msg.Move{Cell: 0}, true
	case pred.WinningMoveIs(obs, 8):
		// chip winning_move_is_8 → play_8 (coverage 516, counterexamples 0)
		return msg.Move{Cell: 8}, true
	...
```

switch そのものが**決定リスト**だ。上から順に読んで、最初に条件が当たったものを採る。
1ケースが**チップ**1つ——人が承認した規則1つ——にあたる。コメントの `coverage` は
その条件を支持した記録の数だ。読めるし、diff も取れる。

パイプライン自体は framework のもの（`behavior` パッケージ）だ。step 4 が供給しているのは
2つしかない——コーパスの作り方と、**規則が使ってよい言葉**。後者を**語彙**と呼ぶ。

コーパスの作り方は難しくない。難しいのは語彙のほうだ。

<LinkCard title="用語の整理" href="/architecture/terms/#記録と方策の語" description="コーパス・述語・語彙・チップ・被覆・反例。このページで出てくる語の一覧。" />

## 最初の語彙は失敗する

盤面から素直に思いつく**述語**——視界に対する、名前の付いた真偽の判断——は「セル k が
空いている」だろう。9個並べ、コーパスから「この条件のときこう指していた」を**採掘**すると、
こうなる。

```
naive: 8 chips, 4 approved, 386/652 decisions covered (59.2%)
```

エラーは出ない。`Propose` は「説明できなかった決定」を0件と報告する。それでも承認まで残った
チップが説明できるのは、ボットの決定の**6割弱**だ。この割合を**被覆**と呼ぶ。

理由は**反例**——条件は当たっているのに、違う行動を取っていた記録——だ。「セル8が空いている
→ 8に置く」はたいていの局面で正しいが、**勝てる手があるとき**と**止めなければ負けるとき**、
ボットは別のセルを選ぶ。その1手ずつが反例に数えられ、反例のあるチップは自動承認されず、
承認されなければ生成にも入らない。

出てくるのは、間違ったボットではない。**4割の局面で黙るボット**だ。

<Aside type="caution" title="失敗が失敗の形をしていない">
被覆率は「承認済みチップが説明する決定の割合」で、`uncovered` は「どの規則の条件にも当たらな
かった決定の数」だ。ナイーブな語彙では後者が0件になる——条件は当たっている。当たったうえで
違う行動を取った記録があるだけで、それは `uncovered` には出てこない。
</Aside>

## 判断に名前を付ける

盤面が言っていない区別に名前を付ける。

| 述語 | 意味 |
|---|---|
| `winning_move_is_k` | この席は k に置けばラインが揃う |
| `blocking_move_is_k` | k を取らないと相手が次に揃える |
| `preferred_cell_is_k` | 急ぎがないとき取るのは k（中央→角→辺） |

同じコーパスで採掘し直すと閉じる。

```
judgement: 19 chips, all approved, 2632/2632 decisions covered
```

**単数形が効いている。** 勝てるセルが同時に2つあることはあり、両方に true を返す述語だと
2つのチップが同じ局面を主張して、記録の半分と食い違う。だから tie-break は**述語の中で**
決めてある——`game.Lines` と同じ順で。オセロの `BestMoveIs` が argmax を述語に畳んだのと
同じ手だ。

**採掘器は意図的に無力だ。** 条件は述語1個で、連言は学習しない。表現力は全部語彙側にあり、
賢さを入れる場所もそこしかない。

## 採掘器は人間とは違う順序を見つける

生成された19ケースの並びの先頭は、こうなっている。

```
 1  preferred_cell_is_4    coverage 800
 2  preferred_cell_is_0    coverage 706
 3  winning_move_is_8      coverage 516
```

「勝ち → ブロック → 好み」を期待していたなら、**先頭の2つが違う**。好みの規則が勝ちより上にいる。

そして正しい。X は必ず中央から入るので、「4 が最優先の空きマス」が成立するのは X の1手目だけで、
そこに勝ちもブロックも存在しない——どちらも2つ目のマークが要る。`preferred_cell_is_0` も同じで、
相手のマークが1個しかない局面だ。この2つは勝ち・ブロックと**同時に成立しえない**ので、上に
置いても何も奪わない。13行目以降の好みの規則は、ちゃんと勝ちとブロックの下にいる。

`SequentialCovering` は「コーパスが一度も否定しなかった規則」を優先する。否定されなかった以上、
上に置いてよい。つまり採掘器が復元したのは、人間が書いた順序ではなかった。**到達可能な範囲で等価な、
別の順序**だった。

生成された switch を眺めて納得するのではなく、全数で突き合わせるテストを置いてあるのはこのためだ。
読んで「順番が違う」と思ったものが、正しいことがある。

## コーパスは自分の穴を見られない

3つのサイズで採掘すると、こうなる。

| 局数 | チップ | 黙る盤面 | 間違える盤面 |
|---|---|---|---|
| 200 | 16 | 8 | 2 |
| **400** | **19** | 0 | **2** |
| 800 | 19 | 0 | 0 |

**どのサイズも、パイプラインの中からは同じに見える。** 反例ゼロ、被覆100%、`uncovered` は0件。

見るべきは真ん中の行だ。400局でチップ数が**打ち止まる**——次に倍にしても新しい規則は1つも
出てこない。完成したように見える最も説得力のある信号がここで出る。それでも生成されたエージェントは
到達可能な盤面を2つ間違える。規則は全部揃っていて、**並びだけが違う**。

その盤面では、X は 3 に置けば勝ちで、同時に 2 を取らないと相手が次に揃える。ボットは勝ちを取る。
生成されたエージェントは**ブロックする**——勝てるのに止めに行く、という人間にも一目で分かる
間違いだ。原因は上位2件の並びだけだ。

```
400局                              800局
 6  blocking_move_is_2  cov 22      6  winning_move_is_3   cov 46
 7  winning_move_is_3   cov 14      7  blocking_move_is_2  cov 38
```

<Aside type="caution" title="倍増して直った理由は、証拠が増えたからではない">
`SequentialCovering` は反例のない規則のうち被覆の大きいものから採る。400局では
`blocking_move_is_2` のほうが支持記録が多く、800局では逆転した。それだけだ。

どちらのサイズでも `blocking_move_is_2` は反例ゼロで、つまり**どちらのコーパスも、この2つの
どちらが上かを知らない**。800局の並びが正しいのは頻度がたまたまそう転んだからで、何かが検証
したからではない。
</Aside>

決定リストの順序は、コーパスが述べている情報ではない。**「反例なし」はコーパスについての言明で
あって、ゲームについての言明ではない。** そして違いを教えてくれたのは、被覆率でもチップ数でもなく、
到達可能な局面を全部指してみたテストだけだった。

framework が承認を人間に通し、最後に `flow:automated-playtest` を置いているのはこのためだ。

## 確かめ方

| 主張 | テスト |
|---|---|
| ナイーブな語彙は、エラーなしにボットの大半を落とす | `TestTheNaiveVocabularyQuietlyLosesMostOfTheBot` |
| 判断語なら全決定が説明され、反例が1つも出ない | `TestJudgementVocabularyExplainsEveryDecision` |
| 生成エージェントは、**到達可能な123局面すべて**で手書きと一致する | `TestGeneratedAgentPlaysExactlyLikeTheBot` |
| 1/4のコーパスは規則を取りこぼす | `TestASmallCorpusIsMissingRules` |
| 半分のコーパスは規則が揃っていて、なお間違える | `TestAHalfCorpusHasEveryRuleAndStillPlaysWrong` |
| 採掘時の述語と実行時の述語が食い違っていない | `TestMinerAndRuntimeAgree` |
| 生成エージェントは実セッションで同じ試合をする | `TestTheDistilledAgentPlaysTheSameMatches` |

3つ目が一番強い主張になる。コーパスは到達可能局面の一部しか踏まないので、**全数で一致する**のは
被覆率が言っている以上のことだ。

6つ目は地味だが、外すと痛い。述語は2回書かれる——採掘時に記録 JSON を読む `Eval` と、生成コードが
実行時に呼ぶ `GoExpr` だ。両者を一致させる仕組みは何もない。ずれると、ライブラリは検証を通り、
コードはビルドでき、エージェントは**コーパスに存在しない方策**を指す。このパイプラインで唯一、
どこにも痕跡が残らない失敗だ。

再生成はコマンドになった。step 2 で `ebigent init` が置いた `cmd/distill` に、step 4 が中身を
入れる——それがこのステップで唯一、フレームワークの側から用意されていたファイルだ。

```bash
cd tutorial/step4-distill && ebigent distill
```

```
800 games, 2632 decisions, 19 chips → distill/gen
100.0% of the recorded decisions are explained by an approved chip
```

書き出す側と比較する側は**同じ呼び出しを通る**。コマンドが `Compiled.Write` を呼び、テストは
`Compiled.Sources` を committed と比べる。別々にコーパスを作れば、再生成してもテストが赤い
ままで、どちらを走らせても閉じない状態が起こりうる。

```bash
cd tutorial/step4-distill && go test ./distill
```

## ルールは1文字も変わっていない

<FileTree>
- tutorial/step4-distill/
  - cmd/distill/ ebigent distill が走らせるエントリ
  - main.go ウィンドウ。生成エージェントを席に着けるのはここ
  - game/ ルール。step 3 から1文字も変えていない
  - distill/
    - distill.go 語彙2つ、コーパス、採掘、playtest
    - pred/pred.go 判断語。人が書き、人がレビューする
    - gen/ 生成物（コミット済み）
</FileTree>

`game` が `distill/gen` を import していないことに注意したい。生成エージェントは `Sight` を
判定する述語を呼ぶので、`gen` は `game` に依存する。ルール側がそれを名指すと**自分の記録から
蒸留されたものに依存する**ことになり、コンパイラが import cycle として拒否する。

だから席の選択は entry point に移った。[step 2](/tutorial/step2/) がトランスポートをそこに
置いたのと同じ理由、同じ場所だ。

```go
func binding() run.Binding[msg.TTTWorld, msg.Move, game.Sight] {
	b := game.Binding()
	b.NewAgent = func(session.SlotID) (string, session.Agent[game.Sight, msg.Move]) {
		return "distilled", &gen.Distilled{}
	}
	return b
}
```

`gen.Distilled` を `game.HandWritten` に替えれば、ウィンドウは元のボットと対戦する。
**この1行以外は何も変わらない**——それが蒸留の主張そのものだ。

## まだないもの

**相手はランダムだ。** `distill.Corpus` の対戦相手は合法手から一様に選ぶだけで、多様性としては
最低限だ。上の表が言っているとおり、必要な局面が現れるかどうかは運任せだ。round-robin、
自己対戦、リーグ——`concept:continuous-match-loop` が書いている組み合わせ方が step 5 だ。

**教師がボットだ。** 蒸留できるのは教師の方策までで、それより強くはならない。step 4 が手書き
ボットを対象にしたのは**答え合わせができる**からで、生成物が正しいかどうかを元のソースと
突き合わせられる。より強い教師に向けたとき、その答えはない。

**人の記録はまだ蒸留していない。** 同じパイプラインを `agent_kind: human` の行に向ければ、
あなたの打ち方が決定リストになる。[step 3](/tutorial/step3/) の結論どおり数十局では足りない
——それも step 5 の理由の一つだ。
