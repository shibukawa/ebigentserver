step 4 で、記録からボットを作れるようになった。ただし2つ引っかかっている——コーパスの並びが
正しかったのは運だったこと、そして教師より強くはならないこと。このステップの終わりには、
**片方が直り、もう片方は直らないことが分かっている**。

```bash
go run ./tutorial/step5-simulate
```

step 4 と同じように遊べて、相手も同じく生成された Go だ。違うのは裏側で、このステップの
成果物は半分がコードで、半分が**測定結果**になる。

## 相手を回すと、量の半分で足りる

`concept:continuous-match-loop` は組み合わせ方を4つ挙げている——round_robin、ランダム
サンプリング、自己対戦、リーグ。framework 側の `matchloop` はシードと集計だけを持ち、
**誰が誰と当たるかは呼び出し側に委ねる**。それはゲームの事実で、ループが推測できるものでは
ないからだ。

3体を回す。コイン、step 3 の手書きボット、完璧な打ち手。

強さのために選んでいない。**違うことのために**選んでいる。コインはまともな打ち手が辿り着かない
局面をうろつき、手書きボットはコインが滅多に作らない「勝ちとブロック」を量産し、完璧な打ち手は
「好みが緊急事態に譲る」局面を確実に作る。

```
rotated 200 games: 77.3% explained; coin 800 games: 72.5%
```

回した200局が、コインの800局より説明できている。だから step 5 の正式なコーパスは400局で、
step 4 の半分になった。

## 完璧な教師は蒸留できない

`distill/teacher.go` の `Perfect` は全幅探索で、負けない。三目並べは小さいので探索は網羅的かつ
厳密だ。これを**教師**——記録を残す側——にして、12通り測った。蒸留して出てくる方策のほうは
**生徒**と呼ぶ。

```
judgement random       200 games  70.7% explained
judgement random       800 games  72.5% explained
judgement round_robin  200 games  77.3% explained
judgement round_robin  800 games  77.8% explained
fork      random       200 games  77.0% explained
fork      random       800 games  78.3% explained
fork      round_robin  200 games  79.2% explained
fork      round_robin  800 games  79.7% explained
best of twelve runs: 79.7%
```

**どのノブを回しても閉じない。** 局数を4倍にして +1.8pt、語彙を増やして +7pt、相手を回して
+2pt。手書きボットなら100%だったところが、最良で 79.7% だ。

### 原因は賢さではない

三目並べの初手は、完全に打てばどれも引き分けになる。だから探索は9通りに**同じ値**を返し、
何か恣意的なものが1つを選ぶ。`Perfect.Principled` を落とすとループの走査順が選び、立てると
中央→角→辺の好みが選ぶ。**強さは同一**だ——どの最適手を選んでも最適なのだから。

述語は局面についての事実しか言えない。そして局面は、その選択を決定していない。
**理由のないところに、蒸留するものはない。**

step 4 が成立したのは手書きボットが良かったからではなかった。**指し手のすべてに、述語が
名指せる理由があった**からだ。

<Aside type="caution" title="語彙を増やすと、黙る代わりに堂々と間違える">
fork 述語（`creates_fork_at_k` / `blocks_fork_at_k`）を足したときの内訳。

```
judgement: 57 silent, 12 wrong.  fork: 3 silent, 36 wrong
```

沈黙は 57 → 3 に減り、**間違いは 12 → 36 に増える**。語彙が豊かになると、採掘器は「コーパスが
一度も否定しなかった規則」をより多く見つけられるようになる。そして**コーパスが否定しなかった
規則は、それだけでは正しくない**。
</Aside>

### 探索はそのまま座らせられる。ただし高い

`Perfect` はごく普通の `session.Agent` だ。蒸留せずに席に着けられる。値段だけが問題になる。

```
search 614.166µs per decision, list 55ns — 11167x
```

alpha-beta で枝刈りした上での数字だ。枝刈りしない探索と比べるのはフェアではないので、実際の
探索と比べて**なお4桁**ある。30tps なら tick 予算は 33ms で、3×3 の盤の1手にその 1.8% を
1席が使う。

`rule:generated-agent-code-is-deterministic` には `cost_bound` という項がある。述語は
エージェントごと・tickごとに走るので、生成は無制限のスキャンを拒否する——言っているのは
これだ。**生徒が教師と同じコストを払うなら、蒸留していないのと同じ**になる。

## これは完全ゲームの限界だ

12通り試して届かなかったのだから、蒸留は強い教師に効かない——そう読める。だが測ったのは
そこではない。**解けている完全情報ゲームの限界**であって、蒸留の限界ではない。

三目並べやオセロには最強の打ち手が存在し、その打ち手は同値な最適手の中から理由なく選ぶ。
だから「教師を強くする」戦略が効かない。

この framework が想定しているゲームでは、事情が逆になる。

| 完全ゲーム | アクションゲームの敵 |
|---|---|
| 最強の相手が存在する | **完璧だと面白くない。適度に弱いのが仕様** |
| 深い読みが要る | パターンで動く。読み合いではなく読める動き |
| 教師は探索。同値な手を恣意的に選ぶ | 教師は**人**。開発者が操作して動きを付ける |
| 恣意性が蒸留を止める | 人が付けた動きは**それ自体が仕様**。恣意ではない |

右の列では、この step で見た問題が起きない。開発者が敵を操作してプレイし、その記録を蒸留し、
ゲーム内で再生する。[step 3](/tutorial/step3/) が「自分で打った記録」から始めたのは、
最終的にそこへ行くためだった。

その形は別のチュートリアルで扱う。**ボードゲーム編はここで終わる。**

## 確かめ方

| 主張 | テスト |
|---|---|
| 相手を回した200局が、コインの800局より説明できる | `TestRotatingTheOpponentBeatsPlayingMore` |
| 完璧な教師は、12通りどれでも8割に届かない | `TestAPerfectTeacherCannotBeDistilled` |
| fork 述語は沈黙を減らし、間違いを増やす | `TestForkWordsTradeSilenceForConfidence` |
| 探索は決定リストの1万倍以上かかる（枝刈り後） | `TestTheSearchCostsWhatTheListDoesNot` |
| 生成エージェントは到達可能な123局面すべてで手書きと一致する | `TestGeneratedAgentPlaysExactlyLikeTheBot` |

2つ目は**通る否定的結果**だ。「閉じなかった」を主張として固定してあるので、誰かが語彙や
採掘器を改良して8割を超えたら、このテストが赤くなって教えてくれる。

## まだないもの

**このステップは `ebigent simulate` を使っていない。** [step 4](/tutorial/step4/) は使っている
——`ebigent simulate && ebigent distill` の2つで、コミット済みの生成物がそのまま出る。違いは
配置の数だ。

**1回の `simulate` は1つの配置だ。** step 4 のコーパスは全局が「ボット対コイン」なので1回で
足りる。step 5 のコーパスは3体を**回した**もので、局ごとに相手が変わる。1つの配置を渡す
コマンドからは出てこない。

そして step 5 の結論は 2語彙 × 2組み合わせ × 3局数の12通りを並べた表だ。コーパスが1つではなく
12個ある、とも言える。`matchloop` がシードと集計だけを持ち、誰と誰が当たるかを呼び出し側に
委ねているのは、まさにこれが**ゲームごとの話**だからだ。

**リーグがない。** `SelfPlay` は定義してあるが、過去バージョンを相手に残すリーグ運用は入れて
いない。三目並べでは意味のある差が出ないためで、それを示すのに1ステップ使う価値がないと判断した。
