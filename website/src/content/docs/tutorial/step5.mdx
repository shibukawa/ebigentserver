step 4 では、用意された判断記録から規則を取り出し、手書きボットと同じ方策を再構成しました。
しかし、実際に方策を育てるには、入力となる記録も作らなければなりません。人が何百局も操作する
代わりに、Agent 同士を自動で対戦させます。これが **simulate** です。

自動対局でコーパスを作り、そのコーパスから Go の決定リストを生成し、生成したボットをゲームで
動かします。Step 5 では、この一連の流れに加えて、対戦相手を変える効果と、教師から学べる限界も
測定します。

## simulate、distill、実行

似た名前が続きますが、入出力は別です。

| 処理 | 入力 | 出力 |
|---|---|---|
| **simulate** | 教師、対戦相手、局数、シード | 対局の判断記録を集めた `corpus/` |
| **distill** | `corpus/` と語彙 | 生成された決定リスト `distill/genrotated/` |
| **実行** | `distill/genrotated/` の `Rotated` Agent | 人と対戦できるゲーム画面 |

`Rotated` は、記録した対局を手順どおりに再生する Agent ではありません。現在の盤面を受け取り、
記録から得た規則を上から評価して、その場で次の手を選びます。記録と違う順番で対局が進んでも、
条件に合う規則があれば行動できます。

固定した一組を対戦させる場合、二つの処理は別々に実行できます。Step 4 の「手書きボット対コイン」を
再生成するなら、次の順序です。

```bash
cd tutorial/step4-distill
ebigent simulate
ebigent distill
```

`simulate` は800局を `corpus/` に保存し、`distill` はその記録を読んで `distill/gen/` を更新します。
二つのコマンドは `corpus/` を介してつながり、互いを直接呼びません。

Step 5 では、局ごとに対戦相手を切り替えます。一組だけを受け取る `ebigent simulate` では表せないため、
`cmd/distill` が `matchloop` を使って自動対局を実行し、続けて蒸留します。生成物は**2つ**です。
Step 4 と同じ製法（コイン相手800局）の `distill/gen/` の `Distilled` と、相手を回した400局から
蒸留した `distill/genrotated/` の `Rotated`。どちらも次の1コマンドで作り直せます。

```bash
cd tutorial/step5-simulate
ebigent distill
```

生成されたボットをゲームで動かすときは、リポジトリのルートへ戻って起動します。

```bash
cd ../..
go run ./tutorial/step5-simulate
```

画面では Step 4 と同じように一人で対戦できます。相手として着席するのは `genrotated.Rotated`——
Step 4 の `Distilled` とは別のフォルダに、別の名前で蒸留し直した写しです。このステップの diff の
本体は、それを座らせる main.go の1行に集約されています。

```go
return "rotated", &genrotated.Rotated{}
```

識別子を `gen.Distilled` に書き戻せば、窓は Step 4 製法のボットに戻ります。両方コミットして
あるのは、この差し替えを両側とも再現できる diff として見せるためです。なお三目並べでは、
差し替えても指し手は変わりません。どちらの写しも到達可能な123局面すべてで手書きボットと
一致します（`TestGeneratedAgentPlaysExactlyLikeTheBot` が両方に同じ質問をします）。変わるのは
並びを支える**根拠**で、それを測るのがこのページの残りです。

## 固定した相手だけでは、コーパスに穴が残る

穴の存在は、Step 4 の終わりに二度見ています。curate の holdout 評価が書き出す `gaps.jsonl` と、
自分の写しが黙って代打に譲った回数です。このステップが測るのは、その穴を**どう埋めるか**——
局数を増やすのか、相手を替えるのか——で、教師を手書きボットに戻すのは答え合わせのためです。

Step 4 と同じ「手書きボット対コイン」を、局数だけ変えて simulate した結果です。

| 局数 | チップ | 行動しない盤面 | 間違える盤面 |
|---|---|---|---|
| 200 | 16 | 8 | 2 |
| **400** | **19** | 0 | **2** |
| 800 | 19 | 0 | 0 |

パイプライン内の被覆率は、どのサイズでも100%です。それでも、400局から作った Agent は二つの
盤面で間違えます。規則は19個そろっていますが、**規則の順序**が違うためです。

問題の盤面では、X は 3 に置けば勝てます。同時に、2 を取らなければ相手が次にそろえます。
手書きボットは勝ちを選びますが、生成 Agent は相手の勝ちを防ぐ手を選びます。

```
400局                              800局
 6  blocking_move_is_2  cov 22      6  winning_move_is_3   cov 46
 7  winning_move_is_3   cov 14      7  blocking_move_is_2  cov 38
```

<Aside type="caution" title="800局で直っても、優先順位を学べたとは限らない">
どちらのコーパスにも、`blocking_move_is_2` を `winning_move_is_3` より下へ置くべきだと示す反例は
ありません。800局で正しい順序になったのは、支持記録の頻度が偶然逆転したためです。

「コーパス内で反例がない」という評価だけでは、ゲーム全体で正しいことを保証できません。そのため、
生成した Agent は到達可能な局面を列挙するテストでも検証します。
</Aside>

## 相手を回すと、量の半分で足りる

`concept:continuous-match-loop` には、round_robin、ランダムサンプリング、自己対戦、リーグという
四つの組み合わせ方があります。framework 側の `matchloop` が管理するのは、シードと集計だけです。
**誰と誰を対戦させるかは、呼び出し側が決めます**。有効な組み合わせはゲームによって異なるためです。

ここでは、コイン、step 3 の手書きボット、完璧な打ち手の3体を順番に対戦させます。

3体を選ぶ基準は強さではなく、**作る局面が異なること**です。コインは通常の方策では選ばない手を指し、
手書きボットは「勝ちとブロック」が現れる局面を多く作ります。完璧な打ち手は、好みより勝ちや
ブロックを優先すべき局面を確実に作ります。

```
rotated 200 games: 77.3% explained; coin 800 games: 72.5%
```

相手を切り替えた200局の被覆率は、コインだけと対戦した800局を上回りました。この結果から、
step 5 の正式なコーパスは400局とします。step 4 の半分の局数です。

## 完璧な教師は蒸留できない

`distill/teacher.go` の `Perfect` は全幅探索を行い、負けません。三目並べは状態空間が小さいため、
すべての手を厳密に探索できます。この `Perfect` を記録を残す**教師**とし、条件を変えて12通り
測定します。記録から蒸留する方策を**生徒**と呼びます。

```
judgement random       200 games  70.7% explained
judgement random       400 games  71.7% explained
judgement random       800 games  72.5% explained
judgement round_robin  200 games  77.3% explained
judgement round_robin  400 games  77.6% explained
judgement round_robin  800 games  77.8% explained
fork      random       200 games  77.0% explained
fork      random       400 games  77.5% explained
fork      random       800 games  78.3% explained
fork      round_robin  200 games  79.2% explained
fork      round_robin  400 games  79.4% explained
fork      round_robin  800 games  79.7% explained
best of twelve runs: 79.7%
```

**どの条件でも被覆率は100%になりません**。局数を4倍にすると +1.8ポイント、語彙を増やすと
+7ポイント、相手を切り替えると +2ポイントです。手書きボットでは100%になりましたが、
完璧な教師では最良でも79.7%でした。

### 原因は賢さではない

三目並べの初手は、最適に指せばどのセルを選んでも引き分けになります。そのため、探索は9通りの
候補に**同じ値**を返します。最後の一手は、ゲームの強さとは無関係な規則で選ぶしかありません。
`Perfect.Principled` が false ならループの走査順、true なら中央→角→辺の好みで選びます。
どちらも最適手を選ぶため、**強さは同じです**。

述語が表せるのは、局面から判断できる事実です。しかし、この局面には同価値の手から一つを選ぶ理由が
ありません。**教師の選択に局面上の理由がなければ、記録から再現できる規則もありません**。

step 4 で手書きボットを再現できたのは、単に教師が弱かったためではありません。
**すべての指し手に、述語で表せる理由があった**ためです。

<Aside type="caution" title="語彙を増やすと、黙る代わりに堂々と間違える">
fork 述語（`creates_fork_at_k` / `blocks_fork_at_k`）を追加した場合の内訳です。

```
judgement: 57 silent, 12 wrong.  fork: 3 silent, 36 wrong
```

行動を返さない局面は 57 → 3 に減りますが、**間違う局面は 12 → 36 に増えます**。語彙を増やすと、
採掘器はコーパス内に反例がない規則をより多く見つけられます。しかし、**コーパス内に反例がない
だけでは、ゲーム全体で正しいとは限りません**。
</Aside>

### 探索はそのまま座らせられる。ただし高い

`Perfect` も通常の `session.Agent` なので、蒸留せずにそのまま席へ置けます。問題は実行コストです。

```
search 614.166µs per decision, list 55ns — 11167x
```

この測定では、alpha-beta 法で枝刈りしています。最適化済みの探索と比べても、決定リストとの間には
**4桁の差**があります。30tps の tick 予算は 33ms です。3×3 の盤面で一手を選ぶだけで、
一席がその1.8%を使います。

`rule:generated-agent-code-is-deterministic` には `cost_bound` という項目があります。述語は
Agent ごと、tick ごとに実行するため、生成器は上限のないスキャンを拒否します。
**生徒の実行コストが教師と同じなら、蒸留によって処理を軽くしたことになりません**。

## これは完全ゲームの限界だ

12通りすべてが8割未満なら、蒸留は強い教師に使えないようにも見えます。しかし、今回測ったのは
**解かれた完全情報ゲームで、同価値の最適手を再現する限界**です。蒸留全般の限界ではありません。

三目並べやオセロには最強の打ち手が存在します。その打ち手は、同じ価値を持つ複数の最適手から、
局面だけでは説明できない方法で一つを選びます。そのため、教師を強くするだけでは被覆率が上がりません。

一方、この framework が主に想定するゲームでは、前提が異なります。

| 完全ゲーム | アクションゲームの敵 |
|---|---|
| 最強の相手が存在します | **完璧だと面白くありません。適度に弱いことが仕様です** |
| 深い読みが要る | パターンで動く。読み合いではなく読める動き |
| 教師は探索。同値な手を恣意的に選ぶ | 教師は**人**。開発者が操作して動きを付ける |
| 恣意性が蒸留を止める | 人が付けた動きは**それ自体が仕様**。恣意ではない |

アクションゲームでは、開発者が敵を操作し、その記録を蒸留してゲーム内で再生できます。敵の動きは
最適解ではなく、開発者が意図した仕様です。そのため、今回のように「同価値の手を選んだ理由がない」
という問題は起きません。[step 3](/tutorial/step3/) で人の記録から始めたのも、この使い方へ
つなげるためです。

この使い方は、別のチュートリアルで扱います。**ボードゲーム編はここで終わりです**。

## 確かめ方

| 主張 | テスト |
|---|---|
| 200局の固定相手では規則を取りこぼす | `TestASmallCorpusIsMissingRules` |
| 400局では規則がそろっても順序を間違える | `TestAHalfCorpusHasEveryRuleAndStillPlaysWrong` |
| 相手を回した200局が、コインの800局より説明できる | `TestRotatingTheOpponentBeatsPlayingMore` |
| 完璧な教師は、12通りどれでも8割に届かない | `TestAPerfectTeacherCannotBeDistilled` |
| fork 述語は沈黙を減らし、間違いを増やす | `TestForkWordsTradeSilenceForConfidence` |
| 探索は決定リストの1万倍以上かかる（枝刈り後） | `TestTheSearchCostsWhatTheListDoesNot` |
| **両方の**生成エージェントが、到達可能な123局面すべてで手書きと一致する | `TestGeneratedAgentPlaysExactlyLikeTheBot` |

`TestAPerfectTeacherCannotBeDistilled` は、改善によって変わり得る否定的な結果を固定します。
現状では8割に届かないことをテストにしているため、語彙や採掘器の改善によって8割を超えると、
このテストが失敗して変化を知らせます。

残す仕組みはありません。三目並べでは意味のある差が生まれないため、このチュートリアルの対象外とします。
